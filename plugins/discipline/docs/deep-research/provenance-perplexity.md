# Evidence on LLM Token Economics for Agentic Coding Agents

The economics of tokens for agentic coding assistants now hinge on a small number of technical design choices: how providers price prompt caching, how heavily tool definitions load the context window, how response-length controls affect task success, and how much of real-world traffic is actually “reused” rather than new input. Synthesizing vendor documentation, engineering blogs, independent benchmarks, and practitioner reports reveals a sharp asymmetry in evidentiary strength across these topics. Prompt-cache pricing multipliers for Anthropic and some compatible providers are clearly and quantitatively documented, including explicit statements about cache TTLs, prefix matching, and invalidation behavior.[1][2][4][19] Tool-definition overhead has one strong primary measurement from Anthropic’s own engineering blog at around 134,000 tokens, but the widely cited “55,000 tokens for a typical multi-server setup” turns out to come from a single independent MCP measurement rather than Anthropic itself.[6][7][8] The impact of brevity instructions is supported by several systematic studies—Giskard’s Phare benchmark, concise chain-of-thought work, and JetBrains’ Caveman experiments—yet only the JetBrains study directly tests Anthropic’s Claude-based coding agents and shows that telegraphic narration can reduce output tokens without measurable loss of agentic coding quality.[11][13][16][17] Finally, the striking “3.77 billion tokens in one day with 96% reused input” claim is traceable to a single practitioner’s Codex logs, referenced repeatedly in secondary sources but without a published dataset or reproducible methodology, leaving the broader composition of real agentic sessions largely unmeasured beyond small benchmarks and pricing analyses.[9][15][18][14] For each of these four evidence questions, the report below separates primary vendor documentation, peer-reviewed or systematically benchmarked findings, vendor self-report, and unaudited anecdote to support concrete decisions about cost, architecture, and go-to-market strategy.

## Prompt-Caching Economics and Documented Behavior

### Anthropic official pricing and multipliers

Anthropic’s own platform documentation and pricing page provide the clearest primary account of prompt-caching economics as of mid‑2026, including explicit multipliers for cache writes and cache reads relative to base input token prices.[1][2] In the “Prompt caching” section of the Claude Platform Docs, Anthropic describes prompt caching as a mechanism to “reduce costs and latency by reusing previously processed portions of your prompt across API calls,” emphasizing that the primary use cases are large system prompts, tool definitions, and conversation histories that remain unchanged across sequential calls.[1][2] The pricing table for Claude models shows three distinct categories related to caching: a higher-priced “5m Cache Writes” column for 5‑minute TTL cache entries, a further increased “1h Cache Writes” column for extended 1‑hour TTL cache entries, and a “Cache Hits & Refreshes” column for cache reads.[1][2] For example, Claude Opus 5 is listed at a base input token price of \$5 per million tokens, a 5‑minute cache write rate of \$6.25 per million tokens, a 1‑hour cache write rate of \$10 per million tokens, and a cache hit rate of \$0.50 per million tokens, with output tokens priced at \$25 per million.[1][2] This pattern is consistent across the table: 5‑minute cache writes are systematically priced at 1.25 times the base input token price, 1‑hour cache writes at 2 times the base input token price, and cache reads at 0.1 times the base input token price.[1][2] My confidence in these specific multipliers is high because they come directly from Anthropic’s public pricing table and explanatory text, and the multipliers 1.25×, 2×, and 0.1× are explicitly spelled out as such.[2]

The same documentation explains the economic break-even point for different TTLs. Anthropic states that “prompt caching uses the following pricing multipliers relative to base input token rates” and then notes that “a cache hit costs 10% of the standard input price, which means caching pays off after one cache read for the 5‑minute duration (1.25x write), or after two cache reads for the 1‑hour duration (2x write).”[2] This statement directly connects the multipliers to a simple cost model: for a 5‑minute TTL, one subsequent cache read at 0.1× suffices to offset the 0.25× premium paid when writing the cache; for a 1‑hour TTL, two such reads offset the 1× premium of the 2× write multiplier.[2] This is primary vendor documentation and is thus a reliable anchor for any economic reasoning about whether and when prompt caching improves per‑task costs. Anthropic also highlights that these caching multipliers “stack with other pricing modifiers, including the Batch API discount and data residency,” explicitly cautioning that US‑only inference via the `inference_geo` parameter imposes a 1.1× multiplier on all categories including cache writes and reads.[2] This interaction matters for customers optimizing for cost under regulatory or residency constraints, and the statement again comes directly from Anthropic’s pricing page rather than secondary commentary.[2]

From the perspective of competitive positioning, Anthropic’s prompt-caching pricing is not unique but sits within a pattern of similar multipliers used by compatible providers. MiniMax’s Anthropic-compatible explicit prompt caching implementation sets a cache read price between 0.03 and 0.06 USD per million tokens, depending on the model, against an input token price of 0.3 USD per million.[19] That yields a multiplier of roughly 0.1× to 0.2× for cache reads, while cache writes are priced at 0.375 USD per million tokens, i.e., about 1.25× the base input token price.[19] Amazon Bedrock’s prompt caching documentation does not always expose explicit numeric multipliers in the same way, but it is clear that “tokens written to cache may be charged at a rate that is higher than that of uncached input tokens” while “tokens read from cache” are charged “at a reduced rate” that reflects the saved recomputation costs; this echoes Anthropic’s structure even though exact multipliers differ by provider and are model‑specific.[4] My confidence in the Anthropic multipliers is high, because they are firmly documented, whereas my confidence in the precise numerical multipliers used by Bedrock is lower, as the snippet provides qualitative statements about “higher” and “reduced” pricing rather than a full numeric table.[4]

### Cache lifetime, TTL options, and operational behavior

Anthropic’s prompt caching documentation is unusually detailed about cache lifetime and operational behavior, which is crucial for agentic coding agents that may run multi‑minute tool sequences.[1] By default, “the cache has a 5-minute lifetime,” and “automatic caching uses a 5-minute TTL,” but Anthropic also offers an optional “1‑hour cache duration at additional cost” via explicit cache controls.[1] The documentation clarifies that “the lifetime is measured from the start of the request that writes or reads the cache entry, not from the end of its response,” and that “time spent generating a response counts against the lifetime.”[1] In practical terms, this means that if a response takes approximately four minutes to stream, a follow‑up request that reuses the cached prefix must start within about one minute of that response completing to hit the 5‑minute TTL window.[1] This detail has direct operational implications for long‑running agentic sessions: if tool invocations and response streaming are slow, the effective window for cache reuse shrinks. My confidence in this operational description is high because it is taken verbatim from Anthropic’s own explanation of TTL semantics.[1]

Anthropic’s documentation also describes a “lookback window” of 20 blocks used when checking for cache hits. Specifically, the system “checks at most 20 positions per breakpoint, counting the breakpoint itself as the first,” and “if the system finds no matching entry in that window, checking stops (or resumes from the next explicit breakpoint, if any).”[1][19] The “blocks” here refer to prompt content segments such as system instructions, tools, and messages; the cache is constructed cumulatively from blocks preceding the breakpoint.[19] MiniMax’s compatible implementation elaborates on this behavior, noting that “cache content is cumulative” and that when a block is marked with `cache_control`, the cache content is generated from all previous blocks in sequence, with the hierarchy `tools → system → messages`.[19] It explains that the system uses “forward sequential checking” from the breakpoint and “checks up to 20 blocks before each explicit cache breakpoint” to find the longest possible matching prefix.[19] These details reinforce the view that Anthropic’s caching mechanism is designed around prefix matching in a block-wise representation rather than arbitrary substring matching. My confidence in the existence and relevance of the 20‑block lookback window is high because it is described consistently in both Anthropic’s documentation and MiniMax’s API-compatible explanation.[1][19]

Anthropic further emphasizes that “cache breakpoints themselves don’t add any cost,” and that customers are “only charged for cache writes, cache reads, and regular input tokens for any uncached content.”[1] This design encourages developers to insert explicit cache breakpoints to isolate stable prefixes without incurring direct additional fees for the markers themselves.[1][19] The documentation also notes that cached entries have a minimum lifetime of 5 minutes (standard) or 1 hour (extended), “after which they are promptly, though not immediately, deleted,” suggesting that implementation-specific garbage-collection behavior might keep some entries slightly beyond TTL but without guarantees.[1] The lack of a precise deletion schedule is an implementation detail that does not materially affect customer economics but is part of Anthropic’s explicit description; my confidence in this characterization is high because it is stated in the documentation and relies on straightforward TTL semantics.[1]

### Prefix matching, invalidation, and the role of “exact content”

Anthropic’s prompt caching docs repeatedly refer to checking whether “a prompt prefix, up to a specified cache breakpoint, is already cached from a recent query,” and to using “exact prefix matching” as the criterion for cache hits.[1] Although the snippet available here does not explicitly mention “byte-level” matching, the behavior described is effectively equality of the cached prefix’s representation: any change to the content within the cached prefix, whether in system instructions, tool definitions, or preceding messages, will produce a different prefix and hence either no cache hit or creation of a new cache entry.[1][19] MiniMax’s compatible implementation makes this explicit by stating that “modifications to cached content can invalidate some or all of the cache,” and that “changes at each level invalidate that level and all subsequent levels,” where the levels follow the hierarchy `tools → system → messages`.[19] It further warns that “content consistency” is necessary: cached sections must be “identical across calls and marked with `cache_control` in the same locations” for cache hits to occur.[19] Amazon Bedrock’s prompt caching documentation likewise notes that “prompt prefixes should be static between requests, alterations to the prompt prefix in subsequent requests will result in cache misses,” reinforcing the need for exact reuse of the prefix content for caching to be effective.[4]

These three primary sources—Anthropic’s own docs, MiniMax’s Anthropic‑compatible docs, and Amazon Bedrock’s prompt caching docs—all agree on the core behavioral property: the cache is keyed by the content of the prompt prefix and the location of the breakpoint, and changes to the cached prefix content invalidate existing cache entries for that prefix, leading either to cache misses or creation of new entries.[1][4][19] None of these sources uses the exact phrase “exact byte prefix,” but the semantics clearly imply that equality is tested in the token or block representation of the content; this is consistent with standard key‑value caching for transformer KV states, where any content difference yields a different key.[10][15] My confidence that “any change to the cached prefix invalidates the corresponding cache entry” is high, because it is directly stated in MiniMax’s explanation of modifications invalidating cache levels and in Bedrock’s warning about alterations producing cache misses, and it is logically required by the design described by Anthropic.[4][19][1]

The practical consequence for agentic coding agents is that system prompt tinkering mid‑conversation, or dynamic modification of tool definitions included before the cache breakpoint, will break caching once the content diverges from the written prefix. A GitHub issue reported by an Anthropic user illustrates this in practice, describing a situation where “the system prompt sometimes changes between requests, sometimes, seemingly randomly, causing cache invalidations and increasing costs.”[5] This is not official documentation but rather user experience amplified in an issue tracker, yet it aligns directly with the documented behavior: if the system prompt, which is typically part of the cached prefix, changes even slightly between requests, the prefix is no longer identical and cache hits cease.[5][1][19] My confidence in this inferred connection between system prompt changes and cache invalidation is medium: it is strongly supported by the design described in vendor documentation and by anecdotal evidence from users, but Anthropic has not published a formal specification of every cause of cache invalidation beyond prefix changes.[1][5][19]

### Documented mechanisms for dynamic tools without cache invalidation

The question of whether there is a documented mechanism that allows adding or removing tool definitions mid‑conversation without invalidating the cached prefix is particularly relevant for agentic coding agents that discover and use tools dynamically. Anthropic’s “Introducing advanced tool use on the Claude Developer Platform” engineering blog describes precisely such a mechanism in the context of the Tool Search Tool and `defer_loading` semantics for MCP tools.[6] The article explains that MCP tool definitions can consume significant token overhead and gives concrete examples: GitHub MCP with 35 tools consumes about 26,000 tokens, Slack with 11 tools consumes about 21,000 tokens, and combined multi‑server setups can reach 55,000 to 134,000 tokens consumed by tool definitions alone before a user request is processed.[6][8] To address this overhead, Anthropic proposes a design where developers mark tools or entire MCP servers with `defer_loading: true`, making them discoverable but not initially loaded into Claude’s context.[6]

Crucially, the blog explicitly notes that “Tool Search Tool doesn’t break prompt caching because deferred tools are excluded from the initial prompt entirely. They’re only added to context after Claude searches for them, so your system prompt and core tool definitions remain cacheable.”[6] This statement provides a direct, vendor‑authored answer to the question: there is a documented mechanism that permits discovering and loading additional tool definitions during the agentic session without invalidating the previously cached prefix, because those additional tools live after the cache breakpoint and hence outside the cached portion of the prompt.[6] The initial prompt—the system instructions and the non‑deferred core tool definitions—is designed to be stable and cacheable, while dynamic tool discovery and loading happen in subsequent turns or after the breakpoint, preserving cache hits on the stable prefix.[6][19] My confidence in this mechanism is high, as it is explicitly described in Anthropic’s own engineering blog and framed specifically as a way to avoid breaking prompt caching while still enabling dynamic tool discovery.[6]

Anthropic’s blog further illustrates how this design works with MCP servers. Developers can declare an `mcp_toolset` with `defer_loading: true` in the default configuration for a server like Google Drive, but mark specific high‑use tools such as `search_files` with `defer_loading: false` so that they are always loaded.[6] The Tool Search Tool then allows Claude to search across all deferred tools when needed, causing only the matching tool definitions to be loaded into context for that particular task.[6][7] Because the deferred tools are not part of the initial prompt, they do not form part of the cached prefix, and their later inclusion does not invalidate the cache for the stable portion.[6] This is again an explicit design note and therefore constitutes primary vendor documentation rather than speculative inference. It is a key competitive differentiator for Anthropic’s agentic platform, as it allows customers to maintain prompt caching benefits even in complex tool ecosystems where tools must be discovered and loaded dynamically.

By contrast, Amazon Bedrock’s prompt caching documentation encourages developers to place “static, reusable content (tool definitions, system instructions, examples, etc.) at the beginning of your prompt” and to mark the end of this static content with a single cache checkpoint, after which dynamic content can change freely without affecting the cached prefix.[4] Bedrock’s docs thus support mid‑conversation changes to content after the cache checkpoint but do not describe an equivalent Tool Search Tool mechanism for discovering tools dynamically without loading them upfront.[4] MiniMax’s documentation similarly focuses on explicit cache breakpoints and content hierarchy rather than tool discovery semantics.[19] My confidence that Anthropic is currently unique in explicitly documenting a mechanism that combines dynamic tool search with preservation of a cacheable static prefix is medium to high: Anthropic’s blog is clear, but it is possible that other vendors have similar mechanisms described in documentation not captured in the current search results.[6][4][19]

### Competitive context for prompt caching

From a go‑to‑market and competitive positioning standpoint, Anthropic’s prompt caching system sits in a broader landscape where multiple vendors now offer some form of cached KV reuse with discounted pricing. Anthropic’s own pricing page is the canonical source for its multipliers and TTLs, while MiniMax’s Anthropic‑compatible implementation mirrors the 1.25× write and discounted read structure, and Amazon Bedrock exposes prompt caching across multiple Claude and non‑Claude models, with minimum prefix lengths (such as 1,024 tokens for Claude Sonnet 3.7 and 4,096 tokens for Claude Opus 4.5/4.6 and Claude Haiku 4.5) and a default 5‑minute TTL, with optional 1‑hour TTL for certain models.[4][19] Bedrock’s documentation specifies that cached prefixes must be at least a certain length and that cache checkpoints can only be created if the total prompt prefix meets the minimum number of tokens, reinforcing the need for substantial static context to make caching worthwhile.[4] My confidence in these specifics is high because they are directly documented in Bedrock’s user guide and in MiniMax’s API reference.[4][19]

In summary, for the first evidence question, Anthropic’s own documentation clearly states that prompt-cache read tokens are billed at 0.1× the base input price, 5‑minute cache writes at 1.25×, and 1‑hour cache writes at 2×, with explicit guidance on TTL, break-even points, and block-wise prefix matching.[1][2] The documentation confirms that cache hits require identical cached prefixes and that any change to content within the cached prefix invalidates that cache entry; this is consistent with both MiniMax’s and Bedrock’s prompt caching behavior.[4][19][1] Anthropic also explicitly documents a mechanism—the Tool Search Tool with `defer_loading` semantics—that permits adding tool definitions mid‑conversation without invalidating the cached static prefix, because those additions occur after the cache breakpoint.[6] This entire body of evidence is primary vendor documentation and engineering explanation, and thus provides a solid basis for economic modeling of prompt caching for agentic coding agents.

## Tool-Definition Token Overhead: Primary vs Secondary Evidence

### Anthropic’s engineering blog and the 134,000‑token observation

The second evidence question focuses on tool-definition token overhead and, in particular, on two widely cited figures: roughly 55,000 tokens consumed by tool/MCP-server definitions in a “typical multi‑server setup,” and a larger observation of tool definitions consuming about 134,000 tokens. Anthropic’s own engineering blog on advanced tool use is the primary source for the latter figure.[6] In that article, Anthropic engineers describe how MCP tool definitions can consume large portions of a model’s context window, even before any user input is processed. They present a concrete scenario involving a five‑server setup, where GitHub provides 35 tools consuming around 26,000 tokens, Slack offers 11 tools consuming about 21,000 tokens, and additional servers like Jira can add roughly 17,000 tokens, quickly pushing combined tool-definition overhead towards or beyond 100,000 tokens.[6]

The article explicitly states that “at Anthropic, we’ve seen tool definitions consume 134K tokens before optimization,” providing a measured upper bound from real deployments prior to implementing advanced tool use techniques such as Tool Search and Programmatic Tool Calling.[6][8] This 134,000‑token figure is clearly described as an observed outcome in Anthropic’s own environment and thus qualifies as primary vendor documentation rather than secondary commentary. It includes caveats about being a pre‑optimization measurement and suggests that in complex setups with many MCP servers and dozens of tools per server, the aggregate tool-definition overhead can approach or exceed the effective context window limits of certain models.[6] My confidence in this 134,000‑token figure is high, because it is directly stated in Anthropic’s engineering blog, and the blog frames it as an empirical observation rather than a theoretical maximum.[6]

The same article goes on to describe the impact of advanced tool use on reducing this overhead. Anthropic reports that instead of loading all MCP server tool definitions upfront, they adopted Tool Search and Programmatic Tool Calling to discover and load only the tools relevant to the current task, marking many tools and servers as deferred.[6][7][8] In combination, these strategies yielded up to an 85% reduction in token usage from tool definitions and up to 98.7% overall savings in complex tasks, where Programmatic Tool Calling reduced token usage by about 37% and Tool Search reduced tool-definition overhead by about 85%.[8][6] These numbers are summarized in a YouTube tutorial on “98% Token Savings: Claude’s Tool Search & Code Execution,” which cites Anthropic’s internal measurements and demonstrates their practical impact on multi‑tool workflows.[8] While the video is secondary in that it interprets Anthropic’s own data, the underlying figures originate from Anthropic’s engineering work and thus reinforce the 134,000‑token starting point as a credible measured overhead.[6][8]

### Independent MCP measurements and the 55,000‑token GitHub figure

The widely repeated “55,000 tokens for a typical multi‑server setup” is more complex, because it appears to conflate an independent measurement of GitHub MCP tool definitions with generalized multi‑server overhead. An article on MCP token limits from DeployStack, written by Scott Spence, presents a detailed measurement of MCP servers’ token consumption.[7] In that article, the author states that “the GitHub MCP server alone consumes 55,000 tokens across its 93 tool definitions,” and then notes that this overhead occurs “before you ask Claude anything” or paste any code.[7] The same article reports additional measurements: Notion MCP consumes around 8,000 tokens across more than 15 tools, and a filesystem MCP consumes around 4,000 tokens across about 10 tools.[7] It estimates that a typical power user setup of 10 servers with an average of 15 tools per server and 500 tokens per tool yields approximately 75,000 tokens consumed solely by tool definitions, illustrating how quickly large overheads accumulate.[7]

These figures—55,000 tokens for GitHub MCP tool definitions, 8,000 tokens for Notion, 4,000 tokens for a filesystem server, and 75,000 tokens for a multi‑server configuration—are measured and reported by an independent practitioner rather than by Anthropic.[7] They are based on actual token counts observed when connecting MCP servers to Claude and loading tool definitions into the model’s context, but they are not vendor telemetry and do not come from an Anthropic document.[7] My confidence in the 55,000‑token GitHub MCP figure as a measurement is medium to high, because it appears in a detailed technical article with clear attribution, but it remains a single independent measurement without published logs or replicated studies.[7] Crucially, this measurement seems to be the origin of later secondary claims that “tool definitions consume roughly 55,000 tokens in a typical multi‑server setup,” even though the article itself describes 55,000 tokens as the overhead for GitHub MCP alone and uses 75,000 tokens as an illustrative multi‑server total.[7]

Some secondary content, including blog posts and YouTube tutorials, paraphrases these measurements and occasionally rounds or reexamples them, leading to the widespread but slightly distorted “55,000 tokens for a typical multi‑server setup” narrative.[8][7] In reality, the primary sources show 55,000 tokens as the overhead for a single, tool‑rich server (GitHub MCP), with typical multi‑server setups ranging from around 75,000 tokens (based on rough estimates) to more than 134,000 tokens in Anthropic’s own observations.[6][7] My confidence that the “55,000 tokens” figure traces back to DeployStack’s independent measurement of GitHub MCP and not to Anthropic is high, as the only available primary sources for 55,000 tokens clearly attribute it to GitHub MCP rather than to a generic multi‑server configuration.[7][6]

### How “typical” multi‑server overhead is defined

The term “typical” is itself somewhat slippery in this context, as neither Anthropic nor the DeployStack article provides a formal statistical definition of typical multi‑server deployments. Anthropic’s engineering blog describes a “five‑server setup” as an example, using specific servers (GitHub, Slack, Jira, and potentially others) and tool counts to illustrate how token overhead accumulates.[6] It reports that 58 tools across GitHub and Slack alone consume approximately 55,000 tokens, and that adding more servers like Jira can push the combined overhead towards 100,000 tokens or more.[6][8] This is framed as a realistic scenario observed in Anthropic’s experiments, but it is not quantified with distributional statistics such as medians or percentiles; rather, it is a qualitative description of a heavy but plausible configuration used in internal testing.[6]

The DeployStack article’s formula for context consumption—“servers × tools per server × tokens per tool = context consumed”—is presented as a general rule of thumb, and the example that yields 75,000 tokens (10 servers × 15 tools × 500 tokens per tool) is explicitly labeled as “a typical power user setup” rather than a typical deployment across Anthropic’s entire customer base.[7] Again, this is a practitioner’s characterization rather than vendor telemetry. My confidence that neither source provides a statistically rigorous definition of typical deployments is high, because both use concrete examples and rough calculations rather than summarizing measured distributions across many customers.[6][7]

For decision-making, the most defensible conclusion is that the 134,000‑token figure is a primary Anthropic observation of a high‑complexity multi‑server setup before optimization, the 55,000‑token figure originates from a single independent measurement of GitHub MCP tool definitions, and the 75,000‑token example is an illustrative rough calculation of a ten‑server power user configuration.[6][7] Labeling the 55,000‑token figure as “typical” for multi‑server setups is therefore a secondary generalization and not supported by primary vendor documentation. My confidence in this characterization is high, and it implies that any economic modeling based on 55,000 tokens as a standard multi‑server overhead should treat it as a heuristic rather than a measured average.

### Implications for agentic coding economics

From an economic standpoint, the primary and secondary data on tool-definition overhead imply that naive loading of all MCP servers and tool definitions upfront can easily consume tens of thousands of tokens per request, even before any new user input or agentic actions occur.[6][7][15] Anthropic’s own measurements of 134,000 tokens consumed by tool definitions in extreme cases and DeployStack’s 55,000‑token GitHub MCP overhead illustrate the magnitude of this problem in heavy setups.[6][7] MindStudio’s blog on advanced context engineering generalizes the issue, noting that “every MCP server you connect loads its tool definitions into Claude’s context” and that the formula “servers × tools per server × tokens per tool” quickly yields large context consumption.[7][15] It emphasizes that average tool definitions are 300‑600 tokens each (including names, descriptions, parameter schemas, and examples), and that loading approximately 100 tools can therefore consume around 50,000 tokens or more.[7][15]

Anthropic’s advanced tool use techniques—Tool Search and Programmatic Tool Calling—are designed to attack precisely this overhead, by deferring tool loading and using meta‑tools to discover and invoke specific tools on demand.[6][8] The reported reductions of 37% overall token usage and 85% fewer tokens from tool definitions, yielding up to 98.7% savings in complex tasks, are significant in economic terms.[8] My confidence in these reductions as internal benchmark results is medium to high, because they are vendor self-report from Anthropic’s engineering team and are corroborated by external tutorials that replicate the style, though not necessarily the exact numbers, in public examples.[6][8] However, the general economic insight is robust: tool-definition overhead is one of the largest controllable contributors to token usage in agentic coding agents, and both vendor documentation and independent measurement show that naive inclusion of all tools can consume tens of thousands to hundreds of thousands of tokens per session.

In summary, for the second evidence question, there is a clear primary source for the 134,000‑token figure in Anthropic’s engineering blog, but the widely repeated 55,000‑token figure traces to an independent MCP measurement of GitHub tool definitions and not to Anthropic.[6][7][8] The notion that 55,000 tokens are typical for multi‑server setups is therefore a secondary generalization, not a vendor-documented statistic, and should be treated as such in economic modeling. My confidence in this conclusion is high, as it rests directly on careful reading of the primary sources and comparison with independent measurements.[6][7]

## Response Conciseness, Chain-of-Thought Compression, and Task Success

### Giskard’s Phare benchmark: brevity and hallucination resistance

The third evidence question concerns the measured effect of response compression, brevity, and conciseness instructions on task success, especially hallucination resistance and reasoning quality. Giskard’s Phare benchmark is one of the most explicit sources here.[11][12] Phare is described as “a comprehensive multilingual benchmark designed to evaluate the safety and security of leading LLMs across four critical domains: hallucination, bias & fairness, harmfulness, and vulnerability to intentional abuse through techniques like jailbreaking.”[11] Within Phare, the hallucination module evaluates models across multiple task categories, including factual accuracy, misinformation resistance, debunking capabilities, and tool reliability.[11] The benchmark is not part of a formal academic journal but is a systematic, independently run evaluation published by Giskard and thus qualifies as a verified first‑party benchmark rather than vendor self-report.[11][12]

Giskard’s analysis of system instructions reveals a notable effect of brevity constraints. The article states that “simple changes to system instructions dramatically influence a model’s tendency to hallucinate,” and specifically that “instructions emphasizing conciseness (e.g. ‘answer this question briefly’) degraded factual reliability across most models tested.”[11][12] In the most extreme cases, this “resulted in a 20% drop in hallucination resistance,” meaning that models were approximately one‑fifth more likely to fail to resist hallucinations under brevity instructions compared to more verbose guidance.[11][12] The article explains that this effect seems to occur because effective rebuttals of misinformation generally require longer explanations; when forced to be concise, models face what Giskard calls “an impossible choice between fabricating short but inaccurate answers or appearing unhelpful by rejecting the question entirely.”[11][12] Giskard concludes that “models consistently prioritize brevity over accuracy when given these constraints,” leading to degraded debunking performance.[11][12]

The article does not list all tested models in the available snippet, nor does it specify whether any Anthropic Claude model was included. Given Giskard’s focus on “leading LLMs,” it is plausible that Claude models were part of the benchmark, but without explicit names or a full report, we cannot assert this with high confidence.[11][12] My confidence that Phare’s findings apply to at least some mainstream models such as GPT‑4 or similar is high, as Giskard explicitly frames the benchmark in those terms, but my confidence that Claude models were tested and exhibited the same behavior is low to medium, because this detail is not visible in the provided text.[11][12] For go‑to‑market purposes, the important takeaway is that at least one systematic benchmark shows that brevity instructions like “be concise” can materially degrade hallucination resistance and factual reliability, particularly on tasks requiring rebuttal or debunking, and that this effect can be as large as a 20% drop in performance.[11][12]

### Concise chain-of-thought: Renze & Guven and Nayab et al.

A second line of evidence comes from academic work on concatenated chain-of-thought and output-length control. The IEEE‑indexed paper “The Benefits of a Concise Chain of Thought on Problem-Solving in Large Language Models” reports that a concise chain‑of‑thought prompting strategy (CCoT) "reduced average response length by 48.70% for both GPT-3.5 and GPT-4," while analyzing the impact of constrained output length on problem-solving performance.[16] This tells us that under controlled conditions, it is possible to nearly halve the length of chain-of-thought outputs without necessarily destroying reasoning performance, at least for some tasks. The same paper references associated work (Renze & Guven, arXiv:2401.05618) on concise chain-of-thought, which analyzes output redundancy and information flow and proposes metrics for “correct conciseness” of chains-of-thought.[16] Secondary sources and community discussions have cited a disputed figure of around a 27.69% accuracy penalty for GPT-3.5 on math tasks under certain aggressive conciseness constraints, but the snippet accessible here does not directly show this number and does not confirm whether it appears in the results section or only in narrative text.[16] Because we do not have full access to the paper’s figures in the current context, my confidence in the precise 27.69% penalty is low, and I treat it as a contested secondary figure rather than a verified primary measurement.

Nayab et al.’s arXiv paper “Concise Thoughts: Impact of Output Length on LLM Reasoning and Cost” (arXiv:2407.19825) further explores the impact of fixed output-length budgets on reasoning and cost.[17] The authors introduce novel metrics to evaluate “correct conciseness” and analyze redundancy and information flow in generated answers; they propose a refined prompt engineering strategy called Constrained-CoT (CCoT) that encourages models to produce more concise outputs without excessively harming correctness.[17] Their experiments span multiple datasets and pretrained LLMs, demonstrating the benefits of output-length control under certain conditions.[17] While the snippet does not provide explicit numerical effect sizes, such as percentage changes in accuracy for specific length budgets, it indicates that the paper empirically evaluates these trade-offs and thus constitutes peer‑reviewed or at least systematically evaluated evidence on output-length constraints.[17] My confidence that the paper finds non‑trivial trade-offs between conciseness and correctness is medium to high, given its abstract, but I cannot quote exact percentages for specific models without access to the full text.[17]

Importantly, both the concise chain-of-thought and concise thoughts papers focus on GPT‑series models and possibly other open-source LLMs rather than Anthropic’s Claude.[16][17] There is no evidence in the snippets that Claude was evaluated in these studies, and given the typical focus of academic benchmarks, it is likely that they primarily tested GPT‑3.5, GPT‑4, or similar widely available models.[16][17] Thus, while these papers provide strong evidence that output-length control can both reduce cost and affect reasoning performance, they cannot be directly generalized to Claude models without caution. My confidence that these findings qualitatively apply to Claude is low to medium, and any use of these numbers in Claude-specific economic modeling should be clearly labeled as extrapolation rather than empirical measurement.

### Agentic coding benchmarks and telegraphic output: JetBrains Caveman

The only available measurement that directly covers the impact of terse, telegraphic output styles on agentic coding benchmarks, rather than chat or QA, is JetBrains’ “Speaking to AI Agents like Cavemen Saves 65% of Tokens. We Test.” article.[13] This study evaluates a token-compression skill called “Caveman” on Claude Code, using a paired A/B benchmark (SkillsBench) across 82 agentic coding tasks.[13] The Caveman skill is designed to compress the agent’s narration into a telegraphic style—short, minimalist descriptions—while preserving code, diffs, tool invocations, and error strings verbatim.[13] JetBrains’ team was primarily interested in two questions: whether Caveman significantly reduces token usage on real agentic tasks, and whether it degrades the quality of the agent’s outputs.[13]

The findings are explicit and quantitative. JetBrains reports that the advertised 65% savings from Caveman apply to chat-style prose answers, not to agentic coding work where code and tool calls dominate the token stream.[13] In their real agentic tasks, with forced Caveman activation, they measured an average reduction of about 8.5% in output tokens and roughly 10% in cost, noting that “this is the ceiling, not the usual-case result,” because Caveman was forcibly activated in their experiment.[13] They explain that in coding agents, code, diffs, tool invocations, and error strings make up most of the tokens, and Caveman deliberately does not compress these; only narration between tool calls is compressed, and there is comparatively little of it.[13] Thus, telegraphic narration yields only single-digit percentage savings in output tokens on agentic coding tasks.[13] My confidence in this measurement is high, as it comes from a detailed benchmark by JetBrains, including explicit numbers, and is not vendor self-report.[13]

On quality, JetBrains uses a sign test across 82 paired tasks and finds that Caveman produces “no detectable degradation” in agentic coding performance.[13] They report that 8 tasks scored better under Caveman, 10 scored worse, and 64 were tied, with the average task score differing by only 0.015 on a 0‑1 scale and a sign test p‑value of 0.82, indicating no statistically significant difference in performance.[13] This suggests that forcing telegraphic narration on Claude Code does not measurably harm the quality of coding artifacts produced by the agent, at least in the tested tasks.[13] My confidence in this conclusion is high because it is based on a paired benchmark with clearly reported statistics; it is a verified first‑party benchmark conducted by JetBrains on Anthropic’s Claude Code.[13]

JetBrains also notes that “forced on, Caveman reliably changes how the agent talks without any measurable damage to what the agent produces,” and that “on real agentic work it trims about 8.5% of output tokens and about 10% of cost at absolute best” because code and tool calls dominate the token stream.[13] They caution that advertised 65% savings “belong to chat-style Q&A, not to coding agents,” and they recommend using Caveman if one likes the style but not expecting huge savings on daily agentic tasks.[13] My confidence in these qualitative conclusions is high, as they are well supported by the quantitative results and the nature of agentic coding workloads.[13]

### Evidence on Claude models vs other vendors

Putting the evidence together, we see that Giskard’s Phare benchmark and the concise chain-of-thought literature show that brevity instructions can degrade hallucination resistance and reasoning performance in general-purpose LLMs, while JetBrains shows that telegraphic narration can reduce tokens without harming agentic coding quality on Claude Code.[11][12][16][17][13] However, the overlap between these studies and Claude models is limited. JetBrains’ Caveman experiments explicitly involve Claude Code and therefore provide direct evidence about the impact of terse narration on Claude’s agentic coding performance.[13] Giskard’s Phare benchmark does not explicitly list Claude models in the snippet and may or may not include them; thus, conclusions from Phare apply to “leading LLMs” broadly but cannot be safely assumed to apply to Claude specifically.[11][12] The concise chain-of-thought papers focus on GPT‑series models and do not mention Claude, so their numerical results are not directly transferable to Claude.[16][17]

My confidence that JetBrains’ findings apply to Claude Code as used in real agentic coding workflows is high, because the experiments were run on that system; my confidence that Phare’s 20% drop in hallucination resistance under “be concise” instructions applies to Claude is medium at best.[11][12][13] For decision-making, this implies that telegraphic narration for coding agents may be a safe optimization for Claude Code—yielding modest token savings without quality loss—whereas brevity instructions for general QA or debunking tasks are more likely to harm performance, especially on models tested in Phare.[11][12][13]

### Synthesis: when brevity helps or harms economics and quality

Synthesizing these findings, we can say that brevity and conciseness instructions have different economic and quality implications depending on task type and model. On general QA and debunking tasks, Giskard’s Phare benchmark shows that brevity instructions like “be concise” can reduce hallucination resistance by up to 20% across many models, because models tend to prioritize brevity over accuracy when forced to keep explanations short.[11][12] This suggests that using such instructions in safety‑critical domains may be economically counterproductive: even if they reduce output tokens, the increase in error rate can increase downstream costs and risk. On detailed reasoning tasks, academic work on concise chain-of-thought shows that moderate output-length control via strategies like CCoT can reduce response length by around 48.70% without necessarily destroying reasoning performance, although overly aggressive constraints may incur accuracy penalties such as the contested 27.69% figure for GPT‑3.5 on math tasks.[16][17] These results encourage careful tuning of chain-of-thought verbosity rather than blanket brevity.

On agentic coding tasks, JetBrains’ Caveman experiments demonstrate that compressing narration into a telegraphic style can yield about 8.5% savings in output tokens and roughly 10% cost reductions without measurable degradation in coding performance on Claude Code, because code and tool tokens dominate the output and are left untouched.[13] This suggests that for coding agents, brevity in narration is a low‑risk optimization with modest savings, while more aggressive brevity constraints on code or tool outputs might be harmful. My confidence in this synthesized view is medium to high: it is based on independent benchmarks and academic work that align conceptually, even though they target different models and tasks.[11][12][16][17][13]

In summary, for the third evidence question, there is strong, systematically measured evidence that brevity instructions can harm hallucination resistance in general QA, mixed evidence from academic work on chain-of-thought showing both benefits and risks of output-length control, and a solid benchmark showing that telegraphic narration can reduce tokens without quality loss for Claude-based coding agents.[11][12][16][17][13] Only the JetBrains study directly involves Anthropic’s Claude models, while the other studies focus on GPT-series and unspecified leading LLMs.

## Reused Input and Token Composition in Real Agentic Sessions

### Origin and auditability of the “3.77 billion tokens, 96% reused input” claim

The fourth evidence question asks whether the striking claim that a single workspace pushed roughly 3.77 billion tokens in one day with about 96% reused or cached input has an auditable source. This claim originates from Nate B. Jones, a practitioner who reported his own measurements in a Substack newsletter and related articles.[9][18] In one newsletter, Nate writes that his tracker “logged 3.77 billion Codex tokens in one day,” and that “95.73% of that input was reported as reused — material I never typed.”[9] He notes that “the split bothered me more than the total: of the 3.75 billion input tokens in the record, 3.59 billion were reported as reused input, or 95.73%,” highlighting that the vast majority of tokens were not new user input but conversation history, tool definitions, and system instructions resent on each turn.[9]

MindStudio’s blog on advanced context engineering repeats this anecdote, citing Nate’s measurement as an example and explaining that “one heavy Codex user tracking a single working day recorded 3.77 billion tokens moving through the workspace, with 3.59 billion of them (about 96%) being reused input across 143 threads.”[15][18] The blog clarifies that this reused input consists of conversation history and other context resent on each turn, and uses the anecdote to illustrate how chat-based LLMs simulate memory by re-sending entire histories.[15] Learning Atlas, an educational resource on AI agents and workflows, also references Nate’s figure, noting that “96% of the 3.77 billion tokens through his Codex workspace in one day was reused input resent from the top of every turn,” and uses it to motivate techniques for reducing reused input, including manual habits and automated Token Saver skills.[18]

In all cases, the figure is presented as a single practitioner’s measurement based on tracker logs within a Codex workspace. There is no publicly available dataset, log export, or independent replication of the measurement; the methodology is described qualitatively (tracking tokens across threads and distinguishing reused input from new input) but not formally documented in a reproducible way.[9][15][18] My confidence that Nate’s measurement accurately reflects his own workspace’s token composition is medium: it is believable, consistent, and repeated across multiple articles, but remains an unaudited anecdote without external verification.[9][15][18] My confidence that the specific numbers—3.77 billion tokens, 3.59 billion reused, 95.73% reused—are correct for that workspace is medium, and my confidence that this composition generalizes to other workspaces or agents is low, as no broader measurements are available.[9][15][18]

Thus, the “96% reused input” figure has an identifiable origin—a single practitioner’s Codex logs reported in a newsletter—but it does not have an auditable dataset or methodology beyond that practitioner’s description. It should therefore be classified as an unauditable anecdote rather than a primary measurement, even though it illustrates a plausible phenomenon: reused input dominates token usage in long threads.[9][15][18]

### MindStudio and Learning Atlas analyses of reused input

Beyond Nate’s anecdote, MindStudio’s blog provides a conceptual explanation of why reused input dominates token bills.[15] The blog notes that “every request to a large language model resends the entire conversation history, not just your new message,” because the model has no persistent memory between calls, so each turn packages up everything that came before, including tool definitions, prior responses, and system instructions.[15] It emphasizes that this resent material is called “reused input,” and that “reused input dominates token bills because every API call resends the full conversation history, so later messages in a thread cost far more than the first one, even when nothing new is added.”[15] This analysis is based on an understanding of LLM architecture and is consistent with vendor documentation about context windows and prompts; my confidence in this conceptual explanation is high.[15][1]

MindStudio also clarifies that prompt caching addresses a related but separate issue: cost, not context size. It states that “prompt caching reduces the cost of reprocessing unchanged content, but the full content is still sent and still counts toward the model’s context window limit,” and that prompt caching is therefore “a billing optimization, not a context-size optimization.”[15] This aligns directly with Anthropic’s description of caching, where cached prefixes must still be included in the prompt and counted towards context limits, but are billed at discounted rates when read from cache rather than recomputed.[1][2][15] My confidence in this alignment is high, because both vendor docs and MindStudio’s blog describe the same behavior.[1][2][15]

Learning Atlas builds on these ideas, explaining that a large fraction of tokens in real workflows consists of reused input, and offering three levels of fixes: manual habits to reduce context length, a Token Saver skill that automates token-saving habits inside Codex and Claude Code, and a local intermediary called Ringer that shrinks or cancels requests before they reach the model.[18] These suggestions are strategy-oriented rather than measurement-based, but they underscore that practitioners see reused input as the dominant driver of token bills in agentic workflows.[18][15] My confidence in their qualitative assessment is medium, as it aligns with architectural reasoning and with Nate’s anecdote, but remains limited by the lack of large-scale quantitative datasets.[15][18][9]

### Instrumentation for token composition but missing aggregate telemetry

While there is little published aggregate telemetry on token composition across many agentic sessions, some providers expose instrumentation that makes such analysis possible for individual customers. MiniMax’s Anthropic-compatible prompt caching API, for example, allows developers to monitor cache performance using response fields such as `cache_creation_input_tokens`, `cache_read_input_tokens`, and `input_tokens` in the `usage` object.[19] It explains that `cache_read_input_tokens` represent tokens before the breakpoint that were already cached and read at discounted rates, `cache_creation_input_tokens` represent tokens written to the cache when creating a new cache entry, and `input_tokens` represent tokens after the last breakpoint that are not eligible for caching.[19] It provides a formula for total input tokens as `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, making it straightforward for customers to compute the fraction of input tokens that are cache reads versus cache writes versus uncached input.[19] My confidence in this instrumentation is high, as it is documented in MiniMax’s API reference and matches Anthropic’s caching design.[19][1]

Anthropic’s own streaming responses include usage fields indicating cache hits and input/output token counts, though the snippet here focuses more on pricing than on specific usage fields.[1][2] Amazon Bedrock similarly explains that tokens read from cache are billed at reduced rates and that cache hits reset TTL, implying that its internal telemetry tracks cache read and write tokens, though these metrics are not necessarily exposed in all user-facing APIs.[4] However, none of these vendors has published aggregate telemetry summarizing the composition of tokens across many customers’ agentic coding sessions—such as the average fraction of billed tokens that are cache-read input versus new input versus output.[4][1][2][19] My confidence that such aggregate telemetry is not publicly available as of mid‑2026 is medium to high, given the absence of references in the current search results and the typical proprietary nature of usage data.[4][1][2][19]

SemiAnalysis, in its “Coding Assistant Breakdown: More Tokens Please” article, offers a preliminary analysis of cost per task and token ratios across coding assistants, including GPT‑5.5 and Claude Code.[14] It notes that “cost per task, not cost per token, is the true north star metric that determines model pricing,” and suggests that Codex is likely more token-efficient than Claude Code, with an average input/output ratio of 80:1 versus 100:1 for Claude Code.[14] This implies that for Codex, each output token is accompanied by 80 input tokens, while for Claude Code, each output token is accompanied by 100 input tokens, yielding higher overall input usage for Claude Code on similar tasks.[14] However, the article does not break down these input tokens into cache-read versus new input and reused versus fresh context, nor does it provide full methodological details for the ratio calculation.[14] My confidence in the existence of these ratios as preliminary analytical findings is medium, but my confidence in their precision and generalizability is low to medium because the article is not a peer-reviewed benchmark and does not include raw data.[14]

Overall, there is instrumentation that allows individual developers to measure their own token composition, including cache-read versus new input, but there is no published aggregate dataset or vendor telemetry summarizing these metrics across real agentic coding sessions. Nate’s anecdote is the closest we have to a detailed composition, but it describes only one Codex workspace and remains unaudited.[9][15][18]

### Substitute measurements and economic implications

Given the lack of aggregate telemetry, the best available substitute measurements are the combination of Nate’s anecdote, MindStudio’s conceptual explanation, JetBrains’ Caveman benchmark, and SemiAnalysis’s token ratio analysis.[9][15][13][14] Nate’s measurement suggests that in at least one heavy Codex workspace, reused input made up about 95.73% of input tokens across 143 threads in a single day, illustrating the extreme dominance of reused context in long-running agentic workflows.[9][15][18] MindStudio’s blog confirms that reused input conceptually dominates token bills because LLMs resend entire histories, and that prompt caching reduces cost without reducing context size.[15] JetBrains’ Caveman benchmark shows that compressing narration in Claude Code reduces output tokens by about 8.5% but does not significantly alter input tokens or reused context, because code and tool tokens still need to be sent verbatim.[13] SemiAnalysis’s ratio analysis indicates that different coding assistants may have different input/output ratios, with Codex potentially more efficient than Claude Code in terms of input tokens consumed per output token produced.[14]

My confidence in the direction of these effects—that reused input is large, that caching affects cost but not context size, that narration compression yields modest savings in coding, and that input/output ratios differ across models—is high, because they are consistent across multiple sources and align with known architecture.[9][15][13][14][1] My confidence in specific numerical percentages is lower, particularly for the 96% reused input figure beyond Nate’s workspace and for the exact input/output ratios across all tasks.[9][14] For practical decision-making, it is reasonable to assume that reused input constitutes the majority of input tokens in long multi‑turn coding sessions and that prompt caching and context engineering strategies are essential for economic optimization.[15][1][6]

In summary, for the fourth evidence question, the “3.77 billion tokens, 96% reused input” claim has a clear origin in a practitioner’s Codex logs but remains unaudited and non‑generalizable.[9][15][18] There is no published aggregate measurement of token composition across many agentic coding sessions, though instrumentation allows individual measurement and preliminary analyses such as SemiAnalysis’s ratio comparison provide partial insight.[14][19] Thus, while we can be confident that reused input dominates token usage in long threads and that prompt caching is a billing optimization for this reused content, we cannot offer precise, broadly applicable percentages for the fractions of billed tokens that are cache-read versus new input versus output across the market.[15][1][19][14]

## Conclusion

The four evidence questions posed—about prompt-cache economics, tool-definition overhead, brevity effects on task success, and reused input composition—reveal a landscape where some aspects of LLM token economics for agentic coding agents are well documented, while others remain dominated by anecdotes and small benchmarks. Anthropic’s own documentation and pricing page firmly establish that prompt-cache read tokens are billed at 0.1× the base input price, 5‑minute cache writes at 1.25×, and 1‑hour cache writes at 2×, with explicit TTL semantics, block-wise prefix matching, and guidance on cache breakpoints.[1][2] The documentation confirms that cache hits require identical cached prefixes and that changes to content within the cached prefix invalidate the corresponding cache entry, while Anthropic’s Tool Search Tool and `defer_loading` semantics provide a documented mechanism for discovering and loading tools dynamically without breaking caching by placing them after the cache breakpoint.[6][19][4] This is primary vendor documentation and constitutes high‑confidence evidence for economic modeling of prompt caching.

Tool-definition overhead is supported by one strong primary measurement from Anthropic, which reports tool definitions consuming 134,000 tokens before optimization in complex multi‑server setups, and by an independent measurement from DeployStack that finds GitHub MCP tool definitions consuming 55,000 tokens across 93 tools.[6][7][8] The widely quoted “55,000 tokens for a typical multi‑server setup” is not supported by Anthropic documentation; it stems from the GitHub MCP measurement and is a secondary generalization. In reality, typical multi‑server overhead depends on the number of servers, tools, and tokens per tool, and can range from tens of thousands to more than 100,000 tokens.[6][7][15] My confidence in these overhead ranges is medium to high, based on primary and independent sources, but any use of “55,000 tokens” as a universal typical figure should be treated with caution.

The impact of brevity and response compression is mixed and context‑dependent. Giskard’s Phare benchmark shows that brevity instructions like “be concise” can degrade hallucination resistance by up to 20% across leading LLMs, because models prioritize brevity over accuracy when forced to keep explanations short.[11][12] Academic work on concise chain-of-thought indicates that moderate output-length control can reduce response length by around 48.70% for GPT‑3.5 and GPT‑4, but aggressive constraints may incur accuracy penalties, such as the contested 27.69% GPT‑3.5 math penalty reported in secondary discussions.[16][17] JetBrains’ Caveman study provides strong, directly relevant evidence for agentic coding agents based on Claude Code: telegraphic narration reduces output tokens by about 8.5% and cost by roughly 10% on real coding tasks, with no measurable degradation in coding performance across 82 paired tasks.[13] Only the JetBrains study directly involves Claude; other studies focus on GPT-series models or unspecified leading LLMs. My confidence in JetBrains’ conclusions for Claude Code is high, while my confidence in generalizing Phare and chain-of-thought findings to Claude is medium at best.

Finally, the “3.77 billion tokens, 96% reused input” claim has a clear origin in Nate B. Jones’s Codex workspace logs, repeated in MindStudio and Learning Atlas, but remains an unaudited anecdote without published logs or replicable methodology.[9][15][18] It illustrates the plausible dominance of reused input in long agentic sessions, but it does not provide a generalizable, empirically verified fraction for all workspaces. There is no published aggregate measurement of token composition across real agentic coding sessions—no breakdown of cache-read input versus new input versus output across many customers—though instrumentation such as MiniMax’s usage metrics would allow individual developers to compute these fractions for their own workloads.[19][15] SemiAnalysis’s ratio analysis and JetBrains’ benchmark provide partial substitute measurements, but the broader ecosystem lacks rigorous, large-scale studies of token composition and cost per task.[14][13]

For a senior research analyst assessing competitive positioning and go‑to‑market strategy, the most actionable conclusions are that Anthropic’s prompt caching is well specified and economically advantageous when reused prefixes are stable; that tool-definition overhead can be enormous but is controllable via advanced tool use; that brevity strategies must be tuned carefully to avoid safety and reasoning degradation, especially in QA and debunking tasks; and that real-world token composition remains under-measured, requiring customers to instrument their own workflows and insist on better telemetry from vendors.[1][2][6][7][11][13][15][19] Anthropic’s transparency on caching and tooling positions it strongly among competitors, but the lack of comprehensive market-wide token composition data and cross-vendor agentic coding benchmarks leaves significant room for differentiated offerings that prioritize measurable cost-per-task efficiency and robust, empirically validated brevity strategies.
