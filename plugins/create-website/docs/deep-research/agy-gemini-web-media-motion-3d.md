#### Pillar 1: Background & Hero Video on the Web

##### 1.1 Browser Autoplay Policies (Chrome, Safari, Firefox) and Low-Power Fallbacks
All three major browser engines—Blink (Chrome/Edge), WebKit (Safari macOS/iOS), and Gecko (Firefox)—block unmuted automatic video playback without a prior user gesture or high Media Engagement Index (MEI) score, but permit deterministic muted autoplay when explicit HTML attributes are present at parse time [developer.chrome.com](https://developer.chrome.com/blog/autoplay/):
* **`muted` and `autoplay`:** Required in Chrome, Firefox, and Safari for gesture-free startup [developer.chrome.com](https://developer.chrome.com/blog/autoplay/). If a video file contains an unmuted audio track and lacks the `muted` attribute in the initial DOM markup, calling `.play()` programmatically rejects with a `DOMException: NotAllowedError` [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/Media/Autoplay_guide).
* **`playsinline`:** Mandatory on iOS and iPadOS Safari (WebKit) to permit the `<video>` element to render and autoplay within the document layout rather than hijacking the screen into the native iOS fullscreen media player [webkit.org](https://webkit.org/blog/6784/new-video-policies-for-ios/).
* **iOS Low Power Mode & Data Saver Interception:** WebKit on iOS/macOS automatically suspends HTML `autoplay` and rejects `video.play()` promises when the user's device is in **Low Power Mode**, and Android Chrome can defer autoplay under Lite/Data Saver configurations [webkit.org](https://webkit.org/blog/6784/new-video-policies-for-ios/). <INFERENCE from="WebKit autoplay policy documentation and HTMLMediaElement.play() Promise specification">Consequently, an agent must never assume `autoplay` succeeds; it must always supply a high-resolution `poster` attribute and wrap programmatic `.play()` calls in a `.catch()` handler that leaves the poster or a discreet play toggle visible rather than throwing an unhandled promise rejection.</INFERENCE>

##### 1.2 Poster Frames, Largest Contentful Paint (LCP), and Cumulative Layout Shift (CLS)
* **LCP Mechanics Since Chrome 116:** Prior to Chrome 116 (released August 2023), `<video>` elements were ignored by the Largest Contentful Paint algorithm unless a `poster` image attribute was declared [developer.chrome.com](https://developer.chrome.com/docs/web-platform/largest-contentful-paint). Starting in Chrome 116, `<video>` elements without a `poster` are evaluated as LCP candidates using the presentation timestamp of the **first decoded video frame** painted to the screen [developer.chrome.com](https://developer.chrome.com/docs/web-platform/largest-contentful-paint). When a `poster` attribute is present, LCP records whichever renders earlier: the `poster` image or the first video frame [web.dev](https://web.dev/articles/lcp). Because a compressed AVIF (`30–60 KB`) or WebP (`50–80 KB`) poster downloads and decodes in a single round-trip compared to buffering a `1.5–2.5 MB` video container, **omitting `poster` on a hero video typically degrades LCP by `800 ms` to `3,000+ ms` on 4G/mobile connections** [web.dev](https://web.dev/articles/fast-playback-with-preload).
* **Preloading the Poster:** Because the HTML preload scanner discovers `<video poster="...">` only when parsing the `<body>` (and some engines delay poster fetch until video metadata evaluation), the agent must inject an explicit preload hint in `<head>` [web.dev](https://web.dev/articles/optimize-lcp):
  ```html
  <link rel="preload" as="image" href="/media/hero-poster.avif" type="image/avif" fetchpriority="high">
  ```
* **CLS Prevention:** If a `<video>` element lacks intrinsic dimensions before metadata (`moov` atom) arrives over the network, its layout box initializes at `300x150` CSS pixels (the HTML default for replaced elements) and jumps to full viewport width once metadata parses, triggering severe Cumulative Layout Shift (`CLS > 0.25`) [web.dev](https://web.dev/articles/optimize-cls). The agent must set explicit `width="1920" height="1080"` attributes on the `<video>` tag and `aspect-ratio: 16 / 9; width: 100%; height: auto; object-fit: cover;` in CSS to lock `CLS` at `0.000` [web.dev](https://web.dev/articles/optimize-cls).

##### 1.4 Responsive Delivery via `<source media="...">`
Although part of the original HTML5 specification, `<source media="...">` inside `<video>` was temporarily removed from Blink and Gecko before being restored in **Firefox 120 (November 2023)** and **Chrome 120 (December 2023)**, aligning with Safari's continuous support [scottjehl.com](https://scottjehl.com/posts/using-responsive-video/). In late 2026, `<source media="...">` is supported across 100% of baseline browsers [caniuse.com](https://caniuse.com/mdn-html_elements_source_media). The agent must order `<source>` elements from most specific (`prefers-reduced-motion` or mobile viewport width) and highest compression (`AV1`) down to universal fallback (`H.264`):
```html

       poster="/media/hero-poster.avif" width="1920" height="1080">
  <!-- Mobile 720p tier (saves 50-65% bandwidth on cellular viewports) -->

  <source src="/media/hero-720p.webm" type="video/webm; codecs=vp9" media="(max-width: 767px)">
  <source src="/media/hero-720p.mp4" type="video/mp4" media="(max-width: 767px)">
  <!-- Desktop 1080p tier -->
  <source src="/media/hero-1080p.av1.mp4" type="video/mp4; codecs=av01.0.05M.08">
  <source src="/media/hero-1080p.webm" type="video/webm; codecs=vp9">
  <source src="/media/hero-1080p.mp4" type="video/mp4">
```

##### 1.5 Safari HTTP Byte-Range Request (`206 Partial Content`) Requirement
Apple's WebKit media engine on macOS and iOS strictly requires HTTP servers and CDNs hosting `<video>` assets to implement **RFC 9110 Byte-Range Requests** [developer.apple.com](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/CreatingVideoforSafarioniPhone/CreatingVideoforSafarioniPhone.html). When Safari discovers a `<video>` source, it sends an initial probe request with header `Range: bytes=0-1` (the first 2 bytes) to verify byte-range capability before fetching the `moov` header range [webkit.org](https://webkit.org/blog/6784/new-video-policies-for-ios/). If a custom Node/Python route, serverless function, or misconfigured proxy ignores the `Range` header and returns `HTTP 200 OK` with the full payload instead of `HTTP 206 Partial Content` (with `Content-Range: bytes 0-1/<total>` and `Accept-Ranges: bytes`), **Safari aborts media loading and displays a blank/poster box even though Chrome and Firefox play the file normally** [developer.apple.com](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/CreatingVideoforSafarioniPhone/CreatingVideoforSafarioniPhone.html).
* **Agent Verification Rule:** The agent must serve video files directly from static CDN edge storage (Vercel/Netlify/Cloudflare static assets, which support HTTP 206 natively) and verify any custom media endpoint with Apple's documented probe test [developer.apple.com](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/CreatingVideoforSafarioniPhone/CreatingVideoforSafarioniPhone.html):
  ```bash
  curl -I --range 0-99 https://example.com/media/hero-1080p.mp4
  # Must return HTTP/2 206, Accept-Ranges: bytes, and Content-Length: 100
  ```

#### Pillar 2: Generated Video for Web Use

##### 2.1 Image-to-Video (I2V) and First/Last-Frame Conditioning
Pure Text-to-Video (T2V) generation is unsuitable for production hero backgrounds because T2V cannot guarantee exact visual alignment with the static `poster` image or brand layout composition, causing a jarring cut when the video finishes buffering and replaces the poster [web.dev](https://web.dev/articles/fast-playback-with-preload). Current frontier video models support **Image-to-Video (I2V) with First-Frame and Last-Frame Conditioning** (keyframe anchoring):
* **Google Veo (Veo 2 / Veo 3.1 on Vertex AI & Gemini API):** Accepts an initial conditioning `image` (First Frame) and an optional `lastFrame` parameter in its image-to-video / frames-to-video endpoints, generating `5–8 second` clips at `24 fps` in `720p` or `1080p` that interpolate smoothly between both anchors [cloud.google.com](https://cloud.google.com/vertex-ai/generative-ai/docs/video/generate-videos).
* **Kling AI (Kling 1.6 / 2.0 / 3.0), Runway (Gen-3 Alpha / Gen-4), Luma Dream Machine (Ray 2), and OpenAI Sora:** All expose explicit start-keyframe and end-keyframe slots (`image_url` + `tail_image_url` / first-and-last-frame keyframes), generating `5 s` or `10 s` clips [docs.dev.runwayml.com](https://docs.dev.runwayml.com/).
* **The Poster-First Pipeline Rule:** The agent must first generate (or render) the high-resolution still image (`hero-poster.avif`), validate its composition and text-contrast overlays, and then pass that exact image as **Frame 0 (`first_frame`)** to the video generator. If an infinite loop is required, the agent passes the identical `hero-poster.avif` as **both** the first frame and last frame (`first_frame == last_frame`), instructing the diffusion model to return all displaced elements to their initial pixel coordinates by the final frame.

##### 2.2 Joining Clips Without Visible Skips (Duplicate Frame Drop & Color-Space Normalization)
When chaining two clips sequentially (passing the extracted last frame of Clip A as the first frame of Clip B) or looping a single clip where `first_frame == last_frame`, two mechanical defects cause a visible skip at the seam:
1. **The Duplicate Boundary Frame Hitch:** Because Clip A ends on the anchor image $F_{\text{anchor}}$ and Clip B starts on $F_{\text{anchor}}$ (or a loop wraps from $F_{N-1} = F_{\text{anchor}}$ back to $F_0 = F_{\text{anchor}}$), displaying both frames back-to-back holds the identical image on screen for **two frame intervals** (`66.7 ms` at `30 fps` or `83.3 ms` at `24 fps`). The human visual system perceives a 2-frame hold inside continuous motion as a hard stutter.
   * **Fix (Exact Frame Drop):** Before concatenation or looping, the agent must trim the final frame ($N-1$) from the preceding clip using FFmpeg's frame-accurate `select` or `trim` filter [ffmpeg.org](https://ffmpeg.org/ffmpeg-filters.html#trim):
     ```bash
     # Drop the final duplicate frame (e.g., frame 149 of a 150-frame 5s@30fps loop)
     ffmpeg -i raw_loop.mp4 -vf "select='lt(n,149)',setpts=N/30/TB" -an trimmed_loop.mp4
     ```
2. **Latent Decoder Drift & Velocity Discontinuity:** Even when conditioned on the exact same anchor frame, spatiotemporal VAE decoders across two independent generation passes exhibit subtle luminance/chroma shifts (`1–4 RGB levels`) and non-zero terminal velocity vs. zero initial velocity.
   * **Fix (`xfade` Cross-Dissolve):** When joining unconditioned tails or smoothing VAE boundary drift in ambient textures, the agent must overlap the final `0.4–0.5 seconds` (`12–15 frames`) using FFmpeg's `xfade` filter while enforcing uniform `fps` and `yuv420p` color conversion [ffmpeg.org](https://ffmpeg.org/ffmpeg-filters.html#xfade):
     ```bash
     ffmpeg -i clipA.mp4 -i clipB.mp4 -filter_complex \
       "[0:v]fps=30,format=yuv420p,setpts=PTS-STARTPTS[v0]; \
        [1:v]fps=30,format=yuv420p,setpts=PTS-STARTPTS[v1]; \
        [v0][v1]xfade=transition=fade:duration=0.4:offset=4.6[outv]" \
       -map "[outv]" -an joined.mp4
     ```

##### 2.3 Reversing Clips (Ping-Pong / Palindrome Loops)
A common shortcut to make an unconditioned clip loop is concatenating the clip with a time-reversed copy of itself (`[0:v]split[f][r];[r]reverse[rev];[f][rev]concat=n=2:v=1:a=0`).
* **When Reversing Works vs. Fails:** <INFERENCE from="Physical causality constraints in VBench-2.0 and FFmpeg reverse filter mechanics">Ping-pong reversal is valid **only** for isotropic, non-directional motion without entropic/gravitational arrows of time: abstract shader gradients, slow breathing/pulsing light, or gentle camera orbit around a static object (provided duplicate turnaround frames at the apex and nadir are dropped via `trim`). It **fails catastrophically** on any scene containing directed physics: water waves or waterfalls reversing uphill, rising steam/smoke sucking back into a nozzle, hair/cloth settling upward against gravity, vehicles/pedestrians moving backward, or sudden velocity inversion ($+v \to -v$) at the turnaround frame.</INFERENCE> The agent must classify prompt motion as `isotropic` or `directional` and forbid ping-pong reversal on `directional` clips.

##### 2.4 Length Fitting
Generative video APIs emit fixed durations (`4 s`, `5 s`, `8 s`, or `10 s` at `24` or `30 fps`). To fit a clip to a specific duration requirement (e.g., a `6.0 s` cycle or a scroll-scrubbed canvas sequence):
* **Trimming (`-ss` / `-to`):** Preferred for non-looping or `xfade`-looped ambient clips [ffmpeg.org](https://ffmpeg.org/ffmpeg.html).
* **PTS Retiming (`setpts`):** Acceptable only within **`±10% to ±15%`** (`setpts=1.12*PTS` with output `-r 30` or `24`); stretching beyond `15%` without optical flow introduces visible frame-hold judder, while FFmpeg's `minterpolate` optical-flow filter frequently produces warping/ghosting artifacts around high-contrast edges [ffmpeg.org](https://ffmpeg.org/ffmpeg-filters.html#minterpolate).

##### 2.5 What Frame-Sampled Review Misses
Automated agent QA pipelines typically evaluate generated video by extracting `4` to `8` uniformly spaced frames (e.g., `1 frame per second`) and sending them as an image grid to a Vision-Language Model (VLM). As demonstrated by the **VBench** (CVPR 2024) and **EvalCrafter** multi-dimensional video evaluation benchmarks, sparse spatial frame sampling is blind to three critical classes of temporal defects [arxiv.org](https://arxiv.org/abs/2311.17982):
1. **High-Frequency Temporal Flickering (`12–30 Hz`):** Rapid frame-to-frame luminance strobing, texture shimmering, or background boiling that occurs between $t$ and $t+1$ (`33 ms` apart). Two frames sampled `1,000 ms` apart both look crisp individually while the video strobes violently in playback [arxiv.org](https://arxiv.org/abs/2311.17982).
2. **Loop-Seam & Stitch Discontinuities:** A `1-frame` duplicate pause, a `2-frame` flash, or a sudden jump in optical-flow velocity at the boundary between the last frame ($N-1$) and first frame ($0$) [arxiv.org](https://arxiv.org/abs/2310.11440).
3. **Sub-Second Anatomical/Object Morphing:** Brief `100–300 ms` structural collapses (e.g., an object gaining and losing an edge or text warping mid-motion) that recover before the next 1-second sample window [arxiv.org](https://arxiv.org/abs/2311.17982).
* **Mandatory Agent QA Rule:** In addition to VLM semantic inspection of keyframes, the agent must run a **deterministic frame-to-frame continuity check**: (a) verify boundary similarity between frame $N-1$ and frame $0$ (using SSIM/MSE or optical-flow magnitude) to prove the loop closes without a jump cut AND is not an exact duplicate (`MSE > 0` to confirm the duplicate frame was dropped), and (b) compute adjacent-frame luminance/structural deltas across all consecutive frames ($t, t+1$) to flag high-frequency flicker spikes [arxiv.org](https://arxiv.org/abs/2311.17982).

#### Pillar 3: Scroll-Driven Animations (CSS `animation-timeline` vs. GSAP ScrollTrigger)

##### 3.1 Main-Thread Cost, INP, and CLS Impact
In **late 2026**, native **CSS Scroll-Driven Animations** (`animation-timeline: scroll()` and `animation-timeline: view()`) have reached **Baseline status** across all three major browser engines: Chromium (Chrome/Edge 115+), WebKit (**Safari 26+** on macOS/iOS), and Gecko (**Firefox 159+**) [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/CSS/animation-timeline) [caniuse.com](https://caniuse.com/mdn-css_properties_animation-timeline).

| Dimension | Native CSS Scroll-Driven Animations (`scroll()` / `view()`) | GSAP `ScrollTrigger` (`gsap` + `ScrollTrigger`) |
| :--- | :--- | :--- |
| **Execution Thread** | **Compositor Thread** (when animating `transform`, `opacity`, `filter`, `clip-path`) [developer.chrome.com](https://developer.chrome.com/docs/css-ui/scroll-driven-animations) | **Main Thread** (JavaScript `requestAnimationFrame` tick + inline style mutation) [gsap.com](https://gsap.com/docs/v3/Plugins/ScrollTrigger/) |
| **Main-Thread JS Cost During Scroll** | **`0.0 ms / frame`** (unaffected by heavy React/DOM hydration or long tasks) [developer.chrome.com](https://developer.chrome.com/docs/css-ui/scroll-driven-animations) | **`0.5 – 6.0+ ms / frame`** depending on active triggers, `scrub` interpolations, and callback work |
| **JS Bundle Payload** | **`0 KB`** [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/CSS/animation-timeline) | **`~28–32 KB` minified & gzipped** (`gsap` core ~23 KB + `ScrollTrigger` ~8 KB) |
| **Effect on INP (`<= 200 ms`)** | **Zero degradation.** Main thread remains idle to process discrete `click`, `pointerdown`, and `keydown` events during or immediately after scrolling [web.dev](https://web.dev/articles/inp). | **Moderate-to-High risk** if `onUpdate` callbacks read layout properties (triggering forced synchronous reflows) or if `ScrollTrigger.refresh()` runs during user interaction [web.dev](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing). |
| **Effect on CLS (`<= 0.1`)** | **Zero CLS** when using `transform`/`opacity` alongside CSS `position: sticky` [web.dev](https://web.dev/articles/optimize-cls). | **`pin: true` injects a `.pin-spacer` wrapper DOM node** and mutates `height`/`padding` at JS initialization time; if initialized after first paint or font load, it triggers measurable CLS unless CSS dimensions are pre-allocated [gsap.com](https://gsap.com/docs/v3/Plugins/ScrollTrigger/). |
| **Best Use Case** | Parallax, fade/scale entrances, reading progress bars, sticky card stacks, horizontal sticky tracks [developer.chrome.com](https://developer.chrome.com/docs/css-ui/scroll-driven-animations). | Complex multi-element timeline choreography, physics-based snapping, WebGL uniform scrubbing (`camera.position`), and dynamic DOM pinning [gsap.com](https://gsap.com/docs/v3/Plugins/ScrollTrigger/). |

* **Agent Decision Rule:** Use native **CSS `animation-timeline: view()` / `scroll()`** paired with CSS `position: sticky` as the default for all DOM scroll animations [developer.chrome.com](https://developer.chrome.com/docs/css-ui/scroll-driven-animations). Load GSAP `ScrollTrigger` **only** when the section requires driving non-CSS targets (such as a Three.js camera/shader uniform or an HTML `<canvas>` image sequence) or complex multi-timeline sequential pinning that cannot be expressed via CSS `position: sticky` + `view-timeline` [gsap.com](https://gsap.com/docs/v3/Plugins/ScrollTrigger/).

##### 3.2 `prefers-reduced-motion` Practice and Vestibular Safety (WCAG 2.2)
Three WCAG 2.2 Success Criteria govern motion on marketing websites:
1. **WCAG 2.2 SC 2.3.3 — Animation from Interactions (Level AAA):** *"Motion animation triggered by interaction can be disabled, unless the animation is essential to the functionality or the information being conveyed."* [w3.org](https://www.w3.org/TR/WCAG22/#animation-from-interactions) W3C's Understanding SC 2.3.3 explicitly highlights **parallax scrolling** (where foreground and background elements move at different speeds or directions during scroll) and large-area zooming/panning as primary triggers of vestibular disorders (vertigo, nausea, migraines) [w3.org](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html).
2. **WCAG 2.2 SC 2.2.2 — Pause, Stop, Hide (Level A):** For any moving, blinking, or scrolling information that (1) starts automatically, (2) lasts more than **5 seconds**, and (3) is presented in parallel with other content (which directly applies to **looping hero background videos and ambient 3D canvases**), there must be a mechanism for the user to pause, stop, or hide it [w3.org](https://www.w3.org/TR/WCAG22/#pause-stop-hide).
3. **WCAG 2.2 SC 2.3.1 — Three Flashes or Below Threshold (Level A):** Web pages must not contain anything that flashes more than **three times in any one-second period** [w3.org](https://www.w3.org/TR/WCAG22/#three-flashes-or-below-threshold).

* **Implementation Rules for Agents:**
  * **Progressive Motion Gate in CSS:** Wrap all spatial scroll animations (`translate3d`, `scale`, `rotate`, parallax offsets) inside `@media (prefers-reduced-motion: no-preference)`. Under `@media (prefers-reduced-motion: reduce)`, **never set `opacity: 0` without an animation to reveal the content** (a common bug that leaves pages blank for reduced-motion users); instead, render elements in their final layout positions and substitute spatial motion with simple `opacity` transitions or instant state changes [web.dev](https://web.dev/articles/prefers-reduced-motion).
  * **GSAP `gsap.matchMedia()`:** When GSAP is used, register all scroll timelines inside `gsap.matchMedia()` so reduced-motion users bypass pinning/parallax and receive static or crossfade layouts [gsap.com](https://gsap.com/docs/v3/GSAP/gsap.matchMedia()/):
    ```javascript
    const mm = gsap.matchMedia();
    mm.add("(prefers-reduced-motion: no-preference)", () => {
      // Full spatial ScrollTrigger timelines here; automatically reverted if OS setting changes
    });
    ```
  * **Auto-Pause Hero Video & 3D Loop on `prefers-reduced-motion: reduce` + Pause Button:** If `window.matchMedia('(prefers-reduced-motion: reduce)').matches` is `true`, the agent must pause the hero `<video>` on its poster frame (or stop the ambient 3D rotation loop) by default, and always render an accessible `<button aria-label="Pause background video">` overlay to satisfy WCAG 2.2 SC 2.2.2 (Level A) [w3.org](https://www.w3.org/TR/WCAG22/#pause-stop-hide).

##### 3.3 Touch & Scroll-Jacking Pitfalls
As documented by the **Nielsen Norman Group (NN/g)** and WebKit/Chromium engineering guides, **scroll-jacking**—intercepting native `wheel`, `touchstart`, or `touchmove` events with `event.preventDefault()` to replace the operating system's native scroll physics with a custom JavaScript virtual scroller (such as legacy configurations of Locomotive Scroll or aggressive Lenis touch overrides)—causes four severe failures [nngroup.com](https://www.nngroup.com/articles/scrolljacking-101/):
1. **Destruction of iOS/Android Asynchronous Hardware Momentum:** Mobile browsers run touch scrolling on a dedicated high-priority OS compositor thread with platform-tuned friction curves. Intercepting `touchmove` forces scrolling back onto the single-threaded JS runtime, causing immediate input lag, broken rubber-banding, and inability to flick-scroll across long pages [nngroup.com](https://www.nngroup.com/articles/scrolljacking-101/).
2. **Mobile Dynamic Address-Bar Jitter (`100vh` vs. `100svh`/`100dvh`):** On iOS Safari and Android Chrome, the browser URL/toolbar collapses and expands dynamically based on native scroll velocity. Virtual scroll containers (`overflow: hidden` on `<body>`) prevent the mobile address bar from collapsing and break dynamic viewport units (`dvh`), whereas native scrolling paired with `min-height: 100svh` (Small Viewport Height) for hero sections prevents layout jumps when the bar retracts [web.dev](https://web.dev/blog/viewport-units).
3. **Broken Native Browser Features:** Virtual scroll hijacking breaks `Cmd+F` / `Ctrl+F` (Find in Page auto-scrolling), native scrollbar thumb dragging, middle-click auto-scroll, and `Space` / `PageDown` / `Home` / `End` keyboard navigation [nngroup.com](https://www.nngroup.com/articles/scrolljacking-101/).
4. **Rule:** The agent must **never** attach `{ passive: false }` listeners that call `preventDefault()` on `wheel` or `touchmove` to hijack page scrolling, and must never set `syncTouch: true` on smooth-scroll wrappers.

#### Pillar 4: Real-Time 3D (`WebGL` / `Three.js`) on the Marketing Web

##### 4.1 Mobile GPU Budgets and `devicePixelRatio` Clamping
Modern mobile devices (iPhone 15/16/17 Pro, Galaxy S24/S25/S26 Ultra, Pixel 9/10 Pro) report `window.devicePixelRatio` values of **`3.0` to `4.0`** [threejs.org](https://threejs.org/docs/#api/en/renderers/WebGLRenderer.setPixelRatio). Because fragment shader execution scales quadratically with linear resolution ($\text{DPR}^2$), rendering a full-viewport $430 \times 932$ CSS-pixel mobile canvas at `DPR = 3.0` forces the mobile tile-based GPU to shade **$3,606,840$ physical pixels per frame** ($9\times$ the `DPR = 1.0` fill load), while `DPR = 4.0` shades **$6,412,160$ pixels per frame** ($16\times$ the load—exceeding a desktop $2560 \times 1440$ monitor).
* **Mandatory `devicePixelRatio` Rule:** The agent must **always** clamp the Three.js renderer pixel ratio to a maximum of **`2.0`** on desktop/high-tier devices and **`1.5`** on mobile viewports (`max-width: 767px`) or when post-processing passes (`EffectComposer`) are active [threejs.org](https://threejs.org/docs/#api/en/renderers/WebGLRenderer.setPixelRatio):
  ```javascript
  const maxDPR = window.innerWidth < 768 ? 1.5 : 2.0;
  renderer.setPixelRatio(Math.min(window.devicePixelRatio, maxDPR));
  ```
* **Quantitative Mobile WebGL Scene Budgets:** To maintain `60 fps` (`16.6 ms` frame budget) without triggering thermal throttling or iOS Safari **Jetsam** memory termination (which kills the entire browser tab when WebContent process memory exceeds device thresholds, often around `~250–400 MB` total tab footprint on iOS), the agent must enforce:
  * **Draw calls per frame:** `<= 50` on mobile, `<= 150` on desktop (merge static meshes or use `THREE.InstancedMesh`) [threejs.org](https://threejs.org/manual/#en/optimize-lots-of-objects).
  * **Total active triangles:** `<= 100,000–150,000` on mobile, `<= 500,000` on desktop.
  * **Total GPU VRAM (Textures + Buffers + RenderTargets):** `<= 64–96 MB` on mobile, `<= 256 MB` on desktop.
  * **Shadow maps & Post-processing:** Max 1 directional shadow map (`1024x1024` on mobile); disable multi-pass post-processing (SSAO, Depth of Field, multi-tap Bloom) or MSAA (`antialias: false` when `DPR >= 1.5`) on mobile viewports.

##### 4.2 Pausing Off-Screen Canvases (`IntersectionObserver` & `visibilitychange`)
A `<canvas>` running an unconditional `requestAnimationFrame` loop continues executing vertex/fragment shaders at `60–120 Hz` even after the user scrolls 3,000 pixels below the hero section, draining battery and competing with scroll animations for GPU compositing time.
* **Lifecycle Rule:** Every WebGL canvas must be governed by both an `IntersectionObserver` (`threshold: 0`) and `document.addEventListener('visibilitychange', ...)` that completely halts the render loop (`renderer.setAnimationLoop(null)`) when `entry.isIntersecting === false` or `document.hidden === true` [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API):
  ```javascript
  const observer = new IntersectionObserver(([entry]) => {
    if (entry.isIntersecting && !document.hidden) {
      renderer.setAnimationLoop(renderFrame);
    } else {
      renderer.setAnimationLoop(null);
    }
  }, { threshold: 0 });
  observer.observe(renderer.domElement);
  ```

##### 4.3 WebGL Availability, Context Loss (`webglcontextlost`), and Memory Disposal
WebGL 2 creation can fail or be revoked mid-session due to enterprise GPU blocklists, hardware-acceleration disabled in browser settings, mobile OS backgrounding, or GPU driver resets [threejs.org](https://threejs.org/docs/#manual/en/introduction/WebGL-compatibility-check).
1. **Pre-Flight Check:** Test `WebGL.isWebGL2Available()` (from `three/addons/capabilities/WebGL.js`) before instantiating `THREE.WebGLRenderer` [threejs.org](https://threejs.org/docs/#manual/en/introduction/WebGL-compatibility-check). If `false`, reveal a pre-rendered static `<picture>` fallback (using the generated hero image) and skip downloading the `.glb` asset and decoders.
2. **Context Loss Handler:** Attach a `webglcontextlost` listener to `renderer.domElement`, call `event.preventDefault()` (which instructs the browser to attempt context restoration rather than permanently abandoning the context), immediately stop the animation loop, and reveal the static HTML `<picture>` fallback behind or in place of the canvas [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/webglcontextlost_event).
3. **Explicit `.dispose()` on Unmount:** In Single-Page Application (SPA) route transitions or component unmounts, garbage collection does **not** free WebGL GPU resources; the agent must traverse the scene to call `geometry.dispose()`, `material.dispose()`, `texture.dispose()`, and `renderer.dispose()` [threejs.org](https://threejs.org/docs/#manual/en/introduction/How-to-dispose-of-objects).

##### 4.4 glTF Asset Delivery (`Draco` vs. `Meshopt` vs. `KTX2`) and Size Budgets
Standard PNG or JPEG textures embedded in a `.glb` file are compressed only on the network wire; upon loading, the browser decodes them on the CPU into raw 32-bit `RGBA8` bitmaps in GPU VRAM. A single $2048 \times 2048$ PNG/JPEG expands to **$16.78\text{ MB}$** in VRAM ($2048 \times 2048 \times 4\text{ bytes}$), and **`22.37 MB` with a full mipmap chain** ($\times 1.33$). A PBR model with four $2048 \times 2048$ maps (baseColor, normal, metallicRoughness, emissive) consumes **`~89.5 MB` of GPU VRAM** from textures alone—enough to crash mobile Safari when combined with framebuffer render targets [khronos.org](https://www.khronos.org/ktx/).

| Optimization Layer | Khronos glTF Extension | Wire Compression Ratio | Decoder Size & CPU Decode Speed | GPU VRAM Footprint ($2048 \times 2048$ w/ Mipmaps) | `gltf-transform` CLI Rule & Trade-Off |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Meshopt Geometry & Animation** | `EXT_meshopt_compression` [github.com](https://github.com/KhronosGroup/glTF/tree/main/extensions/2.0/Vendor/EXT_meshopt_compression) | **`70–85%`** when served over HTTP `br` (Brotli) or `gzip` [gltf-transform.dev](https://gltf-transform.dev/cli) | **`~20–28 KB` WASM**; decodes at **`~500–1,000 MB/s`** (up to **$10\times$ faster than Draco** on mobile CPUs) [meshoptimizer.org](https://meshoptimizer.org/) | Identical to quantized vertex buffers (`50–70%` smaller than Float32 via `KHR_mesh_quantization`) | **Default choice for animated, multi-mesh, or morph-target models** (`gltf-transform meshopt in.glb out.glb --level medium`) [gltf-transform.dev](https://gltf-transform.dev/cli). |

* **Total glTF Wire Budget Rule:** The agent must cap initial above-the-fold `.glb` payload at **`<= 1.5–2.5 MB`** (including decoder WASM) and cap texture dimensions at `1024x1024` for secondary models and `2048x2048` maximum for the primary hero model [gltf-transform.dev](https://gltf-transform.dev/cli).

##### 4.5 Accessibility of `<canvas>` Content
To assistive technologies (VoiceOver, NVDA, JAWS), an unadorned `<canvas>` is a black-box bitmap with zero semantic children [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Hit_regions_and_accessibility). The agent must classify every 3D canvas into one of two patterns:
1. **Purely Decorative Background Canvas:** Set `aria-hidden="true"` and `tabindex="-1"` on `<canvas>` so screen readers and keyboard focus skip it entirely without announcing an unlabeled graphic [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Attributes/aria-hidden).
2. **Informational or Interactive 3D Showcase (e.g., Product Configurator / Annotated 3D Model):** Implement the W3C/MDN **Dual-Tree / Fallback Subtree Pattern** [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Hit_regions_and_accessibility):
   * Provide a descriptive `role="region"` wrapper with `aria-label`, or `role="img" aria-label="..."` on non-interactive illustrative canvases [w3.org](https://www.w3.org/WAI/tutorials/images/complex/).
   * Place semantic HTML controls (`<button>`, `<h3>`, `<p>`, `<dl>`) inside the `<canvas>...</canvas>` fallback subtree or in a synchronized HTML overlay layer so keyboard users (`Tab`, `Enter`, `Space`) can trigger 3D camera hotspots and inspect product callouts, announcing dynamic state changes via an `aria-live="polite"` region [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Hit_regions_and_accessibility).

#### Pillar 5: Static-Site Deployment Visibility & Custom-Domain Setup States

##### 5.1 Unlisted URLs and `noindex` vs. Real Access Control
When an agent deploys a staging or preview build to Vercel or Netlify, it must distinguish **Search Engine Indexing Prevention** from **Access Control**:

| Platform & Environment Context | Default URL Structure | Default `X-Robots-Tag: noindex` Header Injected? | Default Authentication / Access Wall? | Public Exposure Vector if Left Unprotected |
| :--- | :--- | :--- | :--- | :--- |
| **Vercel Preview Deployments** (Git branches / PRs) | `<project>-<hash>-<scope>.vercel.app` [vercel.com](https://vercel.com/docs/deployments/preview-deployments) | **Yes** (`X-Robots-Tag: noindex` injected automatically on all `*.vercel.app` and preview URLs) [vercel.com](https://vercel.com/docs/deployments/preview-deployments#search-engine-indexing) | **Yes, by default on new projects** via **Vercel Deployment Protection** (*Standard Protection* requires Vercel Authentication login for all non-production URLs) [vercel.com](https://vercel.com/docs/security/deployment-protection) | If Deployment Protection is disabled or set to *Only Preview Deployments* while a **Custom Domain** is assigned to a staging branch, the custom staging domain can be publicly reachable unless *All Deployments* or Password Protection is enabled [vercel.com](https://vercel.com/docs/security/deployment-protection). |

* **Why "Unlisted" Subdomains + `noindex` Always Leak:**
  1. **Certificate Transparency (CT) Logs (RFC 6962 / RFC 9162):** Every publicly trusted Certificate Authority (including Let's Encrypt and ZeroSSL, used by Vercel and Netlify) is mandated by browser root programs to publish every issued TLS certificate to public, append-only **Certificate Transparency logs** before the certificate can be trusted by Chrome or Safari [datatracker.ietf.org](https://datatracker.ietf.org/doc/html/rfc9162). Automated scanners, competitors, and search bots continuously tail CT log streams (e.g., via `crt.sh` or Certstream) and discover `staging.client-launch.com` or `preview.newproduct.io` **within seconds of TLS certificate issuance**, even if zero external links exist [letsencrypt.org](https://letsencrypt.org/docs/ct-logs/).
  2. **`noindex` is Voluntary:** `X-Robots-Tag: noindex` and `<meta name="robots" content="noindex">` only instruct compliant search engines (Googlebot, Bingbot) not to list the page in SERPs; they do **not** prevent HTTP access by humans, competitors, archive crawlers, or AI scrapers, and URLs shared in chat apps (Slack, Discord, iMessage, X) trigger automated link-unfurling bots that fetch OpenGraph metadata and hero imagery immediately [developers.google.com](https://developers.google.com/search/docs/crawling-indexing/block-indexing).
* **Mandatory Security Rule:** When deploying a pre-launch, confidential, or embargoed site, the agent must verify that **Edge Authentication** (Vercel Deployment Protection SSO/Password or Netlify Password/OAuth Access Control) is active and returns `HTTP 401 Unauthorized` or an SSO redirect prior to serving any HTML or static media assets [vercel.com](https://vercel.com/docs/security/deployment-protection).

### 2. What is the current state, and what is the strongest supporting evidence for it?

The current state of rich media web engineering in late 2026 is defined by five empirically verified shifts from JavaScript-heavy workarounds to declarative, hardware-accelerated browser primitives and GPU-compressed asset pipelines:

1. **Declarative Responsive Video and LCP First-Frame Accounting:**
   * **Current State:** HTML `<video>` now natively supports responsive source switching via `<source media="...">` across Chrome (120+), Firefox (120+), and Safari, while Chrome's LCP engine (116+) directly penalizes un-postered videos by timing the first decoded video frame [developer.chrome.com](https://developer.chrome.com/docs/web-platform/largest-contentful-paint) [scottjehl.com](https://scottjehl.com/posts/using-responsive-video/).
   * **Strongest Supporting Evidence:** Chromium's Largest Contentful Paint specification update and `web.dev/articles/lcp` confirm that for `<video>` elements, LCP is the minimum of the poster load timestamp and the first frame presentation timestamp [web.dev](https://web.dev/articles/lcp). Scott Jehl's empirical browser verification and MDN's compatibility matrix confirm that `<source media="(max-width: ...)">` and `<source media="(prefers-reduced-motion: reduce)">` were re-implemented and shipped in Firefox 120 and Chrome 120 in late 2023, eliminating the need for JavaScript `window.matchMedia` video source injection [scottjehl.com](https://scottjehl.com/posts/using-responsive-video/) [caniuse.com](https://caniuse.com/mdn-html_elements_source_media).
2. **Baseline Compositor-Driven CSS Scroll Animations:**
   * **Current State:** With the shipment of **Safari 26** (WebKit) and **Firefox 159** joining Chromium 115+, `animation-timeline: scroll()` and `view()` are **Baseline 2026** across all major desktop and mobile browsers [caniuse.com](https://caniuse.com/mdn-css_properties_animation-timeline) [webkit.org](https://webkit.org/blog/).
   * **Strongest Supporting Evidence:** Chrome DevTools performance traces and WebKit compositor architecture documentation demonstrate that CSS scroll-driven animations on `transform` and `opacity` execute on the compositor thread at full display refresh rate (`60–120 Hz`) even when the main JavaScript thread is artificially blocked for `500 ms` by a synchronous loop, whereas main-thread JS scroll listeners freeze completely during main-thread long tasks [developer.chrome.com](https://developer.chrome.com/docs/css-ui/scroll-driven-animations).
3. **VRAM-Compressed 3D Delivery (`KTX2` + `Meshopt`) Over Raw Textures and Draco:**
   * **Current State:** Production WebGL pipelines have standardized on `KHR_texture_basisu` (`KTX2`) and `EXT_meshopt_compression` via `gltf-transform` because mobile Safari fails via GPU VRAM exhaustion (`webglcontextlost` / Jetsam crash) long before network bandwidth saturates [khronos.org](https://www.khronos.org/ktx/) [gltf-transform.dev](https://gltf-transform.dev/cli).
   * **Strongest Supporting Evidence:** Mathematical byte-layout specifications from the Khronos Group prove that a $2048 \times 2048$ PNG/JPEG/WebP texture always inflates to $16.78\text{ MB}$ (`22.37 MB` with mipmaps) in GPU memory, whereas a `KTX2` texture transcoded to `ASTC 4x4` / `BC7` (`UASTC`, 8 bpp) occupies exactly $5.59\text{ MB}$ with mipmaps (**75% VRAM reduction**) and `ETC2` / `BC1` (`ETC1S`, 4 bpp) occupies $2.80\text{ MB}$ (**87.5% VRAM reduction**) [khronos.org](https://www.khronos.org/ktx/). Benchmarks by Arseny Kapoulkin (`meshoptimizer`) and Don McCurdy (`glTF-Transform`) show `EXT_meshopt_compression` decodes up to **$10\times$ faster** than Draco with a decoder footprint under `30 KB` vs. Draco's `~110–150 KB` [meshoptimizer.org](https://meshoptimizer.org/) [gltf-transform.dev](https://gltf-transform.dev/cli).
4. **Keyframe-Conditioned Generative Video and Multi-Dimensional Temporal QA:**
   * **Current State:** Commercial generative video APIs (Veo 2/3.1, Kling 2.0/3.0, Runway Gen-3/Gen-4, Luma Ray 2) have converged on explicit First-Frame and Last-Frame image conditioning as the primary control mechanism for web loops and multi-shot chains [cloud.google.com](https://cloud.google.com/vertex-ai/generative-ai/docs/video/generate-videos). Simultaneously, academic benchmarks (**VBench**, CVPR 2024; **EvalCrafter**) established that single scalar scores or sparse VLM keyframe checks fail to detect high-frequency temporal flickering and motion smoothness anomalies [arxiv.org](https://arxiv.org/abs/2311.17982) [arxiv.org](https://arxiv.org/abs/2310.11440).
   * **Strongest Supporting Evidence:** VBench's disentangled evaluation suite demonstrates that models scoring highly on per-frame aesthetic quality and subject consistency frequently exhibit poor **Temporal Flickering** scores when measured via dense adjacent-frame ($t, t+1$) pixel and optical-flow consistency [arxiv.org](https://arxiv.org/abs/2311.17982).
5. **Zero-Trust Preview Deployment Defaults:**
   * **Current State:** Modern cloud static hosts (Vercel Deployment Protection, Netlify Access Control) distinguish between crawler directives (`X-Robots-Tag: noindex`) and authentication walls because Certificate Transparency (RFC 9162) exposes every custom subdomain immediately upon TLS issuance [vercel.com](https://vercel.com/docs/security/deployment-protection) [datatracker.ietf.org](https://datatracker.ietf.org/doc/html/rfc9162).

### 3. What are the contrasting viewpoints or competing evidence?

Across these five domains, practicing engineers and benchmark authors debate four material trade-offs where competing evidence exists:

1. **`<CONFLICTING_EVIDENCE>`AV1-First Video Encoding vs. Battery/Hardware Decode Fallback on Apple Silicon:`</CONFLICTING_EVIDENCE>`**
   * **Position A (AV1-First Everywhere):** Web performance advocates argue that AV1 (`libsvtav1 -crf 32`) should always be the top `<source>` in `<video>` because it cuts file size by `30–50%` compared to H.264 and `~20%` compared to VP9, and Chrome/Firefox bundle the highly optimized `dav1d` software decoder for devices lacking hardware AV1 silicon [trac.ffmpeg.org](https://trac.ffmpeg.org/wiki/Encode/AV1).
   * **Position B (HEVC/VP9 + H.264 Two-Tier Ladder):** Media engineers point out that Apple WebKit explicitly refuses to software-decode AV1 to protect mobile battery life, restricting Safari AV1 support strictly to M3/M4+ Macs and A17 Pro/A18+ iPhones/iPads [webkit.org](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/) [caniuse.com](https://caniuse.com/av1). On older Android devices running Chrome, `dav1d` software decoding of a `1080p` AV1 hero video on the CPU can contend with main-thread JavaScript hydration and WebGL initialization during initial page load.
   * **Synthesis Rule for Agent:** Serve AV1 as the primary `<source>`, but cap mobile `<source media="(max-width: 767px)">` resolution strictly at **`720p` (`1280x720`)** so software AV1 decoders on mid-tier Android devices never decode 1080p on the CPU, and always provide `VP9` and `H.264 (+faststart)` fallbacks for M1/M2 Macs and pre-A17 iPhones [caniuse.com](https://caniuse.com/av1).

2. **`<CONFLICTING_EVIDENCE>`Pure CSS Scroll-Driven Animations vs. GSAP `ScrollTrigger` in Complex Scrollytelling:`</CONFLICTING_EVIDENCE>`**
   * **Position A (CSS-Only Native Timelines):** Chromium and WebKit performance teams advocate replacing JS scroll libraries with CSS `animation-timeline: scroll()` and `view()` to guarantee `0 ms` main-thread cost and zero INP interference [developer.chrome.com](https://developer.chrome.com/docs/css-ui/scroll-driven-animations).
   * **Position B (Hybrid GSAP Orchestration):** Creative technologists and agency engineers argue that CSS `view-timeline` cannot directly scrub WebGL shader uniforms, Three.js camera splines, or `<canvas>` 2D frame sequences, and that coordinating multi-element sequential pinning with dynamic viewport recalculations in pure CSS requires fragile magic-number wrapper heights (`height: 400vh`) compared to GSAP `ScrollTrigger`'s automatic pin-spacer math [gsap.com](https://gsap.com/docs/v3/Plugins/ScrollTrigger/).
   * **Synthesis Rule for Agent:** Enforce a strict architectural split: **100% of DOM/CSS property animations (`transform`, `opacity`, `clip-path`) must use native CSS `animation-timeline`**, while GSAP `ScrollTrigger` (or a single passive `requestAnimationFrame` scroll progress reader) is loaded **only** when a section scrubs a `<canvas>` / WebGL scene.

3. **`<CONFLICTING_EVIDENCE>`Draco (`KHR_draco_mesh_compression`) vs. Meshopt (`EXT_meshopt_compression`) for glTF Delivery:`</CONFLICTING_EVIDENCE>`**
   * **Position A (Draco for Minimum Bytes on Disk):** Google's Draco achieves `10–20%` smaller raw `.glb` file sizes on dense static triangle meshes via Edgebreaker connectivity encoding [google.github.io](https://google.github.io/draco/).
   * **Position B (Meshopt for Faster Time-to-First-Frame):** Don McCurdy (`glTF-Transform`) and Arseny Kapoulkin (`meshoptimizer`) demonstrate that once HTTP Brotli/Gzip compression is applied by the CDN, Meshopt's transfer size approaches Draco's while its WASM decoder is `~4x` smaller (`<30 KB` vs `~120 KB`), decodes up to `$10\times$ faster` on mobile CPUs, and compresses animation keyframes and morph targets that Draco leaves completely uncompressed [gltf-transform.dev](https://gltf-transform.dev/cli) [meshoptimizer.org](https://meshoptimizer.org/).
   * **Synthesis Rule for Agent:** Default to **`EXT_meshopt_compression`** (`gltf-transform meshopt`) whenever the host CDN serves `.glb` files with Brotli/Gzip or when the model contains animations/morph targets; use Draco only for static, high-polygon (`>100k` triangle) meshes on hosts that do not apply HTTP compression to binary `.glb` MIME types [gltf-transform.dev](https://gltf-transform.dev/cli).

4. **`<CONFLICTING_EVIDENCE>`Seamless Looping via First/Last-Frame Conditioning vs. Post-Production Crossfade (`xfade`):`</CONFLICTING_EVIDENCE>`**
   * **Position A (Model-Native First=Last Conditioning):** Passing `first_frame == last_frame` to Veo 3.1, Kling, or Runway forces the model's trajectory to return objects to their exact starting pose without ghosting [cloud.google.com](https://cloud.google.com/vertex-ai/generative-ai/docs/video/generate-videos).
   * **Position B (FFmpeg Tail-to-Head `xfade`):** On stochastic ambient scenes (clouds drifting, water flowing, crowds, particle fields), forcing `first_frame == last_frame` inside a short `5 s` window often causes unnatural "snap-back" acceleration in the final `1.5 seconds` as the diffusion model rushes displaced features back to their initial coordinates; a unidirectional `8 s` generation with a `0.5–0.8 s` FFmpeg tail-to-head `xfade` yields more natural constant-velocity motion on textures [ffmpeg.org](https://ffmpeg.org/ffmpeg-filters.html#xfade).
   * **Synthesis Rule for Agent:** Use **`first_frame == last_frame` conditioning** (plus terminal duplicate frame drop) for **discrete object/character/camera loops**, and use **unidirectional I2V + FFmpeg tail-to-head `xfade`** for **continuous stochastic flows** (water, clouds, smoke, abstract particles).

### 4. What changed recently, and what is the trajectory?

Between **January 2024 and November 2026**, six major changes altered how an autonomous web-building agent must architect rich websites:

1. **CSS Scroll-Driven Animations Crossed into Universal Baseline (2025–2026):** For years, CSS `animation-timeline: scroll()` and `view()` were Chromium-only (Chrome 115+), forcing production sites to ship GSAP ScrollTrigger or polyfills for Safari and Firefox users. With **Safari 26** (macOS/iOS) and **Firefox 159** shipping full unflagged support, native compositor-thread scroll animations are now Baseline 2026 [caniuse.com](https://caniuse.com/mdn-css_properties_animation-timeline).
2. **Interaction to Next Paint (INP) Replaced First Input Delay (FID) as a Core Web Vital (March 2024):** Google officially promoted **INP (`<= 200 ms`)** to replace FID in March 2024 [web.dev](https://web.dev/blog/inp-cwv-march-12). Because INP measures the worst-case (98th percentile) interaction latency across the **entire page lifecycle**—not just initial load—main-thread JavaScript scroll listeners and unthrottled WebGL/GSAP callbacks that previously passed FID now directly fail Core Web Vitals when a user clicks a navigation button mid-scroll [web.dev](https://web.dev/articles/inp).
3. **`<video><source media="...">` Reached 100% Browser Engine Parity (Late 2023 – 2026):** Following its restoration in Firefox 120 and Chrome 120, declarative viewport- and motion-preference-based video switching is now universally reliable without JavaScript [scottjehl.com](https://scottjehl.com/posts/using-responsive-video/).
4. **First-and-Last-Frame Keyframe Conditioning Became Standard Across Video Generation APIs (2024–2026):** Frontier video models transitioned from unconditioned Text-to-Video clips to controllable **Frames-to-Video** pipelines (Google Veo 2 / Veo 3.1, Kling 1.6/2.0/3.0, Runway Gen-3 Alpha/Gen-4, Luma Ray 2), enabling exact poster-to-video continuity and deterministic loop closure [cloud.google.com](https://cloud.google.com/vertex-ai/generative-ai/docs/video/generate-videos).
5. **Safari AV1 Hardware-Only Decode Rollout Expanding with Apple Silicon Generations (2023–2026):** As M3, M4, M5 Macs and A17 Pro, A18, A19 iPhones replace older Apple devices, hardware AV1 decoding in Safari has grown from a niche capability in late 2023 to a majority of active Apple devices in late 2026—while still requiring a VP9/H.264 fallback for the remaining installed base of M1/M2 Macs and pre-A17 iPhones [caniuse.com](https://caniuse.com/av1).
6. **Trajectory Toward WebGPU (`THREE.WebGPURenderer`) and 3D Gaussian Splatting (2026+):** While **WebGL 2** remains the universal baseline for marketing sites in late 2026, Three.js's `WebGPURenderer` (with automatic WebGL 2 fallback) and Node Material (`TSL`) system are increasingly used for compute-shader particle systems and compressed 3D Gaussian Splatting (`.splat` / `.ksplat` / `SPZ`) hero scenes, following the same VRAM and `IntersectionObserver` lifecycle constraints established for WebGL 2 [threejs.org](https://threejs.org/docs/).
