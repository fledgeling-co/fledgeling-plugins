## Codex Computer Use on macOS: Capabilities and Design Choices

### Service-oriented architecture and capability surfaces

Codex’s choice to ship a separate, sandboxed “computer use” service under `~/.codex/` rather than an in‑place module inside the Electron host is aligned with Apple’s guidance on using helper processes and plug‑ins to extend authorization and automation services.[2] Apple’s Authorization Plug-ins documentation explains that plug‑ins are separate bundles that participate in authorization decisions and can modify the system’s authorization policy with custom code, specifying an `AuthorizationPluginInterface` version that the authorization engine uses to call into them.[2] That model maps closely onto the observed `CodexComputerUseAuthorizationPlugin.bundle`, which is installed at `/Library/Security/SecurityAgentPlugins` and registered against specific authorization mechanisms such as `system.login.screensaver`.[1][2][3] The helper-service pattern also matches how macOS typically structures assistive technologies: the AXUIElement API, defined by `AXUIElement.h`, is designed for “assistive applications” that run as separate processes and communicate with accessible applications via an IPC-like mechanism mediated by the accessibility server.[12]

By statically importing AXUIElement’s full read/write surface, the Codex computer use service can inspect the accessibility tree of all UI elements on the system, and perform actions such as pressing buttons or setting text fields, without needing to synthesize lower-level input events.<INFERENCE from="[AXUIElement.h description of controlling accessible applications[12]]">[12] Apple’s documentation emphasizes that AXUIElement is intended to allow assistive apps to “communicate with and control accessible applications,” which includes reading attributes (titles, positions, roles) and performing accessibility actions (press, increment, showMenu, etc.).[12] This is reinforced by platform behaviour: for example, changing sliders or invoking menu items via accessibility does not require them to be frontmost in the same way as synthetic events often do.<INFERENCE from="[AXUIElement.h semantics[12]]">[12] Coupled with ScreenCaptureKit—which Apple has promoted in recent macOS releases as the preferred way to programmatically capture high‑resolution, high‑performance screen content via `SCStream` and associated filters—this allows Codex to maintain a visual representation of the desktop while using accessibility actions to manipulate application state.<CONFIDENCE:MEDIUM>[INFERENCE from="[Apple’s ScreenCaptureKit descriptions in WWDC sessions (not present in current search results), AXUIElement.h[12]]"] 

The absence of synthetic event APIs is also meaningful. ### Lock-screen participation via SecurityAgent authorization plug‑in

Apple’s Authorization Plug-ins documentation describes how plug‑ins can extend authorization services by implementing callbacks that participate in authorization decisions and UI flows.[2] Each plug‑in can declare the mechanisms it handles, such as `system.login.console` for loginwindow authentication, or `system.login.screensaver` for screensaver unlock.[1][2] The documentation notes that plug‑ins can implement both policy decisions and custom UI, and that they are loaded by SecurityAgent when the corresponding mechanism is invoked.[2] Developer forum threads under the “Security Interface” tag confirm that authorization plug‑ins apply to mechanisms like `system.login.console` and `system.login.screensaver`, providing hooks for login window and screensaver authentication.[1] Third‑party administrators routinely modify the `system.login.screensaver` rule in the authorization database to constrain who can unlock a screen; for example, Jamf community posts show the use of `security authorizationdb write system.login.screensaver authenticate-session-user` to ensure only the logged-in user can unlock, or `authenticate-admin-or-owner` to require admin or session owner privileges.[10] Another Apple Community thread documents changing the `system.login.screensaver` rule from `use-login-window-ui` to `authenticate-session-owner-or-admin` to display a custom authentication plug‑in view when the screensaver starts or the screen locks.[3]

## SecurityAgent Authorization Plug-ins as an Agent Capability (Subtopic 1)

### What authorization mechanism plug‑ins can legitimately do

Apple’s Authorization Plug-ins documentation explains that authorization plug‑ins extend the authorization services API by allowing custom code to participate in authorization decisions.[2] Plug‑ins implement a well-defined interface consisting of callbacks such as `Authorize`, `Deauthorize`, and `MechanismInvoke`, and are loaded by SecurityAgent—the system component responsible for managing authentication and authorization UI—when a corresponding authorization mechanism is triggered.[2] Each mechanism corresponds to a policy entry in the authorization database; examples include `system.login.console` for loginwindow authentication and `system.login.screensaver` for screensaver unlock.[1][2] Within the context of SecurityAgent and loginwindow, a plug‑in can legitimately perform tasks such as prompting the user for credentials, validating those credentials against local or remote identity providers, enforcing additional factors (Touch ID, smart cards), and logging audit information.[2][4]

In macOS 26/27, authorization plug‑ins operate under strict constraints: they run as root or under the SecurityAgent’s privileges, but are subject to the system’s hardened runtime and SIP protections, meaning they cannot arbitrarily disable system security features or modify protected locations outside of their prescribed interface.[2] They can, however, initiate network connections, interact with hardware (for example smart cards), and call into other system frameworks as long as those capabilities are permitted by the host process and its entitlements.[4] Platform SSO is an example of a first‑party system that uses a form of authorization extension to integrate organizational identity into macOS login, lock-screen, and FileVault flows.[4] Apple’s Platform SSO documentation describes how an SSO extension compatible with an identity provider (IdP) can be deployed to provide a seamless login and authentication experience, allowing the user to use their organizational identity throughout macOS starting with initial setup.[4] The SSO extension participates in prompts such as FileVault unlock, lock-screen, and login window, and supports authentication methods including passwords, Secure Enclave-backed keys, web-based flows, smart cards, and access keys.[4] This demonstrates Apple’s intended pattern: authorization-related plug‑ins are a legitimate way to integrate external identity and policy into SecurityAgent’s flows for critical prompts.

### How rewriting `system.login.screensaver` changes the unlock path

The authorization database in macOS is a policy store that maps mechanisms like `system.login.screensaver` to a list of required rules or plug‑ins.[2] Tools such as the `security authorizationdb` command can read and write these entries, altering which mechanisms are invoked for a given action.[10] For example, administrators can run `security authorizationdb write system.login.screensaver authenticate-session-user` to change the rule so that only the session user may unlock their screen, or `authenticate-admin-or-owner` to also allow admins.[10] The default configuration typically uses `authenticate-session-owner-or-admin` with `use-login-window-ui`, which means the standard loginwindow UI appears and credentials are verified against local users or directory services.[3][10] When Codex rewrites this rule to `["com.openai.sky.CUAService.AuthorizationPlugin.remote", "use-login-window-ui"]`, it is effectively adding a custom mechanism that runs before the usual login window UI.

In practice, when the screensaver activates or the user locks the screen, SecurityAgent looks up the `system.login.screensaver` rule and invokes each listed mechanism. For `com.openai.sky.CUAService.AuthorizationPlugin.remote`, SecurityAgent loads Codex’s authorization plug‑in bundle and calls into its entry points, allowing it to intercept the lock-screen event, display overlays, or interact with the accessibility tree of the lock-screen UI via classes like `SystemLockScreenAXInteractor`.[2][3] Depending on how the plug‑in is implemented, it can choose to authorize the unlock (for example by obtaining credentials from a remote agent) or defer to `use-login-window-ui` to display the usual credential prompt. This provides a hook for remote or agent-driven unlock operations, as long as the plug‑in ultimately satisfies SecurityAgent’s expectations for authorization outcomes.<CONFIDENCE:HIGH><INFERENCE from="[Authorization Plug-ins documentation[2], examples of system.login.screensaver rule modification[3][10]]">[2][3][10]

### Security and fleet-management consequences; controls and reversion

From a fleet-management standpoint, the insertion of a third-party plug‑in into `system.login.screensaver` has several consequences. First, it alters a core security path—the unlock of a locked session—and does so in a way that is not visible in standard UI or TCC prompts, since authorization plug‑ins are not themselves gated by per-app consent in the same way as screen recording or Apple Events.[2][6][7] Second, because the plug‑in runs inside SecurityAgent with elevated privileges, any flaws in its implementation (for example insecure use of a world‑writable socket) may create new local privilege escalation or credential exfiltration surfaces.<CONFIDENCE:MEDIUM><INFERENCE from="[Authorization Plug-ins running under SecurityAgent[2], Unix socket world-write implications]">[2]

The available controls are fragmentary. MDMs can enforce certain lock-screen policies, such as requiring a password on screensaver unlock and configuring timeouts, but these do not directly control which authorization mechanisms are used.[7] Platform SSO’s login policy configuration allows admins to require IdP authentication at lock-screen prompts, but does not expose direct management of authorizationdb entries in Apple’s documented UI.[4] Some enterprise tools, such as Intune, can manage Apple Events automation by specifying which apps or processes are allowed to receive restricted Apple Events, and whether access is allowed or blocked.[11] Intune’s device restriction settings for macOS include “Apple events,” where admins can add receiving apps or processes by bundle ID or path and set access to Allow or Block.[11] This can constrain the Apple Events control plane used by Codex, but not its accessibility-based control or authorization plug‑in behaviour. TCC’s system-wide database for permissions like `kTCCServiceAppleEvents` is SIP-protected and not modifiable without SIP bypass, but per-user TCC records can be updated by configuration profiles or per-user actions.[6] This means admins can potentially pre-deny automation permissions for Codex or similar agents, but only if they know to do so.

As for removal and reversion, Apple’s documentation does not state that uninstalling a plug‑in automatically reverts authorizationdb rules.[2] The Jamf Community posts imply that authorizationdb entries are persistent system state that must be explicitly modified to change behaviour.[10] Therefore, removing the Codex app or its plug‑in bundle is unlikely to revert the `system.login.screensaver` rule; instead, the rule will continue to reference a mechanism that no longer exists, which may lead to errors or fallback behaviour, but not a clean restoration of the default. Administrators would need to run `security authorizationdb write system.login.screensaver` with the desired default rule to fully undo the modification.<CONFIDENCE:LOW><INFERENCE from="[behaviour of authorizationdb commands[10], lack of documentation about automatic reversion[2]]">[10][2]

In summary, SecurityAgent authorization plug‑ins are powerful, legitimate integration points for identity and policy systems in macOS 26/27, and Codex’s use of them is structurally consistent with Apple’s design. However, the combination of a remote/socket-brokered mechanism, accessibility-driven lock-screen interaction, and dynamic scripting orchestration raises security questions that are not fully answered by existing MDM and TCC controls, and removal of such plug‑ins requires explicit policy changes rather than simple app deletion.

## Session-State Capability Matrix on macOS 26/27 (Subtopic 3)

### Relevant session states and control/observation planes

For an agentic UI-testing toolchain, it is critical to understand how different session states affect the functionality of key macOS automation APIs. The relevant states for this analysis include:

1. Display-asleep (screen powered down, but session active).
2. Screensaver-active (screen showing screensaver, but session still nominally logged in).
3. Session-locked (lock-screen UI active; user must authenticate).
4. Fast-user-switched-away (another user’s session is in the foreground; the original session remains in background).
5. No-display/headless (virtual display or remote session without physical monitor).
6. Window-occluded (window covered by other windows).
7. Window-minimized.
8. Window-on-another-Space (virtual desktop).

The automation planes considered are: AX attribute reads and actions (AXUIElement), AXObserver notification delivery, Apple Events, ScreenCaptureKit streams (display-scoped and window-scoped), `CGWindowListCreateImage` (snapshot capture), and synthetic events (`CGEventPost`), even though Codex does not use the latter.

### Behaviour in session-locked and fast-user-switched-away states

When the session is locked, the lock-screen UI (managed by SecurityAgent/loginwindow) is active, and the user must authenticate to regain access. Fast user switching complicates matters: when user A fast-switches to user B, user A’s session remains in memory but is no longer the active console. ## Control Planes: Process-directed Actuation vs Event-stream Injection (Subtopic 4)

### Accessibility and Apple Events as process-directed actuation

Process-directed actuation manipulates application state directly, rather than synthesizing low-level input events. AXUIElement is the canonical interface for this on macOS: Apple’s AXUIElement.h documentation states that “assistive applications use the functions defined in this header file to communicate with and control accessible applications running in macOS.”[12] Functions such as `AXUIElementCreateApplication` create references to application-level accessibility elements, and `AXUIElementSetAttributeValue` and `AXUIElementPerformAction` allow changing attributes and invoking actions on these elements.[12] Because accessibility elements are typically tied to semantic UI components (buttons, sliders, text fields), this approach allows agents to “press” buttons or “set” text fields without sending keypress or mouse-click events. Accessibility actions are often implemented by toolkits such as AppKit, SwiftUI, and UIKit (via Mac Catalyst), and in many cases they bypass standard focus rules, permitting actions on non-frontmost windows when toolkits honour them.<CONFIDENCE:MEDIUM><INFERENCE from="[AXUIElement.h semantics[12], general toolkit behaviour]">[12]

Apple Events represent another process-directed plane. The Apple Events Entitlement documentation describes the entitlement `com.apple.security.automation.apple-events` as a Boolean value indicating whether the app may prompt the user for permission to send Apple events to other apps.[5] Once approved via TCC, this entitlement allows the app to script other applications using AppleScript or raw Apple Events, invoking operations such as opening documents, saving files, or running commands.[5][6] HackTricks’ TCC documentation notes that `kTCCServiceAppleEvents` is the TCC service name for automation via Apple Events, and that permissions in the TCC database specify which app is allowed to manage which other app.[6] This is powerful because many core macOS apps—Finder, Automator, Mail—have rich AppleScript dictionaries (sdef files) exposing high-level automation verbs; for example, Finder can copy, move, and delete files, and Automator can run workflows that themselves automate other applications.<CONFIDENCE:HIGH><INFERENCE from="[TCC Apple Events documentation[6], AppleScript practices]">[6]

### Synthetic event injection via CGEventPost

Synthetic event injection uses APIs such as `CGEventCreateKeyboardEvent`, `CGEventCreateMouseEvent`, and `CGEventPost` to insert events into the Quartz event stream, mimicking user input. While these APIs are documented, they are increasingly constrained by system policies. Apple’s security model has evolved over recent macOS releases to treat synthetic event posting as a privileged operation gated by accessibility permissions (for example, “Allow the app to control your computer”) and features such as Secure Input.<CONFIDENCE:MEDIUM><INFERENCE from="[general macOS security evolution, App Nap and TCC documentation[6][18]]">[6][18] CGEventPost posts events into the global event stream, targeting whichever process currently has keyboard focus; CGEventPostToPid allows targeting a specific process, but focus rules and SecureEventInput can still interfere.<CONFIDENCE:MEDIUM><INFERENCE from="[Quartz event model]"> EnableSecureEventInput (invoked by system components when entering password fields) instructs the system to route keyboard input exclusively to secure fields and to block event taps and possibly synthetic events; this is documented at a high level in Apple’s platform security materials but not in the current search results.<MISSING_DATA>[Detailed documentation of EnableSecureEventInput behaviour; would require Apple Platform Security guide references.]

From the perspective of an agent, synthetic events are useful when toolkits do not fully expose accessibility actions for certain controls, or when the agent must interact with third-party apps that have poor accessibility support. However, because synthetic events are subject to focus, lock-screen restrictions, and system protections, they are less reliable and less secure than process-directed actuation, and are generally disfavoured in security-conscious environments.<CONFIDENCE:MEDIUM><INFERENCE from="[macOS security best practices, TCC and accessibility prompts[6]]">[6]

### Toolkit behaviour on AX actions for non-frontmost windows

Apple’s AXUIElement documentation makes no guarantees about whether actions can be performed on non-frontmost windows; it only states that assistive applications can control accessible applications.[12] Behaviour depends on toolkit implementation. AppKit controls, such as NSButton and NSSlider, often implement accessibility actions in a way that does not strictly require the window to be key; an AXPress on a button may trigger its target action even if the window is in the background, though some applications explicitly guard against this to avoid unexpected behaviour.<CONFIDENCE:LOW><INFERENCE from="[empirical behaviour, lack of formal guarantees]"> SwiftUI’s accessibility is built on AppKit/UIKit and may behave similarly. Mac Catalyst apps, being UIKit-based, typically require the view to be in a visible window, but accessibility actions may still operate on background windows if the accessibility hierarchy is active.<CONFIDENCE:LOW><INFERENCE from="[UIKit accessibility semantics]"> Electron/Chromium-based apps expose accessibility trees derived from the browser’s DOM; AX actions such as press and increment may simulate DOM events without strictly requiring window focus, though Chromium’s own occlusion handling can throttle rendering for occluded windows.[17]<CONFIDENCE:LOW><INFERENCE from="[Chromium occlusion documentation[17]]">[17] Qt and Java Swing/SWT have varying accessibility support, and their behaviour for AX actions on non-frontmost windows is inconsistent.

The key point is that process-directed actuation via AXUIElement does not inherently require foregrounding windows; when toolkits implement accessibility actions as direct state mutations or event dispatches, an agent can operate on background windows without moving them to the front. This is precisely the capability that Codex appears to rely on: it uses AXUIElementPerformAction and AXUIElementSetAttributeValue rather than synthetic events, allowing it to operate on background windows and lock-screen UI even when they are not the active focus owners.<CONFIDENCE:MEDIUM><INFERENCE from="[AXUIElement.h design[12], Codex absence of synthetic event imports]">[12]

### Keyboard focus singleton and Escape of CGEventPostToPid

Keyboard focus on macOS is effectively a singleton per WindowServer instance: at any given time, one application and one window are designated as focused for key events, and events are routed accordingly.<CONFIDENCE:HIGH><INFERENCE from="[WindowServer design principles]"> CGEventPost sends events into this global stream, so it cannot bypass focus. CGEventPostToPid appears to suggest process-directed posting, but in practice the event is still subject to system focus rules and may be discarded or misrouted if the target process does not own a visible window or if SecureEventInput is enabled.<CONFIDENCE:LOW><INFERENCE from="[general behaviour, lack of detailed documentation]"> In contrast, AXUIElement does not depend on keyboard focus; it operates on accessibility elements directly. This distinction is critical: Codex’s avoidance of CGEventPost means it is not attempting to circumvent focus—it is instead operating entirely within the process-directed plane where focus is less constraining.<CONFIDENCE:MEDIUM><INFERENCE from="[absence of synthetic event APIs in SkyComputerUseService, AXUIElement.h semantics[12]]">[12]

### Effect of EnableSecureEventInput on each plane

EnableSecureEventInput is invoked by system components such as loginwindow or password fields to protect sensitive input. When enabled, event taps and keyloggers are prevented from observing keyboard events, and some synthetic event injection may be blocked.<CONFIDENCE:MEDIUM><INFERENCE from="[Apple Platform Security overview, general understanding of Secure Input]"> Accessibility actions and Apple Events automation are typically not blocked by SecureEventInput, because they operate at a different level; they may still be constrained by lock-screen state and TCC permissions, but they are not part of the raw keyboard pipeline. This means that SecureEventInput is primarily a defense against CGEvent-based keyloggers and synthetic input, not against process-directed automation via accessibility or Apple Events.<CONFIDENCE:LOW><INFERENCE from="[general model, lack of explicit documentation]"> For an agent like Codex, this is advantageous: by avoiding synthetic events, it operates in a plane where SecureEventInput does not directly interfere.

## Background and Occluded Window Capture: Live vs Stale Pixels (Subtopic 5)

### NSWindowOcclusionState, App Nap, and Core Animation suspension

Apple introduces App Nap as a mechanism to reduce power and CPU usage by suspending or throttling apps that are not actively in use (for example, when their windows are fully hidden or minimized).[18] The HackTricks TCC documentation notes that TCC controls access to sensitive services like location, contacts, photos, microphone, camera, accessibility, and full disk access, but does not directly address App Nap.[6] A developer discussion on NSProcessInfoActivity explains that developers can disable App Nap for an app that needs to be ready to receive commands in the background by creating an NSProcessInfoActivity and indicating that they are performing a user-initiated activity.[18] In that thread, the developer notes that they added code to disable App Nap for an app that receives commands in the background, and asks whether NSProcessInfoActivity behaviour has changed in macOS High Sierra.[18] This implies that NSProcessInfoActivity remains a supported way to keep an app awake and responsive even when not visible.

AppKit’s NSWindow occlusion APIs, while not present in the current search results, allow an app to query whether its windows are visible or occluded, and the system uses occlusion state to inform App Nap decisions. When a window is fully occluded and the app is not performing a significant activity, App Nap may suspend the app’s rendering, causing its Core Animation layer tree to stop updating and its backing store to become stale.<CONFIDENCE:MEDIUM><INFERENCE from="[App Nap and NSProcessInfoActivity discussion[18]]">[18] Similarly, minimized windows may have their backing stores purged, meaning that snapshots captured via `CGWindowListCreateImage` or ScreenCaptureKit could show the last-rendered frame rather than live pixels.<CONFIDENCE:LOW><INFERENCE from="[general macOS behaviour, Chromium occlusion documentation[17]]">[17]

### WindowServer backing-store purge and offscreen surfaces

WindowServer manages backing stores for windows and compositing them onto displays. When memory pressure is high or windows are occluded or minimized, WindowServer can discard backing stores and re-render content on demand when the window becomes visible again.<CONFIDENCE:MEDIUM><INFERENCE from="[general WindowServer design]"> On platforms like Windows, Chromium’s occlusion tracking explicitly stops rendering for occluded windows and treats them as background tabs, stopping rendering and throttling JavaScript.[17] It also notes that when the screen is locked, all Chromium windows are considered occluded.[17] Although Apple has not published equivalent documentation, similar patterns likely apply on macOS: windows that are minimized or moved to another Space may be treated as occluded for rendering and backing store retention.

For ScreenCaptureKit, Apple has indicated in WWDC sessions that window-scoped capture operates by tapping into WindowServer’s render path for specific windows rather than capturing from the final display composite.<CONFIDENCE:MEDIUM><INFERENCE from="[ScreenCaptureKit WWDC descriptions (not in current search results)]"> If a window’s backing store is stale or purged, ScreenCaptureKit may capture a stale frame until the app resumes rendering. `CGWindowListCreateImage` similarly returns the backing-store content; if the store is stale, the image is stale.

### Supported ways to keep non-visible windows rendering

NSProcessInfoActivity provides a documented way to prevent App Nap and keep an app active even when its windows are occluded or minimized.[18] Developers can create an NSProcessInfoActivity with options such as `NSActivityUserInitiated` or `NSActivityLatencyCritical` to signal that the app is performing important work, and the system will avoid napping it.[18] In the developer discussion, this approach was used to ensure that an app remains ready to receive commands in the background.[18] Additionally, certain apps (like Finder) always have full disk access and may have special treatment in terms of App Nap, as HackTricks notes that Finder always has full disk access and can be controlled via Apple Events.[6] For agent-driven UI testing, developers can embed NSProcessInfoActivity into the test target or supporting helper apps to keep them rendering even when not visible.<CONFIDENCE:HIGH><INFERENCE from="[NSProcessInfoActivity discussion[18]]">[18]

Another strategy is to periodically invalidate views or trigger animations, which can keep the rendering pipeline active. However, this may be throttled or suspended by App Nap if the app is deemed inactive. In high-performance contexts, apps can opt out of App Nap entirely via Info.plist keys, but Apple discourages this for power reasons.<CONFIDENCE:LOW><INFERENCE from="[general App Nap documentation]"> An agent that relies on ScreenCaptureKit must be mindful of these factors; for test harnesses, running the target in a virtual display or VM where the window is considered visible may be more robust.

### Detecting stale frames in-band

Detecting whether a captured frame is stale is challenging. ScreenCaptureKit can provide frame metadata such as timestamps and dirty rects, indicating which portions of the frame have changed since the last capture.<CONFIDENCE:LOW><INFERENCE from="[ScreenCaptureKit design]"> An agent can monitor these timestamps and dirty rects; if they stop changing while the agent expects activity, it may infer that rendering has been suspended.<CONFIDENCE:LOW><INFERENCE from="[general principles]"> Similarly, AXObserver notifications about value changes or layout modifications can be combined with capture data; if accessibility state changes but pixels do not, the agent may detect a discrepancy and treat the frame as stale.<CONFIDENCE:LOW><INFERENCE from="[AXObserver semantics[12]]"> Another heuristic is to hash captured frames and monitor for identical hashes over time; repeated identical hashes despite expected activity may indicate stale content.<CONFIDENCE:LOW><INFERENCE from="[state hashing principles]">

However, none of these heuristics are foolproof, and Apple does not provide a direct API to query “is this window actively rendering into its backing store.”<MISSING_DATA>[API for querying rendering status of windows; would require platform documentation.] For deterministic UI testing, running apps in VMs or virtual displays where occlusion and App Nap are minimized, and keeping App Nap disabled via NSProcessInfoActivity or Info.plist settings, appears to be the most reliable approach.<CONFIDENCE:MEDIUM><INFERENCE from="[NSProcessInfoActivity discussion[18], virtualization capabilities[14][15]]">[18][14][15]

## Native Equivalents of getComputedStyle on macOS (Subtopic 6)

### Core Animation layer and presentation trees

In web automation, `getComputedStyle` provides a snapshot of the final computed values for CSS properties at a given moment. On macOS, there is no direct analogue, but Core Animation’s layer tree and presentation layer provide something similar: a snapshot of visual properties (frames, transforms, colors) as they are currently rendered. The Core Animation tutorial video for macOS development explains how to convert drawing code to use layers, disable default animations with `CATransaction`, and create custom animations via `CABasicAnimation` that animate properties such as background color over time.[19] The tutorial emphasizes that Core Animation’s presentation layer reflects current animated values, whereas the model layer holds target values, and that developers can inspect and manipulate these layers programmatically.[19]

For an agent controlling its own app, it is straightforward to inspect the Core Animation layer tree; the app can provide an API to dump layer properties, effectively yielding a “computed style” snapshot for its UI. However, inspecting Core Animation layers of third-party apps is not supported by public APIs. Hardened runtime and SIP prevent injecting code or attaching to processes with arbitrary debugging privileges unless the app is properly signed, notarized, and configured for debugging.<CONFIDENCE:HIGH><INFERENCE from="[Apple Platform Security, notarization and hardened runtime practices]"> Thus, Core Animation layers are a viable computed-style source only for the agent’s own app or cooperatively instrumented apps.

### Xcode’s View Debugger transport

Xcode’s View Debugger allows developers to pause their app and view a 3D representation of the UI hierarchy, including views and constraints. It uses debugging transports such as DTX (Debugging Transport) and LLDB injection to communicate with the running app, load specialized libraries (like libViewDebuggerSupport), and extract view information.<CONFIDENCE:HIGH><INFERENCE from="[Xcode View Debugger behaviour, general LLDB/DTX design]"> This infrastructure is tightly integrated with Xcode and requires the target app to be launched under Xcode or to have debugging privileges enabled. It is not exposed as a public API for arbitrary third-party apps.

In theory, an agent could emulate Xcode’s View Debugger by using LLDB to attach to a process and load a debugging library that introspects the view hierarchy. It is best suited for instrumenting the agent’s own apps.

### MTLCaptureManager and GPU command-stream capture

MTLCaptureManager, part of the Metal framework, allows creating capture scopes for GPU commands submitted to specific devices or command queues.[16] Apple’s documentation describes MTLCaptureManager as a type that can programmatically customize GPU frame capture, enabling developers to inspect GPU workloads using tools like Xcode’s Metal frame debugger.[16] MTLCaptureManager operates at the GPU command-stream level; it captures draw calls, pipeline state, and resource usage, not high-level UI layout. While it can reveal how an app uses the GPU for rendering, it does not provide a direct mapping to semantic UI elements or styles.

MTLCaptureManager is primarily intended for the app’s own rendering, with the app explicitly enabling capture and cooperating with tools. It is not designed to capture GPU commands from other apps arbitrarily; such behaviour would violate process isolation and security. Therefore, while MTLCaptureManager is useful for profiling and debugging rendering performance, it is not a general computed-style tool for agentic UI testing.<CONFIDENCE:HIGH><INFERENCE from="[MTLCaptureManager documentation[16]]">[16]

### CoreText glyph-submission interposition

One hypothetical approach to recovering computed styles is to intercept CoreText calls that layout and draw text, logs glyph runs, and infers font, size, weight, and other attributes. CoreText is widely used across macOS for text rendering; intercepting its APIs could reveal textual styling. However, such interposition typically requires dynamic library injection or function hooking, which is constrained by hardened runtime and SIP for third-party apps. Without explicit support, this approach is not practical for cross-app agents.<CONFIDENCE:LOW><INFERENCE from="[general CoreText behaviour, platform security]">

### Re-rendering into PDF/vector contexts

Many macOS apps support printing or export to PDF, which relies on generating vector graphics commands that describe their UI. An agent controlling an app via Apple Events or automation might trigger a print-to-PDF operation and then inspect the PDF’s vector content to reconstruct layout and styles. It is also limited to apps that expose print/export commands.<CONFIDENCE:LOW><INFERENCE from="[general Quartz/PDF rendering behaviour]">

### Comparative assessment

The effective “native equivalent” of `getComputedStyle` for cross-app agents on macOS is the accessibility tree. AXUIElement exposes attributes such as role, subrole, title, value, position, size, and sometimes traits that correspond to styling (for example, whether a control is enabled, selected, or has a specific role).[12] While this is not as rich as CSS computed styles, it provides a consistent, cross-toolkit semantic view. Other approaches—Core Animation layers, View Debugger, MTLCaptureManager, CoreText interposition, print-to-PDF—are either limited to the agent’s own apps or constrained by platform security. Therefore, for agentic UI/UX and end‑to‑end user-flow testing across arbitrary installed apps, accessibility plus pixel capture (ScreenCaptureKit or CGWindowListCreateImage) remains the most practical combination.<CONFIDENCE:HIGH><INFERENCE from="[AXUIElement.h[12], MTLCaptureManager documentation[16], App Nap and NSProcessInfoActivity[18]]">[12][16][18]

## Accessibility Tree as Negotiated State (Subtopic 7)

### AXManualAccessibility, AXEnhancedUserInterface, and lazy activation

Apple has introduced mechanisms such as AXManualAccessibility and AXEnhancedUserInterface to allow apps to control when and how their accessibility support is activated. Although detailed documentation is not present in the current search results, the general idea is that apps can opt into more detailed accessibility information (enhanced user interface) or manually manage accessibility activation to optimize performance.<CONFIDENCE:LOW><INFERENCE from="[general knowledge of Apple accessibility APIs]"> Accessibility trees are often built lazily; toolkits create accessibility elements when accessibility is enabled or when assistive apps connect, rather than maintaining a fully realized tree at all times. This is partly for performance and partly to avoid exposing internal structure unnecessarily.

From an agent’s perspective, this means that the accessibility tree is negotiated state: connecting an AXUIElementSystemWide reference and starting to traverse the tree can cause the target app to instantiate accessibility elements, and this may have observable performance costs. For complex apps, building the full tree can be expensive, and frequent traversal can impact responsiveness.<CONFIDENCE:MEDIUM><INFERENCE from="[AXUIElement.h guidance for assistive apps[12]]">[12] An agent that aggressively crawls the accessibility tree to maintain a global UI map may induce overhead in target apps, which could be detectable.

### Detection of agent-driven behaviour by target apps

Apps can detect when accessibility is active. For example, they can query whether accessibility is enabled for the system, and they may notice when accessibility queries or actions occur. Some apps use this information to adjust behaviour—for example, to simplify animations or adjust UI for screen readers. Others may log accessibility activity for diagnostics. This introduces an observer effect: an agent driving the app via AXUIElement can be detected, and the app may respond differently than it would to a human user.<CONFIDENCE:MEDIUM><INFERENCE from="[general accessibility API behaviour]"> For end-to-end test suites that aim to approximate real user flows, this difference may be a validity threat. However, most mainstream apps do not intentionally treat AX-driven input differently in ways that affect functional correctness; the primary differences are performance or visual.

### Accessibility projection of web content in WKWebView and Electron

Web content presented via WKWebView or Electron/Chromium is exposed to accessibility as a tree of elements representing the DOM: roles such as AXWebArea, AXLink, AXStaticText, and AXButton map to HTML elements.[CONFIDENCE:HIGH]<INFERENCE from="[general WebKit and Chromium accessibility mappings]"> Chromium’s accessibility implementation aligns with the Windows occlusion and rendering models described in its Native Window Occlusion Detection document; when a window is occluded or offscreen, accessibility may still present the DOM tree, but rendering stops.[17] However, accessibility attributes provide limited styling information; they may indicate whether an element is focusable, selected, or has certain traits, but not full computed CSS styles. For that, tools must use browser-internal APIs such as the Chrome DevTools Protocol (CDP), which provides `getComputedStyle` and layout inspection. CDP is not exposed to external agents for arbitrary apps; it is limited to browsers and dev tools.

For Codex, which operates at the OS level rather than the browser devtools level, accessibility provides only semantic structural information about web content. If Codex needs to reason about CSS-specific layout or styles, it must either capture pixels and infer visually, or rely on app-specific APIs (such as CDP) when operating within a browser context. There is no OS-level equivalent of `getComputedStyle` for arbitrary windows.<CONFIDENCE:HIGH><INFERENCE from="[Chromium occlusion documentation[17], AXUIElement.h[12]]">[17][12]

## Determinism Primitives for Agentic UI Testing (Subtopic 8)

### Virtual time and animation control

In browser automation, CDP’s `Emulation.setVirtualTimePolicy` allows controlling the flow of time for scripts and animations, improving determinism by running asynchronous tasks in a controlled virtual timeline. macOS does not provide a general OS-level API for per-process or per-window virtual time; clocks such as `CFAbsoluteTimeGetCurrent` and `mach_absolute_time` reflect real time. While individual apps can implement their own virtual time for animations or logic, agents cannot globally override time semantics for arbitrary apps via public APIs.<CONFIDENCE:HIGH><INFERENCE from="[absence of documented virtual time APIs in macOS, contrast with CDP features]">

### Quiescence and settle signals

Agents need to know when the UI has “settled” after an action—when animations, network requests, and layout changes have completed. macOS offers several indirect signals:

1. ScreenCaptureKit dirty rects can indicate areas of the screen that have changed since the last frame; if dirty rects shrink to zero over several frames, the UI may have visually settled.<CONFIDENCE:LOW><INFERENCE from="[ScreenCaptureKit design]">

2. Core Animation commit counters (internal to the framework) could, in principle, indicate when a transaction has completed; however, these are not exposed as public APIs for third-party processes.<MISSING_DATA>[Documentation of Core Animation commit counters; would require Apple framework docs.]

3. AXObserver notifications can signal specific events, such as value changes, focus changes, or layout modifications; when no relevant notifications occur for a period, the accessibility tree may be stable.[12]<CONFIDENCE:MEDIUM><INFERENCE from="[AXObserver behaviour in AXUIElement.h[12]]">[12]

4. Run-loop idleness (for example detection of idle periods in the main run loop) is observable within the agent’s own process, but not across other apps.

Each of these signals is partial. Visual settling does not guarantee that background network operations have finished; accessibility settling does not guarantee that no hidden UI changes are pending. For deterministic testing, the agent must combine multiple signals and possibly app-specific knowledge (for example a “ready” callback or test hook).

### Per-step state hashing and nondeterminism quantification

One robust way to detect divergence between runs is to compute hashes of state at each step. For a UI agent, state may encompass:

- Accessibility tree snapshots (element hierarchy and attributes).
- Captured screen frames or window images (for example hashed pixel values).
- Process-level state (for the agent’s own app).

Hashing these components at each step allows detecting when runs diverge: the first step at which hashes differ marks the divergence point. Quantifying nondeterminism as a number (for example proportion of runs in which certain steps diverge) requires repeated runs and hashing. This is conceptually straightforward and does not depend on specific macOS APIs; it can be implemented purely within the agent.<CONFIDENCE:HIGH><INFERENCE from="[general software testing and state hashing practices]"> However, the quality of the metric depends on what is hashed; partial hashing may miss subtle differences, and hashing entire frames may be sensitive to minor variations (such as rendering noise or timestamps).

Overall, macOS does not provide strong, OS-level determinism primitives analogous to CDP’s virtual time; determinism must be engineered by combining accessibility, screen capture, and app-specific instrumentation, and measured via state hashing rather than enforced via OS features.<CONFIDENCE:HIGH><INFERENCE from="[macOS documentation, lack of virtual-time APIs]">

## Isolation and Parallelism (Subtopic 9)

### CGVirtualDisplay and ScreenCaptureKit binding

CGVirtualDisplay is an API that allows creating virtual displays in macOS, used in contexts such as AirPlay and Sidecar. While detailed documentation is not present in the current search results, CGVirtualDisplay provides a way to allocate logical display surfaces without physical monitors. ScreenCaptureKit is designed to capture from these logical displays via `SCDisplay` objects; Apple’s WWDC sessions on virtualization indicate that virtual displays and virtual machines can integrate with ScreenCaptureKit to provide capture surfaces.[CONFIDENCE:LOW]<INFERENCE from="[ScreenCaptureKit and virtualization design, WWDC virtualization session[15]]">[15] For agents, CGVirtualDisplay offers a way to run UI sessions in isolation: each virtual display can host a separate test instance, and ScreenCaptureKit can capture from each display independently.

However, creating CGVirtualDisplay instances may require special entitlements or be limited to certain contexts; Apple has not made it a general-purpose tool for arbitrary apps.<MISSING_DATA>[Public documentation of CGVirtualDisplay entitlements and availability in macOS 26/27.] ScreenCaptureKit’s ability to bind virtual displays as SCDisplay objects is implicit but not explicitly documented.<CONFIDENCE:LOW><INFERENCE from="[general design, WWDC virtualization session hints[15]]">[15]

### Virtualization.framework macOS guest save/restore, latency, and fidelity

Apple’s Virtualization framework allows developers to create and manage virtual machines, including macOS guests. The `restoreMachineStateFrom(url:completionHandler:)` method enables restoring a stopped VM to a previously saved state, with the caveat that it fails if any of the VM’s configuration has changed.[14] The documentation notes that one must first save machine state via `saveMachineStateTo(url:completionHandler:)` and then restore it later to resume the VM from that checkpoint.[14] A WWDC 2026 session, “Expand the capabilities of your Virtualization app,” explains that the Virtualization framework in macOS 27 now lets apps specify provisioning options when a virtual Mac is started, such as full name, username, password, and options to enable auto-login or remote login via SSH.[15] Developers create a `VZMacGuestProvisioningOptions` object with desired settings, set it on a `VZMacOSVirtualMachineStartOptions` object, and start the VM; the guest uses these provisioning options to automate user account creation and initial configuration.[15] The session also discusses Accessory Access, which allows apps to register listeners for USB accessories and attach devices to virtual machines via `VZUSBPassthroughDeviceConfiguration`.[15]

These features make macOS guests increasingly viable as isolated agent-driven UI testing environments. Save/restore allows capturing a known-good baseline state and reusing it across test runs, improving determinism and reducing setup latency.[14] Auto-provisioning reduces manual steps. However, virtualization has limitations: there is no GPU acceleration under the Virtualization framework, as noted in a discussion about Virgl not functioning under Apple’s virtualization framework.[13] A developer notes that there is no GPU acceleration under AVF (Apple Virtualization Framework), and that Apple has only added Virtio GPU 2D support in macOS Ventura, with no 3D acceleration; GUI performance is laggy, and there is no QEMU when using virtualization.framework.[13] This implies that UI rendering fidelity and performance in macOS guests may be limited, affecting screenshot-based agents.<CONFIDENCE:HIGH><INFERENCE from="[Virtualization framework docs[14][15], UTM virtualization discussion[13]]">[14][15][13]

### TCC behaviour inside guests and pre-seeding of grants

Inside a macOS guest, TCC behaves as it does on physical machines: access to sensitive services such as Apple Events automation, screen recording, camera, and accessibility must be granted per-app, either via user consent or configuration profiles.[6] For testing purposes, one can pre-seed TCC grants by baking configuration profiles or TCC database entries into the guest image, though system-wide TCC databases are SIP-protected and may require special handling.[6] Because guests are separate OS instances, their TCC policies are isolated from the host, which is advantageous for testing but requires duplication of configuration management.

### Ceiling on concurrent agent-driven UI sessions on Apple silicon

Apple silicon SoCs provide significant CPU and GPU resources, but agent-driven UI sessions are constrained by several factors:

1. GPU limitations in virtualization: as noted, virtualization.framework macOS guests lack full GPU acceleration; multiple guests running complex UIs will compete for CPU-based rendering resources, reducing performance.[13][15]

2. ScreenCaptureKit overhead: capturing multiple displays or windows simultaneously consumes CPU and memory bandwidth; high-resolution streams for many sessions may not scale linearly.

3. Accessibility overhead: traversing many accessibility trees concurrently may induce overhead in target apps.

Empirically, the ceiling on concurrent sessions will depend on hardware (e.g., number of performance cores, GPU capability), the complexity of target UIs, and the fidelity required. Without published benchmarks, it is difficult to state a precise number.<MISSING_DATA>[Benchmarks of concurrent macOS agent-driven UI sessions on Apple silicon; would require experimental data.] From a design perspective, isolating each agent in its own macOS guest or virtual display, and carefully managing resource usage, will yield better parallelism than trying to drive many apps in a single session.<CONFIDENCE:MEDIUM><INFERENCE from="[Virtualization framework capabilities[14][15], UTM discussion of GPU limitations[13]]">[14][15][13]

## Declared Automation Contracts as Pixel-free Action Surface (Subtopic 10)

### App Intents, Assistant Schemas, and Shortcuts

App Intents and Assistant Schemas are Apple’s mechanism for declaring structured automation actions that can be invoked by system assistants (like Siri) and Shortcuts. While detailed documentation is not present in the current search results, App Intents allow developers to define actions, parameters, and entities in code, making them discoverable and callable by Shortcuts and other automation surfaces.[CONFIDENCE:HIGH]<INFERENCE from="[Apple developer docs on App Intents (not in current search results)]"> Shortcuts orchestrates these intents and other actions into workflows.

On macOS 26/27, App Intents and Shortcuts are first-class; they provide a pixel-free control plane where automation can operate at a semantic level (for example “create new note,” “send email”) without interacting with UI. However, invocation of intents is typically mediated by Shortcuts or Siri, and third-party processes cannot directly invoke arbitrary intents without going through these interfaces. URL schemes and NSServices provide additional pixel-free automation surfaces: apps declare URL schemes that accept parameters (for example `x-apple-mail:`) and NSServices for operations like text transformations. These surfaces can be invoked programmatically by other apps via `NSWorkspace` or Apple Events.

### AppleScript sdef dictionaries

AppleScript dictionaries (sdef files) describe the Apple Events interface of apps, specifying classes, commands, and properties. Many macOS apps, especially legacy ones, expose rich dictionaries; for example, Finder’s dictionary allows file operations, and Automator’s dictionary allows workflow control.[6] Agents equipped with Apple Events entitlements can use these dictionaries to script apps at a high level, avoiding pixel-based interactions.

### Coverage across typical installed app base

The coverage of declared automation contracts varies. System apps like Finder, Automator, Mail, and Calendar have robust AppleScript dictionaries and some App Intents. Third-party apps increasingly adopt App Intents and Shortcuts support, but coverage is far from universal. Many Electron-based apps have limited AppleScript support or rely on URL schemes. For a typical enterprise Mac, a substantial fraction of daily workflows can be automated via declared contracts, but many web apps and cross-platform tools do not expose such contracts. In those cases, accessibility and pixel-based automation remain necessary.<CONFIDENCE:MEDIUM><INFERENCE from="[general app ecosystem observation, HackTricks description of Finder’s automation privileges[6]]">[6]

### Evidence for Codex routing through intents before falling back to AX

Public documentation and observable behaviour do not yet provide clear evidence that Codex prefers declared automation contracts (App Intents, AppleScript, URL schemes) before using accessibility. The SkyComputerUseService’s imports and entitlements show that it uses AXUIElement and Apple Events, and its dynamic server-delivered scripts could choose to use AppleScript when available.[5][6][12] However, without detailed logging or code inspection, it is impossible to state whether Codex uses intents or AppleScript dictionaries preferentially. There is no public statement from OpenAI describing such a strategy.<INSUFFICIENT_EVIDENCE>[Whether Codex prioritizes App Intents or AppleScript over accessibility actions; requires OpenAI engineering documentation or instrumentation.] The safest assumption for design is that Codex and similar agents will mix declared automation and accessibility based on convenience and coverage, and that accessibility remains the primary control plane.

## Recommended Next Steps

For teams deciding whether to build their own macOS agent-observation and UI-testing toolchain, and whether to route actuation through accessibility/intents rather than synthetic events, several follow-up investigations are warranted.

First, an empirical study of ScreenCaptureKit’s behaviour under different occlusion and App Nap scenarios would be highly valuable. This would involve instrumenting a test app with NSProcessInfoActivity controls, creating windows in various states (visible, occluded, minimized, offscreen), and measuring SCStream outputs and CGWindowListCreateImage snapshots over time, including during display sleep and screensaver activation. The results would inform design decisions about relying on window-scoped vs display-scoped capture and about required anti-App-Nap measures.

Second, a targeted reverse-engineering of Codex’s SkyComputerUseService and authorization plug‑in, focusing on logging and observed API calls, could clarify whether it uses declared automation contracts (AppleScript, URL schemes, intents) in addition to accessibility and Apple Events. With appropriate safeguards and within legal bounds, this would allow constructing a more precise picture of its routing logic and highlight best practices for balancing semantic and pixel-based automation.

Third, experiments with macOS guests under Virtualization.framework, using save/restore and provisioning APIs, would help quantify the latency and fidelity of UI sessions and the scalability of parallel agent runs. Combining this with ScreenCaptureKit within guests would yield practical guidance on how many concurrent sessions a given Apple silicon machine can support and under what performance constraints.

Fourth, engaging with Apple’s Platform SSO and security teams, via developer support or feedback channels, could explore potential policies or entitlements to better constrain third-party authorization plug‑ins and automation agents. Comparing this prototype’s capabilities and limitations against Codex’s behaviour would inform whether the accessibility/intents plane suffices for the team’s needs and where synthetic events or virtualization might still be necessary.

## Conclusion

Codex’s macOS “computer use” agent exemplifies a powerful, modern approach to OS-level automation: it leverages accessibility APIs and Apple Events for process-directed control, ScreenCaptureKit and CGWindow metadata for observation, and a root-installed SecurityAgent authorization plug‑in to participate directly in lock-screen flows—all orchestrated by server-delivered JavaScript running in an Electron host.[2][5][6][8][12] By deliberately avoiding synthetic event injection, it operates in a plane that is less constrained by focus and SecureEventInput and more aligned with Apple’s assistive technology model, allowing actions on background windows and lock-screen UI without foregrounding them.[12] At the same time, its architecture raises non-trivial security and auditability questions: authorization plug‑ins inherently modify critical security paths; dynamic scripting blurs the relationship between entitlements and behaviour; and Apple’s platform controls (TCC, MDM, Platform SSO, Intune Apple Events settings) only partially constrain these capabilities.[2][4][6][7][11]

For teams designing agentic UI/UX and end‑to‑end user-flow testing on macOS 26/27, the analysis suggests several robust conclusions. Accessibility plus Apple Events constitutes the most durable and widely available control plane, with cross-toolkit coverage and support in locked or obscured states, albeit with performance and observer-effect considerations.[12][5][6] ScreenCaptureKit and CGWindowListCreateImage are best-available observation tools for pixels, but their behaviour under occlusion and App Nap must be carefully characterized, and NSProcessInfoActivity or virtualization may be necessary to keep rendering deterministic.[14][15][18] Declared automation contracts—App Intents, AppleScript dictionaries, NSServices, URL schemes—provide valuable pixel-free action surfaces and should be exploited where available, especially for system apps and core workflows, but coverage is incomplete and accessibility remains essential.[6]

MacOS lacks strong OS-level determinism primitives akin to CDP’s virtual time; instead, determinism must be engineered by combining quiescence signals from accessibility and screen capture, careful App Nap management, and state hashing to quantify divergence. Virtualization.framework macOS guests, with save/restore and provisioning, offer promising isolation and repeatability, but GPU limitations constrain high-fidelity parallel sessions.[13][14][15] Finally, security and fleet-management controls around authorization plug‑ins and automation entitlements are currently coarse-grained; organizations should proactively monitor authorizationdb entries, TCC automation grants, and installed plug‑ins, and consider explicit policies for third-party agents.

In sum, routing agent actuation through the accessibility/intents plane rather than synthetic events is technically sound, aligned with Apple’s design, and necessary for operating in locked and background contexts. The best-buildable toolchain today will lean heavily on AXUIElement, Apple Events, ScreenCaptureKit, and virtualization, with declared automation contracts used whenever possible. Codex’s implementation illustrates both the power and the risks of this approach; future work should focus on sharpening platform controls, improving transparency, and empirically characterizing performance and determinism to make agentic testing a first-class, secure citizen of the macOS ecosystem.
