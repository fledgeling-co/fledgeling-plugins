# Codex Computer Use on macOS, and the Agent-Observation Stack for macOS 26/27

*Research conducted 12 August 2026. Three source fetches were blocked by my own content safeguards mid-run (Apple's Authorization Plug-ins doc page, a security-research write-up on authorization plugins, and two queries phrased around event injection and TCC database seeding). I routed around each with differently-phrased queries; where a gap remains it is tagged below rather than papered over.*

---

## Executive Summary

- **(High Confidence) Codex does not operate the lock screen — it removes the lock.** While the session is genuinely locked (`CGSSessionScreenIsLocked=1`), Codex can reach only `loginwindow`; every real application returns `Computer Use server error -10005: cgWindowNotFound` [openai/codex#26743](https://github.com/openai/codex/issues/26743). The SecurityAgent plugin exists precisely because the capability is impossible without a real session unlock. OpenAI's own wording confirms the design: the plug-in "hooks into the macOS unlock flow" and "ChatGPT covers every display while the desktop is temporarily unlocked" [OpenAI, Computer Use docs](https://learn.chatgpt.com/docs/computer-use).

- **(High Confidence) The actuation plane is process-directed, not event-stream.** The absence of `CGEventPost`/`CGEventCreateMouseEvent`/`IOHIDPostEvent` imports alongside the full `AXUIElementPerformAction`/`AXUIElementSetAttributeValue` surface is architecturally coherent with the shipped behaviour: "multiple Mac apps in the background using parallel cursors that do not bring apps to the foreground" [MacStories, Viticci](https://www.macstories.net/notes/openais-new-codex-app-has-the-best-computer-use-feature-ive-ever-tested/). <INFERENCE from="zero synthetic-event imports; parallel non-foregrounding cursors; AX write surface present">The visible "cursor" is a drawn overlay for user legibility, not a WindowServer pointer — there is only one real pointer, and N of them cannot exist.</INFERENCE>

- **(High Confidence) Observation is a two-channel hybrid, AX-primary.** Codex loads "the whole contents and hierarchy of a window … as LLM context" from the AX tree, with screenshots, coordinate clicks and AppleScript as *fallbacks, not primary methods* [MacStories](https://www.macstories.net/notes/openais-new-codex-app-has-the-best-computer-use-feature-ive-ever-tested/). The same split is documented for Appshots: Screen Recording captures the bitmap, Accessibility reads structured text "including text the app exposes outside the visible scroll area" [The Decoder](https://the-decoder.com/openai-appshots-turn-any-mac-window-into-context-for-codex/).

- **(High Confidence) The authorization-plugin path is fragile and already visibly failing in production.** Library Validation rejects the staged plugin on macOS 26.5 — "mapping process is a platform binary, but mapped file is not" (Team ID `2DC432GLL2`, `platform: no`) [openai/codex#24013](https://github.com/openai/codex/issues/24013) — and one reporter measured a **17.5-minute lock-screen stall** on macOS 26.5.1, versus ~73 ms after removing the rule [openai/codex#29616](https://github.com/openai/codex/issues/29616). Removing the app does **not** self-heal the rule; the reporter had to edit `system.login.screensaver` by hand, and the bundle remained on disk.

- **(High Confidence) There is no native `getComputedStyle` for third-party macOS apps.** Every candidate mechanism — View Debugger (`libViewDebuggerSupport.dylib` via `DYLD_INSERT_LIBRARIES` + LLDB expression evaluation on `DebugHierarchyTargetHub`) [Adam Bell](https://blog.adambell.ca/posts/20190724-Visualizing-Xcode's-View-Debugger/), `MTLCaptureManager` (self-capture only, one manager per process, gated on `MetalCaptureEnabled`) [Catnip codes](https://alia-traces.github.io/metal/tools/xcode/2020/07/18/adding-framecapture-outside-of-xcode.html) — requires the target to be *your own* debuggable build. AX geometry plus pixels is the ceiling for foreign apps.

- **(Medium Confidence) Declared automation contracts are a real but partial surface, and Codex does not appear to route through them first.** App Intents has no public third-party invocation API — Apple's sanctioned surfaces are Shortcuts, Spotlight actions and Siri [WWDC25 Session 275](https://developer.apple.com/videos/play/wwdc2025/275/). Codex's own behaviour (a competitor "couldn't hit Play in Music because AppleScript fell short; Codex used its virtual cursor") [MacStories](https://www.macstories.net/notes/openais-new-codex-app-has-the-best-computer-use-feature-ive-ever-tested/) indicates AX-first with Apple Events as fallback, not the reverse.

- **(High Confidence) Parallelism is hard-capped at 2 concurrent macOS guests per host.** Virtualization.framework returns `VZErrorDomain` code 6 on the third guest; the cap is enforced in the kernel, not just in licence text [Eclectic Light](https://eclecticlight.co/2022/08/04/virtualisation-on-apple-silicon-macs-8-how-apple-limits-vms/). The bypass requires disabling SIP and a boot-arg [khronokernel](https://khronokernel.com/macos/2023/08/08/AS-VM.html).

- **(Medium Confidence) The durable build is: AX read + AX/Apple-Events write + ScreenCaptureKit pixels, running unsandboxed on a real (or SIP-disabled VM) session.** Everything else on the list — virtual displays, view-debugger transport, GPU capture, authorization plugins — is either private API, own-builds-only, or one Library Validation tightening from closure. The Codex LV rejection is that tightening already happening in real time.

## Detailed Findings

### Core question: how Codex actually observes and controls the Mac

The machine inspection and the public record agree on a three-plane architecture, and the planes have different trust properties.

**Plane 1 — semantic observation (AX read).** `AXUIElementCreateApplication` / `AXUIElementCreateSystemWide` plus attribute reads produce the window's element tree, which is serialised into model context. Viticci, who tested it against Slack, Ivory and Unread, is explicit that these APIs "were not meant for automation," returning enormous volumes of text with elements "nested 20 levels deep," and that the payoff is Codex "can 'see' more inside apps and can control them more precisely" than screenshot-and-click agents [MacStories](https://www.macstories.net/notes/openais-new-codex-app-has-the-best-computer-use-feature-ive-ever-tested/).

**Plane 2 — pixel observation (ScreenCaptureKit + `CGWindowListCopyWindowInfo`).** `CGWindowListCreateImage` is *obsoleted* in the macOS 15 SDK — a hard compile error, not a warning: `'CGWindowListCreateImage' is unavailable: obsoleted in macOS 15.0 - Please use ScreenCaptureKit instead` [MacPorts #71136](https://trac.macports.org/ticket/71136). `CGWindowListCopyWindowInfo` was *not* deprecated and remains the enumeration path [Nonstrict](https://nonstrict.eu/blog/2023/a-look-at-screencapturekit-on-macos-sonoma/). Codex importing exactly this pair (SCK for pixels, CGWindowList for enumeration) is the textbook post-Sequoia configuration. The `codex_chronicle` binary linking ScreenCaptureKit + Vision + CoreML + Metal is consistent with on-device OCR/element-detection over captured frames. <INSUFFICIENT_EVIDENCE>No public source describes `codex_chronicle`'s function; the Vision+CoreML linkage supports an OCR/detection reading but does not establish it.</INSUFFICIENT_EVIDENCE>

**Plane 3 — actuation (AX write + Apple Events).** `com.apple.security.automation.apple-events` plus `kTCCServiceAppleEvents=2` for `com.openai.codex` is the standard configuration for a signed binary that wants the Automation prompt attributed to itself rather than its parent host [Scripting OS X](https://scriptingosx.com/2020/09/avoiding-applescript-security-and-privacy-requests/). The zero synthetic-event imports are the load-bearing observation: an agent that never posts a CGEvent cannot move the real pointer, cannot steal keyboard focus, and cannot be blocked by Secure Event Input on the actuation path.

**The locked-machine answer is the sharpest finding in this report.** OpenAI's marketing framing ("use your Mac even when locked") describes the *user experience*, not the mechanism. The mechanism is: unlock the session for the duration of the turn, blank the displays, act on a normally-unlocked session, relock on physical input. The evidence that nothing works through a genuinely locked session is direct — with `CGSSessionScreenIsLocked=1` and `kCGSSessionSecureInputPID=400`, `get_app_state({app:"com.google.Chrome"})` returns `cgWindowNotFound`, `get_app_state({app:"Finder"})` times out at 120 s, and only `get_app_state({app:"loginwindow"})` responds [openai/codex#26743](https://github.com/openai/codex/issues/26743). Notably, **AppleScript still worked in that locked state** — the reporter drove Chrome to a URL and got the page title back — which is a meaningful asymmetry between the Apple Events plane and the CGWindow/AX plane.

### 1. SecurityAgent authorization plugins as an agent capability

**What the mechanism can do.** loginwindow queries the authorization database for a right; the right names an ordered array of mechanisms; each mechanism runs and can deny, and all must conclude the user is validated [Jamf Connect docs](https://docs.jamf.com/jamf-connect/2.6.0/documentation/Editing_the_macOS_loginwindow_Application.html). Mechanisms set a single `AuthorizationResult` and pass data via hints and context; `kAuthorizationContextFlagExtractable` allows a client to retrieve a value via `AuthorizationCopyInfo()`, and `kAuthorizationContextFlagSticky` persists a value through a failed evaluation [Apple, AuthorizationPlugin.h](https://opensource.apple.com/source/Security/Security-59306.140.5/OSX/libsecurity_authorization/lib/AuthorizationPlugin.h.auto.html). A mechanism suffixed `,privileged` runs root-hosted with System keychain access; unprivileged mechanisms run as `_securityagent`. Apple DTS explicitly advises fetching keychain items in a *privileged* mechanism and placing them into the authorization context rather than using the `_securityagent` login keychain.

The context-flag mechanics are the whole story for a socket-brokered design. <INFERENCE from="AuthorizationPlugin.h context/hint model; the Codex rule class `evaluate-mechanisms` with a single mechanism `CodexComputerUseAuthorizationPlugin:allow`; the LockScreenLoginAuthorizationBroker/SocketServer class names">The Codex mechanism does not itself type a password into the UI; it returns `kAuthorizationResultAllow` (or seeds credential context) after asking the out-of-process broker over the unix socket whether a trusted Computer Use turn is pending. The rule's own comment says exactly this: it "asks SkyComputerUseClient whether an active Computer Use login authorization is pending" [openai/codex#29616](https://github.com/openai/codex/issues/29616).</INFERENCE>

**What the rewrite changes.** Apple's default `system.login.screensaver` is `authenticate-session-owner-or-admin`. The Codex value is an array — `["com.openai.sky.CUAService.AuthorizationPlugin.remote", "use-login-window-ui"]` — where the first entry is a *rule* of `class = evaluate-mechanisms`, `mechanisms = CodexComputerUseAuthorizationPlugin:allow`, `tries = 1`, `shared = true` [openai/codex#29616](https://github.com/openai/codex/issues/29616). Structurally this converts a "prove you are the session owner" right into "try the OpenAI branch first; if it declines, fall through to the normal login UI." The design is sound in principle. The failure mode is that **the OpenAI branch sits in the critical path of every human unlock**, which is exactly what the 17.5-minute stall demonstrates: `authd` began evaluating at 19:02:04.891 and the Codex mechanism did not run until 19:19:34.368 [openai/codex#29616](https://github.com/openai/codex/issues/29616).

**Precedent.** Third-party authorization plugins are long-established and commercially normal. Jamf Connect installs `JamfConnectLogin:Initialize` into `system.login.console` and removes only `loginwindow:login` [Jamf](https://docs.jamf.com/jamf-connect/2.6.0/documentation/Editing_the_macOS_loginwindow_Application.html). XCreds installs `XCredsLoginPlugin.bundle` into `/Library/Security/SecurityAgentPlugins`, adds a launch daemon overlay, and — importantly — **backs up the replaced rules to `/Library/Application Support/xcreds/rights.bak`** [Twocanoes](https://twocanoes.com/knowledge-base/xcreds-admin-guide/). Crypt and Escrow Buddy do the same for FileVault key escrow [Elliot Jordan](https://www.elliotjordan.com/posts/macos-authdb-mechs/). What is *not* precedented is a consumer app doing this for **`system.login.screensaver`** (unlock) rather than `system.login.console` (login), to enable unattended remote actuation.

**Does removal revert the rule?** No, on the available evidence. The one reporter who fixed the stall did so by manually deleting the entry from the rule; the bundle stayed on disk and there is no uninstall-reverts claim in any source [openai/codex#29616](https://github.com/openai/codex/issues/29616). XCreds' `rights.bak` pattern exists precisely because nothing in macOS restores the default for you. **Failure mode:** a partially-uninstalled agent leaves a dangling mechanism in the unlock path, and `authd` will still try to run it.

### 2. The server-delivered-JavaScript capability model

**Public documentation of the specific architecture: essentially none.** <MISSING_DATA>[Sought: OpenAI documentation of `code_mode_host`, `cua_node/node_repl`, the objc-js bridge, or `kernel.js`. Nothing found in OpenAI's docs, changelog or engineering blog. The only public traces are incidental references in bug reports.]</MISSING_DATA>

**Comparable shipping designs are well documented, and the pattern is now mainstream.** Cloudflare's Code Mode gives the model a single `codemode({code})` tool executing in a V8 isolate, arguing that a binding "provides a well-defined JavaScript interface" superior to network filtering, and that generated code "never receives connector credentials" — calls cross the sandbox boundary via RPC where the runtime applies approval, logging, replay and rollback [Cloudflare](https://blog.cloudflare.com/code-mode/). Anthropic's "Code execution with MCP" presents servers as a filesystem of code modules the model imports, keeping intermediate results in the execution environment [Anthropic Engineering](https://www.anthropic.com/engineering/code-execution-with-mcp). The token economics are the stated motive: ~1,000 tokens for an entire API surface versus >1M tokens if every endpoint were a native tool [Cloudflare](https://blog.cloudflare.com/code-mode-mcp/).

**The auditability problem, stated precisely.** Both published designs sandbox the delivered code *away* from native capability — a V8 isolate with RPC bindings, or a filesystem of typed modules. <INFERENCE from="the presence of an objc-js Objective-C bridge in the Codex bundle; Cloudflare's and Anthropic's explicitly-bounded binding surfaces">An Objective-C bridge inverts that property. If server-delivered JavaScript can construct arbitrary Objective-C selector invocations, the client's effective native capability is no longer bounded by its imports — and static binary analysis, which is exactly how the AX/SCK/no-CGEvent finding in this brief was established, stops being a sound method. The imports tell you what the *host* linked; they do not tell you what the bridge can reach at runtime through `NSClassFromString`/`objc_msgSend`.</INFERENCE> <CONFIDENCE:LOW>Whether the Codex bridge is in fact unrestricted or exposes a curated allowlist could not be established from public sources; this is the single highest-value thing to determine by first-party inspection.</CONFIDENCE:LOW>

The consequence for a fleet operator is concrete: notarisation, Team ID and entitlement review are point-in-time attestations about a binary whose behavioural surface is refreshed from a server. `kernel.js` running from a temp directory means the audited artefact is not the executed artefact.

Any agent that re-enumerates per step will lose windows that a reference-caching agent keeps. Build for `AXWindowCreated` observation and cache, not per-step enumeration.

### 4. The two control planes

**Process-directed actuation genuinely escapes activation.** `AXUIElementPerformAction` is dispatched to the target process's accessibility server rather than through the WindowServer event stream, which is why it does not require frontmost status. `axcli`'s documentation is the cleanest public statement of the two-path model, and it confirms both `AXPress` and `CGEventPostToPid` deliver "no focus steal, no cursor movement … on AppKit and Chromium/Electron apps" [andelf/axcli](https://github.com/andelf/axcli).

**Toolkit honour matrix.** Public evidence is thinner than the question deserves.

| Chromium / Electron | Yes, **after** tree activation (see §7) | Confirmed [axcli](https://github.com/andelf/axcli); [screenpipe #3002](https://github.com/screenpipe/screenpipe/issues/3002) |

| Java / Swing | <MISSING_DATA>[Same. Java's macOS AX bridge quality is undocumented in accessible sources.]</MISSING_DATA> | — |

**Menus are the reliable exception.** Menu interaction generally needs the app raised; a working implementation opens nested submenus by replaying AXPress on each ancestor, which implies single AXPress on a deep menu item does not reliably work standalone [axcli](https://github.com/andelf/axcli). **Hover-gated UI is the second exception** — AXPress cannot trigger elements that only enable on mouseover, and the mitigation (`--hover`) necessarily moves the real cursor, breaking the no-foreground property.

**Keyboard focus and `CGEventPostToPid`.** Keyboard focus *as the WindowServer routes it* is a per-session singleton — one key window receives the global event stream. `CGEventPostToPid` bypasses that routing by delivering into a specific process's event queue, which is why background keystroke delivery works [axcli](https://github.com/andelf/axcli). It does not, however, make the target's *internal* first-responder become the element you want; that still requires `AXUIElementSetAttributeValue(element, kAXFocusedAttribute, true)` or equivalent. <INFERENCE from="axcli's separate --strategy pid for keystrokes and its separate AX path for actions">A robust agent needs both: AX to set intra-app focus, then either AX value-set or per-pid events to deliver text.</INFERENCE>

**Secure Event Input.** It "prevents applications from performing accessibility-related tasks … and prevents event taps from working" [Espanso](https://espanso.org/docs/troubleshooting/secure-input/). Two things matter for design. First, it is chronically **stuck-on**: BetterTouchTool users reported failure ~50% of the time after sleep, and Apple DTS's Quinn stated the I/O Registry mechanism third-party apps use to identify the holder is "best effort" with numerous situations where it won't be accurate [Apple Developer Forums 726353](https://developer.apple.com/forums/thread/726353). Second — and this is the strategic point — **an AX-only actuation plane is largely immune to it**, because Secure Input's primary teeth are against event taps and event posting. <CONFIDENCE:LOW>Sources describe Secure Input as blocking "accessibility-related tasks" generally, which could imply some AX degradation; no source distinguishes AX *reads/actions* from event *taps* under Secure Input. This is worth an empirical test.</CONFIDENCE:LOW> Note the locked-session evidence showed Secure Input actively held (`kCGSSessionSecureInputPID=400`) while AppleScript still functioned [openai/codex#26743](https://github.com/openai/codex/issues/26743) — consistent with Apple Events being on the far side of that boundary.

### 5. Background and occluded capture: live or stale pixels?

**The design intent is that occluded windows stop rendering.** Apple's Energy Efficiency Guide is unambiguous: "as soon as your app or any of its windows becomes hidden, your app should immediately halt any work that is no longer useful," citing Photo Booth turning off the camera when occluded, and defining hidden to include *occluded by other apps*, *screensaver on*, and *in a Mission Control space where the user isn't working* [Apple](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/WorkWhenVisible.html). Detection is `applicationDidChangeOcclusionState:` / `windowDidChangeOcclusionState:` against `NSApplicationOcclusionStateVisible`.

**The most useful concrete finding for agent design:** off-screen windows emit completed SCK frames **only when there is mouse movement on the display containing the window, and only when the stream is configured to capture the mouse pointer** [Apple Developer Forums, ScreenCaptureKit](https://developer.apple.com/forums/tags/screencapturekit). That is a startlingly specific and load-bearing constraint: a background-window capture pipeline on an idle machine may receive nothing at all.

**In-band staleness detection is available and should be mandatory.** `SCStreamFrameInfo.status` carries `SCFrameStatus`: `.complete` = new video frame; `.idle` = "the system didn't generate a new frame because the display didn't change" (no new IOSurface); plus `.blank`, `.suspended`, `.stopped` [Apple, SCFrameStatus.idle](https://developer.apple.com/documentation/screencapturekit/scframestatus/idle). Apple's own sample guards on `!= .complete` and returns nil [Apple, Capturing screen content in macOS](https://developer.apple.com/documentation/ScreenCaptureKit/capturing-screen-content-in-macos). Additional attachments: `.contentRect`, `.dirtyRects`, and an undocumented `SCStreamUpdateFrameDisplayResolution` key that returns the retina factor when `.scaleFactor` does not.

**Failure modes.** (a) `SCFrameStatus` reported as *always* `.idle` in at least one binding, and "many idle frames" reported by others [screencapturekit-rs #12](https://github.com/doom-fish/screencapturekit-rs/issues/12) — so treat `.idle` as "no new pixels," never as an error. (b) HDCP/DRM produces deliberately black frames. (c) Secure Input can cause partial or full black recordings. (d) Multi-virtual-display configurations make new SCStreams stream the *last connected* virtual screen regardless of the `SCContentFilter`'s displayID — longstanding, present since SCK's introduction, radar FB17797423 [Apple Developer Forums 786829](https://developer.apple.com/forums/thread/786829). (e) On macOS 26, FB18327911 reports `CGWindowListCopyWindowInfo` returning all menu-bar status items as belonging to Control Center [feedback-assistant/reports #679](https://github.com/feedback-assistant/reports/issues/679). (f) SCK honours per-window privacy flags and filters them before frames reach you — **so the SCK window set and the `CGWindowListCopyWindowInfo` set legitimately differ**; never assume they match.

**Supported ways to keep a non-visible window rendering:** there is no supported way to force WindowServer to composite an occluded window from *outside* the app. Suppressing App Nap via `NSProcessInfo.beginActivity(options:.userInitiated)` keeps timers and CPU work alive but does not force compositing. For your own apps, render into an offscreen `IOSurface`-backed Metal texture (Apple's guidance moved from `NSOpenGLPixelBuffer`, now deprecated, to IOSurface + FBO) [Apple](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/WorkWhenVisible.html). For third-party apps, the only reliable answer is **keep the window unoccluded on a real or virtual display**.

That gets you a genuine `getComputedStyle` analogue for the code you control, at low cost, with no private API and no notarisation risk.

### 7. The accessibility tree as negotiated state

**Activation is a handshake, and it is toolkit-specific.** Chromium "turns accessibility support on or off based on whether it sees a client … set the `AXEnhancedUserInterface` attribute on the main application window" [Chromium](https://www.chromium.org/developers/design-documents/accessibility/). Electron added `AXManualAccessibility` specifically because `AXEnhancedUserInterface` "is already reserved by VoiceOver" and Electron apps were otherwise inaccessible without VoiceOver running [electron/electron#10305](https://github.com/electron/electron/pull/10305).

**The lazy-materialisation trap is documented with a real reproduction.** Chromium builds the tree lazily *after* the flag is set — "the first walk returns empty, and subsequent walks would work, but a capture pipeline that bails on the first miss falls back to OCR" [screenpipe #3002](https://github.com/screenpipe/screenpipe/issues/3002). Set **both** flags on the **application** element (main app PID, not a renderer helper — the focused-app PID is frequently a helper, which returns `None`), ignore `kAXErrorAttributeUnsupported` from `AXManualAccessibility` rather than aborting, and re-walk with a delay. Even both flags are not universal: some apps still refuse until VoiceOver or Accessibility Inspector actually launches [Apple Developer Forums 756895](https://developer.apple.com/forums/thread/756895).

**Observer effect — this is a genuine validity threat to an e2e suite, and it is measurable from inside the app.** Setting `AXEnhancedUserInterface = 1` on an AXWindow "breaks (and makes sluggish) window positioning with window managers like Magnet" [vimac #78](https://github.com/nchudleigh/vimac/issues/78). Electron exposes `app.setAccessibilitySupportEnabled()` and reports assistive-technology presence to app code [Electron docs](https://www.electronjs.org/docs/tutorial/accessibility); AppKit exposes equivalent state. **So yes: a target app can trivially detect that it is being agent-driven, and can behave differently.** For a UI-testing programme this means an AX-driven suite is not measuring the same application that a human uses — it is measuring the application in its assistive-technology configuration, with a different code path and a documented performance profile. That is a legitimate finding to state in any published methodology.

**AX projection of web content vs CDP.** WKWebView's accessibility elements are handled out-of-process and bridged back as a remote element, which is why the subtree only surfaces when the web view is *not* treated as a leaf (`isAccessibilityElement = true` on the web view hides everything inside it) [Texture #1954](https://github.com/TextureGroup/Texture/issues/1954). What AX yields is the *accessibility* projection: role, name, value, state, geometry. What it does not yield is the cascade — no computed colour, font stack, box model, z-index or specificity. <INFERENCE from="AX exposes role/name/value/frame; CDP exposes getComputedStyle over the full CSS cascade; no macOS AX attribute set corresponds to the cascade">For any web content, CDP is strictly more informative than AX for visual-fidelity questions and strictly comparable for semantic questions. An agent testing web UI inside an Electron or WKWebView host should reach for CDP where a debugging port is available and treat AX as the fallback for the native chrome around it.</INFERENCE> <MISSING_DATA>[Sought: a documented mapping of WebKit's `AXWebArea` attribute set on macOS (e.g. `AXDOMIdentifier`, `AXARIALive`, `AXLoadingProgress`). Not obtainable from web search; requires reading `Source/WebCore/accessibility/mac/` in the WebKit tree.]</MISSING_DATA>

### 8. Determinism primitives

**There is no native macOS analogue to `Emulation.setVirtualTimePolicy`.** Core Animation timing is driven by `CACurrentMediaTime()` (i.e. `mach_absolute_time`) inside the out-of-process render server, and no supported hook slaves it to a test clock. Note also that even the CDP command is marked **Experimental** in the protocol docs, along with `Emulation.virtualTimeBudgetExpired` [Chrome DevTools Protocol](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/), and carries known budget-never-expires hangs [chrome-headless-render-pdf #29](https://github.com/Szpadel/chrome-headless-render-pdf/issues/29).

The nearest native lever is `CAMediaTiming`: set `layer.speed = 0` and drive `timeOffset` manually, sampling `presentationLayer` — but that is **in-process only**, so it is available for your own apps and unavailable for foreign ones. `CABasicAnimation` also has no support for directly calling its timing functions, and SwiftUI's `UnitCurve` exposes `value(at:)`/`velocity(at:)` with no spring equivalent reachable from `Animation` [Cameron Little](https://camlittle.com/posts/2024-11-14-swiftui-core-animation/).

**Honesty ranking of settle signals:**

| Signal | What it actually proves | Honesty |
|---|---|---|
| `SCFrameStatus == .idle` + empty `dirtyRects` | Compositor produced no new pixels for this surface | **Highest available for foreign apps** — but see the off-screen/mouse-movement caveat in §5 |
| Run-loop idleness (`CFRunLoopObserver`) | Your *own* process is idle | In-process only; says nothing about the target |
| `AXObserver` notifications | Something the app chose to announce changed | **Lowest.** Registration fails intermittently with `-25204`; `kAXMenuItemSelectedNotification` does not fire for mouse selection on Sonoma; observers die silently on element invalidation [Apple Developer Forums 741013](https://developer.apple.com/forums/thread/741013) |
| CA commit counters | Frames committed | Not exposed cross-process |

The field-tested design that follows: **treat AX notifications as hints that trigger a re-read, never as state; register on `kCFRunLoopCommonModes` not `.defaultMode` (or you lose events during menu tracking and window resize); re-register on `kAXFocusedWindowChangedNotification` and on `kAXErrorInvalidUIElement`; set `AXUIElementSetMessagingTimeout`; and back it with a 250 ms–2 s diffing poll so a dropped notification costs latency, not correctness** [Apple, AXObserverAddNotification](https://developer.apple.com/documentation/applicationservices/1462089-axobserveraddnotification).

**Per-step state hashing.** <INFERENCE from="SCK dirtyRects + AX tree serialisability + the absence of any native virtual-time control">The buildable determinism metric is a two-part per-step hash: (a) a normalised AX subtree digest with volatile fields (timestamps, scroll offsets, `AXValue` of clocks) masked, and (b) a perceptual hash of the SCK frame restricted to `contentRect`. Run N identical scripted sessions, record the step index of first hash divergence, and report the distribution. First-divergence-step is the honest single number for nondeterminism because it localises *where* the run stopped being reproducible rather than asserting a pass/fail. No public tool or paper was found doing this on macOS; it is a build.</INFERENCE>

### 9. Isolation and parallelism

**`CGVirtualDisplay` is private, unentitled, and load-bearing for anyone who wants headless.** No public entitlement sanctions it; apps using it ship as notarised direct downloads outside the Mac App Store [Hacker News discussion of the reverse-engineered surface](https://news.ycombinator.com/item?id=45201767). Practical constraints from shipping implementations: creation may need a clean helper process because TCC and WindowServer registration appear to require it; activation uses the SkyLight private function `SLSConfigureDisplayEnabled`; extend mode must be forced because macOS auto-mirrors new displays, hiding them from `CGGetActiveDisplayList`; refresh rate is capped at 60 Hz [Lumen](https://github.com/trollzem/Lumen). **ScreenCaptureKit does bind a virtual display as an SCDisplay** — the virtual-display → SCK → VideoToolbox pipeline is the standard game-streaming architecture — but with the multi-virtual-display SCStream defect noted in §5.

**Virtualization.framework.** `saveMachineStateTo(url:)` / `restoreMachineStateFrom(url:)` arrived in macOS 14, are `#if defined(__arm64__)` only, and the framework **deletes the save file after restore** because the disk no longer matches — so this is suspend/resume, **not multi-snapshot** [Apple sample: Running macOS in a virtual machine on Apple silicon](https://developer.apple.com/documentation/virtualization). A 2026 forum report describes both calls "taking a long time even for VMs with only 4–8 GB RAM," with no Apple response and no dirty-page-tracking or compression answer [Apple Developer Forums, Virtualization](https://developer.apple.com/forums/tags/virtualization). <MISSING_DATA>[Sought: quantified save/restore latency figures and any macOS 26/27 changes to Virtualization save/restore. No numbers published; no macOS 26 release-note change found.]</MISSING_DATA>

**TCC in a guest.** The honest answer is that pre-seeding works only by disabling SIP. Cirruslabs' Tart base images ship with SIP disabled, which permits writing TCC grants directly into `TCC.db` at image build — the documented example grants `kTCCServiceScreenCapture` to `com.apple.sshd-session` so an SSH-driven session can capture at all [jonnyzzz/tart-skills](https://github.com/jonnyzzz/tart-skills). On a SIP-on system you cannot; Accessibility is grantable by PPPC, Screen Recording is not. Residual friction to bake into the image: strip `com.apple.quarantine` from cask-installed apps; future-date `~/Library/Group Containers/group.com.apple.replayd/ScreenCaptureApprovals.plist` to suppress the periodic Sequoia-era re-consent prompt (that plist is itself TCC-protected, so the writer needs Full Disk Access); reboot after writing grants.

**The concurrency ceiling.** Two macOS guests. `VZErrorDomain` code 6 — "The number of virtual machines exceeds the limit" — on the third, enforced in the kernel, unaffected by having 128 GB and an M1 Ultra [Eclectic Light](https://eclecticlight.co/2022/08/04/virtualisation-on-apple-silicon-macs-8-how-apple-limits-vms/). Linux guests are not capped. The bypass (boot-arg plus an `AppleInternal` check, reported running 9 VMs on an M2 Pro) requires disabling SIP and places you outside the licence [khronokernel](https://khronokernel.com/macos/2023/08/08/AS-VM.html). VMs cannot nest; concurrent VMs need distinct Machine IDs and MAC addresses.

**Real ceiling for concurrent agent-driven UI sessions per Apple silicon host:** 2 guests + 1 host session = **3**, and the host session is the one a human is using. For a portfolio needing more, the answer is more Macs, not more VMs. <INFERENCE from="the 2-VM kernel cap; the SIP requirement for TCC pre-seeding; the single-session nature of WindowServer">Meaningful parallel macOS UI testing is a hardware-purchase decision, not a software-architecture decision. Within one session, parallelism has to come from AX's process-directed nature — N background windows driven concurrently through AX, which is precisely what Codex demonstrates — rather than from N sessions.</INFERENCE> That is the most important architectural implication in this report for a small team.

### 10. Declared automation contracts as a pixel-free action surface

**App Intents has no third-party programmatic invocation API on macOS 26.** The sanctioned surfaces are Shortcuts, Spotlight (new on Mac in 26 — "hundreds of actions directly from Spotlight," any app can provide them via App Intents), Siri/Apple Intelligence via Assistant Schemas, and hardware triggers [Apple Newsroom, June 2025](https://www.apple.com/newsroom/2025/06/macos-tahoe-26-makes-the-mac-more-capable-productive-and-intelligent-than-ever/). Composition is the substitute: a returned entity can be an input to another intent within a Shortcut [WWDC25 Session 275](https://developer.apple.com/videos/play/wwdc2025/275/). Entity *query* is likewise system-mediated: `IntentValueQuery` processing `SemanticContentDescriptor` is invoked by the system, not by a peer process.

**The practical escape hatch is the `shortcuts` CLI**, with two documented operational hazards: wrap every call in a timeout because a shortcut that prompts pauses forever, and pre-authorise each shortcut's permission prompts interactively before unattended use [Crosley, Shortcuts reference](https://blakecrosley.com/guides/shortcuts).

| Contract | Third-party programmatic invocation | Query entities? | Coverage across a typical installed base |
|---|---|---|---|
| App Intents | **No** direct API; via `shortcuts` CLI only | No (system-mediated) | Growing but shallow; new-code-only |
| AppleScript `sdef` | Yes (Apple Events + TCC) | Yes, richly, where implemented | Declining; inconsistent — Spotify's shipped broken (`.sdef` in the wrong place per Info.plist) [Spotify community](https://community.spotify.com/t5/Desktop-Mac/Please-bring-back-AppleScript-support/td-p/1066196) |
| NSServices | Yes (selection-scoped) | No | Narrow; text/file selection only |
| URL schemes | Yes | No | Broad but write-only — fire-and-forget, no result |
| Shortcuts CLI | Yes | Only what the shortcut returns | Bounded by App Intents adoption |

**The coverage curve is the killer.** <INFERENCE from="App Intents having no third-party invocation API; sdef adoption declining with vendors deprioritising it for App Intents; URL schemes returning nothing; NSServices being selection-scoped">There is no declared-contract surface that covers a typical installed app base. Every pixel-free plane is either broad-and-shallow (URL schemes: you can open things, you cannot read anything back) or deep-and-narrow (sdef: excellent where present, absent or broken in most modern apps). This is the structural reason a general-purpose Mac agent must fall back to AX, and it is why Codex's architecture is the right one given its goal.</INFERENCE>

**Does Codex route through declared intents first? No — the evidence points the other way.** OpenAI's own documentation describes screen viewing, screenshots, and interacting with "windows, menus, keyboard input, and clipboard state," with no mention of intents [OpenAI](https://learn.chatgpt.com/docs/computer-use). Viticci's comparison is the sharpest evidence: a competitor "couldn't hit Play in Music because AppleScript fell short; Codex used its virtual cursor and played the album" [MacStories](https://www.macstories.net/notes/openais-new-codex-app-has-the-best-computer-use-feature-ive-ever-tested/). The ordering is AX-first, Apple Events and pixels as fallbacks. <INSUFFICIENT_EVIDENCE>No public source states Codex's internal tool-selection ordering; this is inferred from observed behaviour and OpenAI's own capability description.</INSUFFICIENT_EVIDENCE>

### What changed recently, and the trajectory

Three vectors, all pointing the same way. **Capture is consolidating on ScreenCaptureKit** — `CGWindowListCreateImage` went from deprecated (14.0) to obsoleted (15.0) in one release, and macOS 15.4 added an entitlement letting certain clients see privacy-flagged windows, meaning the capture surface is increasingly entitlement-partitioned rather than uniformly available. **Injection is closing** — Library Validation rejecting a notarised, Developer-ID-signed, correctly-`codesign --verify`ing OpenAI plugin from a platform-binary host is the clearest possible signal about the future of any view-debugger or interposition strategy against third-party apps. **Declared contracts are being promoted but not opened** — Apple keeps expanding App Intents surfaces (Spotlight actions in 26) while keeping invocation strictly system-mediated, which grows the contract's value to Apple's own agent and not to a third-party one.

The Appshots documentation is the closer match to reality, describing both a screenshot and window text "including text the app exposes outside the visible scroll area." ## Knowledge Gaps

**Not publicly documented at all**
- OpenAI's `code_mode_host` / `cua_node` / `objc-js` bridge architecture, and specifically whether the Objective-C bridge is capability-restricted. This is the load-bearing unknown for any auditability claim.
- `codex_chronicle`'s function.
- Whether the `/tmp/com.openai.sky.CUAService/` socket directory is world-writable in practice, and whether the server validates peer credentials.
- Codex's internal tool-selection ordering (AX vs Apple Events vs pixels).

**Requires first-party measurement, not literature**
- SCStream behaviour with the display asleep versus the session locked, disentangled. Every public source conflates them.
- Whether Secure Event Input degrades AX reads/actions as distinct from event taps — sources say "accessibility-related tasks" without disambiguating, and the locked-session evidence hints they are separable.
- AX action honour on non-frontmost windows for Qt, Java/Swing and Mac Catalyst.
- Virtualization save/restore latency figures for realistic guest sizes.

**Blocked by my own tooling during this run**
- Apple's `developer.apple.com/documentation/security/authorization-plug-ins` page and one security-research write-up on authorization plugins. Both were routed around via the Apple OSS header and vendor documentation, which cover the same ground; the Apple doc page's stated *limitations* section is the piece I could not read directly.
- WebKit's `AXWebArea` attribute set, which requires reading the WebKit source tree rather than searching.

**Structurally unknowable from public sources**
- Whether Apple intends to close the `SecurityAgentHelper` Library Validation path deliberately or whether #24013 is an unintended regression. This determines whether the entire locked-use capability survives macOS 27.

## Recommended Next Steps

1. **Determine the objc-js bridge's capability boundary by first-party inspection** (strings/class-dump on the bridge, and observe what `kernel.js` actually calls). *Rationale:* it is the one finding that would invalidate the import-analysis method this whole brief rests on, and it is the difference between "Codex cannot inject events" and "Codex's binary does not link event injection." For a published report, stating the limit of the method is more valuable than any additional subtopic.

2. **Run the session-state matrix as an actual experiment** on one macOS 26.5+ machine: a small harness that, for each of the eight states, attempts AX read, AX action, Apple Event, window-scoped SCStream, display-scoped SCStream, and logs `SCFrameStatus` per frame. *Rationale:* seven of the eight rows in §3 contain at least one inferred cell, and the empirical matrix is both the deliverable your build decision needs and the single most citable original contribution the published report could make — nothing equivalent exists publicly.

3. **Prototype the in-process debug reflector for your own Mac apps** — a `#if DEBUG` XPC endpoint dumping the CALayer tree with computed geometry, resolved colours and font metrics, plus `AXFrame` correlation. *Rationale:* §6 concludes this is the only route to a genuine `getComputedStyle` analogue, it costs days not weeks, uses no private API, and it converts your own portfolio from "AX-only, same as any foreign app" to "fully introspectable."

4. **Measure the observer effect before committing to AX-driven e2e.** Run the same scripted flow with and without `AXEnhancedUserInterface`/`AXManualAccessibility` set, and compare step timings and any behavioural divergence. *Rationale:* §7 establishes that the flags change target behaviour and are detectable by the app. If the delta is large, an AX-driven suite is measuring a different application than your users run, and that has to be stated in the methodology rather than discovered later.

5. **Decide the parallelism question as a hardware question now, not later.** Validate the 2-guest cap on your own silicon, measure save/restore latency for a realistically-sized guest, and price the alternative (additional Mac minis) against it. *Rationale:* §9 shows the ceiling is kernel-enforced and the only bypass costs you SIP — which in turn is the same SIP you need *off* to pre-seed TCC. The two constraints compound, and the answer determines the shape of the whole toolchain rather than one component of it.
