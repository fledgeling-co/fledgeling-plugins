Virtual memory: every address is a question

Virtual addresses, page tables, paging and page faults — one mechanism, followed all the way down.

The thing most people get wrong. That an address names a place in RAM. It does not. It names a row in a table, and the operating system may rewrite that row — moving your bytes to a different chip, or out to disk and back — while your pointer stays exactly the same number it always was.

Virtual memory has several moving parts. This page follows only the one that unlocks the others, and lets the rest hang off it.

Already know this? Nothing here is gated; the tiers are a suggested order, not a queue.

The turn

A pointer is not a place. When your program runs mov al, [0x2A00], the hardware does not walk to the 10,752nd byte of RAM. It asks a question — what does 0x2A00 mean for this process, at this instant? — and a table answers.

The table belongs to the process, not to the machine, and the kernel may rewrite it between one instruction and the next. So two processes can hold the identical number and be pointed at different silicon. A page can move to another frame, or to disk and back, and the pointer never changes, because the pointer was never the location.

Predict first. Process A and Process B are both running. Both hold the pointer 0x2A00. A writes the byte 0x41 there. Commit a guess: what does B read at 0x2A00?

The two processes have different page tables. Virtual page 2 in A's table names frame 6; virtual page 2 in B's table names frame 1. Neither process can name the other's memory, because neither has a row that resolves to it.

The first answer is not silly — it was correct for decades. On a machine without an MMU, two programs holding the same address held the same byte, which is precisely why one stray pointer could take the whole system down. The third is a fair guess too, and it is what you would get if page 2 were unmapped in B; the only reason it is wrong here is that B does happen to have page 2 mapped. And sharing is still possible on purpose: when the kernel points two rows at one frame, you get shared libraries and mmap.

Where this analogy stops being true

The ledger carries the load-bearing part: a name resolved when it is used, out of a book someone else can rewrite. It fails in three places, and the third is the one that costs people real time.

  1. There is no clerk. The lookup runs in silicon, in the memory management unit, on every single access — billions per second. A desk visit per access would make the machine unusable, which is why a cache of recent answers sits in front of the table.
  2. A librarian who cannot find your book tells you so. The hardware tells your program nothing. The instruction is suspended part-way through, the kernel repairs the row, and the same instruction runs again as though the first attempt never happened.
  3. You cannot get a book that was never catalogued. An address with no valid row is not a slow request; it is one the kernel refuses to service. That is a segmentation fault.

The case where believing the analogy gives you the wrong answer: you cannot write code that detects its own page fault. Take the ledger too literally and you go looking for a return value, an errno, an exception to catch. There is none. A fault leaves no trace in your program's logic at all — only in elapsed time, which is why memory problems so often present as mysterious latency rather than as errors.

The mechanism

One access, followed end to end, three ways. The same address takes a different path depending only on what the hardware finds cached and what the row says — and the cost between the fastest and slowest path here is roughly five orders of magnitude.

Pick a path, then move through it. Nothing advances on its own unless you press Play.

Two details in that walk are worth pulling out, because they are where most confusion lives.

The offset is never translated. With 4 KiB pages, only the address above the low 12 bits is looked up. 0xA00 arrives at the physical frame exactly as it left the CPU. That is why translation granularity is a page and not a byte: the table would otherwise need a row per byte.

A fault is a trap, not a failure. The instruction does not return an error and does not complete; it is abandoned mid-flight and re-run after the kernel has repaired the row. Everything your program can observe is identical either way — the same registers, the same result. Only the clock knows.

The real thing

The walk is not the cost. The cache in front of it is the story.

A modern x86-64 core keeps roughly 64 translations in its first-level data TLB and one to two thousand in the second level, backed by a hardware walker with its own cache of upper-level rows. Hit rates above 99 per cent are ordinary. That is the only reason a design which requires a memory lookup in order to do a memory lookup is viable at all.

It also reframes what huge pages are for. When people switch a database to 2 MiB pages they are almost never buying fewer faults; they are buying TLB reach, because one cached translation now covers 512 times as much address space.

A second lens: the address is a route, not a number

The ledger explains resolution. It says nothing about why the table is affordable, and for that the useful picture is a postal sorting hierarchy rather than a book. A 48-bit address is read as a series of fields: four 9-bit indices, each selecting a slot in one 4 KiB table, and a 12-bit offset that is never translated at all.

That structure is what makes the table cheap. A flat array covering every 4 KiB page of a 48-bit space would need 236 rows at 8 bytes each — 512 GiB per process, before a single byte of your data. A radix tree materialises only the branches you actually use, so a process with 10 MiB mapped carries a handful of 4 KiB tables and nothing else.

Where the second lens stops being true. A postcode implies an office behind every prefix. Here most prefixes have nothing behind them: an unused slot in the top table is a zero word, and no table exists below it. And unlike a postcode the fields carry no meaning you could read off — address space layout randomisation scrambles them deliberately, so that an attacker who knows your binary still does not know where it landed.

A cleared present bit is a general-purpose hook

Most faults never touch a disk. Your executable is mapped rather than loaded, so its pages arrive on first touch. malloc extends a mapping and hands back a pointer with no physical memory behind it — which is why a program can allocate more than the machine has and only die later, when it writes. A fresh anonymous page points at one shared read-only frame of zeroes until the first write. And fork copies the table, not the memory: both processes point at the same frames, marked read-only, and the first write faults, copies that one page and remaps it. Every one of those is the same trap taking a different branch.

Eviction is approximate, and thrashing is a cliff

No production kernel implements true least-recently-used replacement; the bookkeeping costs more than it saves. Linux keeps active and inactive lists and reads an accessed bit that the hardware sets and the kernel periodically clears — second chance, not true recency. A separate dirty bit decides the price of eviction: a clean page is simply dropped, a dirty one must be written out first. When the working set exceeds RAM the fault rate rises non-linearly and throughput collapses. That is thrashing, and it is why a machine five per cent short of memory can run fifty times slower rather than five per cent slower.

The same table is the security boundary

Each row carries permission bits, so the hardware that translates also enforces: no-execute on data pages, read-only on program text, deliberately unmapped guard pages between thread stacks. After Meltdown, kernel page-table isolation unmaps most of the kernel while user code runs — a defence that exists in this table precisely because translation and protection are one lookup.

Still simplified here

This page followed one address, on one core, through one page table. It has not shown you: how a TLB is invalidated when a row changes, and what that costs when other cores hold the stale copy; nested paging, where a guest's translation is itself translated again by a hypervisor; the IOMMU doing all of this for devices rather than for the CPU; address space identifiers that let translations survive a context switch; or machines whose TLBs are filled by software rather than by hardware. Each is a separate piece of machinery, and none of them appeared above.
