## Detailed Findings

### Research Question 1: Cross‑Genre Architecture, Data Sourcing, APIs, Formats, and ToS Constraints

#### 1.1. Official Game APIs and Developer Portals by Genre

Across the eight target genres, official telemetry access varies widely, but there are clear anchors in certain ecosystems. Riot Games provides one of the most structured developer environments through its Developer Portal, which automatically issues a development API key when a user logs in with a Riot account and creates a Developer Portal account.[1] This development key is intended for tinkering and prototype work, deactivates every 24 hours, and must be regularly reset, highlighting Riot’s emphasis on controlled experimentation rather than long‑lived production usage on such keys.[1] Personal API keys can be obtained by registering a product intended for a small, private community, with strict rate limits of 20 requests per second and 100 requests per two minutes per region, and no access to the Tournaments API.[1][9] Production API keys, by contrast, are meant for large‑scale public products, require a working prototype, and start at 500 requests every 10 seconds and 30,000 requests every 10 minutes per region, with higher limits negotiable after further review.[1] <CONFIDENCE:HIGH>

These Riot policies directly constrain the architecture of companion apps for hero shooters and MOBAs (League of Legends, VALORANT, 2XKO), where high‑volume meta sites such as U.GG explicitly state that all of their data comes from Riot’s API and that they analyze every game available from that API.[6] U.GG’s reliance on the official API, combined with Riot’s enforcement of application and method‑level rate limits per region, means that a cross‑genre blueprint must treat Riot as a canonical example of “API‑first” telemetry: developers must design ingestion systems that respect per‑region quotas, retry and backoff semantics, and single‑product‑per‑key constraints, and they must register separate applications for each game they want to support.[1][9] Meanwhile, Riot’s API Terms require that a developer create only one developer account, complete a registration process using their game username and password, and accept that Riot may issue one or more unique Developer Keys in its sole discretion.[2] This makes it impossible to casually spin up multiple apps sharing a single key across genres; any cross‑genre season guide must treat each Riot title as an independent integration with its own keys and application metadata.[1][2][9] <CONFIDENCE:HIGH>

In the MMO/ARPG space, Bungie’s Destiny2Services documentation describes a rich REST API at `https://www.bungie.net/Platform/Destiny2`, exposing endpoints for character activity history, character stats, profile information, stats definitions, and aggregate historical stats across account characters.[14] For example, there are documented URIs such as `/{membershipType}/Account/{destinyMembershipId}/Character/{characterId}/Stats/Activities/` for activity history, `/{membershipType}/Profile/{destinyMembershipId}/Character/{characterId}/` for character information, and `/Manifest/` for obtaining the current version of the manifest as a JSON object, with `/Manifest/{entityType}/{hashIdentifier}/` providing static definitions of entities by type and hash.[14] Bungie explicitly advises against using the manifest endpoint as a “chatty alternative” to maintaining a local manifest database for large data sets, encouraging an architecture in which companion apps periodically download and store manifest data and only query individual entities when needed.[14] <CONFIDENCE:HIGH> 

Valve’s Steamworks Web API provides HTTP‑based access to many Steam features, including methods for getting and setting user stats, achievements, and leaderboard scores.[13] The public Web API is accessed via GET or POST requests to `api.steampowered.com`, using an interface/method/version URI pattern such as `https://api.steampowered.com/<interface>/<method>/v<version>/`, and requires parameters encoded as URL‑encoded form data over HTTP 1.1, with UTF‑8 encoding.[13] Many methods require authentication via a Web API key, and there is a separate partner‑only host `https://partner.steam-api.com` for publisher‑specific integrations.[13] This is complemented by third‑party services such as steamwebapi.com, whose terms of service clarify that API keys are bound to exactly one user account, may not be shared or resold, and must not be used to circumvent rate limits or quotas or to systematically appropriate data for competing aggregations.[10] steamwebapi.com warns that data may be delayed, incomplete, erroneous, or outdated and emphasizes that the service is not intended for security‑critical, business‑critical, or financial applications.[10] <CONFIDENCE:HIGH>

In the battle royale space, Epic’s Fortnite ecosystem is supported by both official and community APIs. Epic’s developer documentation defines “API” as libraries of callable functions, types, and data structures for interacting with Unreal and Fortnite systems, although the specific endpoints for Fortnite player telemetry and item data are less granular in the provided excerpt.[4] FortniteAPI.com, a community service, offers an authorization‑token‑based API for item and store information, requiring the token to be passed via an `Authorization` header or `authorization` GET parameter.[3] It exposes endpoints such as `https://fortnite-api.theapinetwork.com/store/get` for the daily store (automatically updated at 1 am CET) and `/upcoming/get` for unreleased items, with frequent updates.[3] <CONFIDENCE:HIGH> For a cross‑genre blueprint, this illustrates a common pattern: official APIs may focus on platform‑level features, while community APIs concentrate on gameplay‑adjacent data like cosmetics and items, and any architecture must decide how much to depend on third‑party providers whose terms may change independently of the game publisher.

World of Warcraft and similar MMOs have both official APIs from Blizzard and community aggregators like Raider.IO. Raider.IO’s developer API provides detailed character and guild rankings for raiding and Mythic+ content, exposing an OpenAPI 3.0 specification and allowing unauthenticated requests up to 200 requests per minute, with HTTP 429 responses on limit breach.[20] Public‑facing applications must include a link back to Raider.IO, and higher request rates require app registration at raider.io/settings/apps.[20] Raider.IO sources its data from Blizzard’s World of Warcraft API, its Live Tracking system, and community contributions, making it a hybrid aggregator that sits on top of official telemetry while adding its own instrumentation.[20] <CONFIDENCE:HIGH>

Digital card games such as Hearthstone have a different kind of “API”: a deck encoding format. The Hearthstone Deckstring format, documented by HearthSim, is a base64‑encoded compact byte string that losslessly encodes a deck using DBF IDs of cards found in game files.[11] It begins with a reserved byte `0x00`, followed by a version (currently 1) and a format varint representing Standard or Wild, and then a “cards block” split into heroes, single‑copy cards, two‑copy cards, and n‑copy cards, each preceded by a length varint and containing card IDs and counts encoded as unsigned varints.[11] This structure is deliberately compact and ensures that deckstrings for identical decks are reproducibly identical when cards are sorted by ascending DBF ID.[11] The availability of such a deckstring format enables companion apps to support import/export of decks with high fidelity and is a strong model for build or comp sharing across other genres when official telemetry is absent but structured sharing is possible.<INFERENCE from="[11]">A cross‑genre blueprint should treat Hearthstone’s deckstring as an archetype of compact build representation, even in genres without official analogues.</INFERENCE> <CONFIDENCE:HIGH>

Fighting games, racing, and sports titles often lack a unified official telemetry API akin to Riot or Bungie. #### 1.3. Build, Deck, and Loadout Import‑Export Formats

#### 1.4. Developer Keys, Rate Limits, and ToS as Architectural Constraints

Developer keys and rate limits are load‑bearing constraints in any season guide architecture. Riot’s keys are differentiated by lifecycle (development, personal, production), with development keys expiring every 24 hours and production keys requiring prototype verification and being tied to per‑region rate limits.[1] Riot enforces application rate limits per key and method rate limits per endpoint, emphasizing per‑region enforcement and forbidding public products from using development keys.[1] The Riot API FAQs further clarify that only one product/website is allowed per key and that multiple game APIs cannot be assigned to a single application/key, requiring separate application requests for each game, although an exception exists for RSO (Riot Sign On) clients that can span multiple games.[9] <CONFIDENCE:HIGH>

Riot’s 2XKO Developer API Policy underscores security expectations: use SSL/HTTPS to protect API keys, keep product descriptions and metadata up to date, and adhere to policy changes over time.[5] It introduces RSO integration for production‑level apps, requiring players to link their Riot accounts via an OAuth flow that supports both Client Secret Basic and JWT‑based modes, and uses `https://auth.riotgames.com/authorize?client_id=&redirect_uri=&response_type=code&scope=openid+offline_access` as the canonical authorization URL.[5] <CONFIDENCE:HIGH> For a cross‑genre blueprint, this suggests that production‑level integrations with account‑linked features (e.g., personalized season progression or account‑level suggestions) will need OAuth flows and must respect scopes and revocation, with Riot as one of the clearer examples.

Steam’s Web API requires a unique key per publisher or user, and its documentation includes authentication details for using the Web API key with requests to `api.steampowered.com` and `partner.steam-api.com`.[13] The steamwebapi.com terms reinforce that API keys are non‑transferable, must be kept as confidential as passwords, and that all activity under a key is the user’s responsibility until compromise is reported.[10] They also explicitly forbid reselling, sub‑licensing, or rebranding the service; sharing keys with unrelated third parties; circumvention of rate limits or quotas; deliberate overloading of infrastructure; and scraping to create competing aggregations.[10] <CONFIDENCE:HIGH> This set of restrictions strongly influences build‑vs‑buy decisions: if a season guide uses a third‑party aggregator like steamwebapi.com, it must respect those constraints and cannot treat the data as wholly free to republish or resell.

#### 1.5. Cross‑Genre Architectural Blueprint

Synthesizing these constraints, a reusable architecture for season guide websites and iOS companion apps should adopt a layered design.

At the bottom layer, an ingestion and catalog system manages per‑provider connectors: Riot (standard APIs plus RSO for authenticated features), Bungie (Destiny2Services), Steam Web API and steamwebapi.com, Epic/Fortnite plus FortniteAPI.com, Blizzard/Warcraft, Raider.IO, and, where no telemetry exists, content and schema from community sites like Dustloop.[1][2][3][4][10][13][14][17][20] Each connector is configured with provider‑specific keys, endpoints, quotas, and normalization rules, and writes to a unified event store and manifest catalog keyed by canonical IDs and enriched with patch and season labels.<INFERENCE from="[1][3][4][10][13][14][20]">This layer must support multi‑region segmentation, because Riot and others enforce rate limits per region, and meta often varies by region and platform.</INFERENCE> <CONFIDENCE:HIGH>

Above this, a normalization and analytics layer computes derived metrics: champion, comp, deck, loadout, weapon, and squad win rates; pick rates; average placement or rank outcomes; popularity scores; and “God Roll” or tier tags based on community and theorycrafter labels.[6][7][11][12][20] It enforces patch boundaries by tracking version IDs from manifests (Bungie’s manifest version, Riot’s patch metadata, MetaTFT’s patch labeling) and ensures that meta views for a given season are computed only from matches played on that patch or later, with clear separation around balance changes and content drops.[6][7][14][20] It also enforces rank and mode segmentation, mirroring U.GG’s filters for rank, region, role, and patch, MetaTFT’s separation of Hyper Roll and Double Up from ranked, and Raider.IO’s distinctions between raiding and Mythic+.[6][7][20] <CONFIDENCE:HIGH>

At the top layer, the presentation stack comprises a web front‑end and a native iOS app that share a design system but adapt to platform norms and App Store guidelines.
